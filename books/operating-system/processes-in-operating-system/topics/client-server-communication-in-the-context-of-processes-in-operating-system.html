What is Client server communication in the context of processes in operating system?

Definition:
Client-server communication is an IPC paradigm where client processes request services from dedicated server processes using structured protocols, typically involving connection establishment time TconnT_{conn}Tconn​ and service time TsvcT_{svc}Tsvc​ with total response Tresp=Tconn+Tsvc+TnetT_{resp} = T_{conn} + T_{svc} + T_{net}Tresp​=Tconn​+Tsvc​+Tnet​.

Example:
A browser (client) initiates a TCP handshake with a web server process listening on port 80, sends an HTTP GET request, and receives the HTML response, after which the server may spawn child processes or threads to handle subsequent requests concurrently.

Reason:
This model centralizes resource management and security enforcement in the server process, enabling scalable service delivery where clients remain lightweight and stateless while servers handle authentication, data persistence, and load balancing across multiple concurrent connections.

Q1. A developer is designing a distributed system where processes on different continents must communicate reliably despite occasional network partitions. Which communication method would be most suitable and why?

A.Sockets, because they provide a low-level unstructured byte stream that is efficient
B.RPC with exactly-once semantics, because it abstracts network complexity and handles retransmission ✅
C.Shared memory, because it is faster than message passing over long distances
D.Ordinary pipes, because they require no parent-child relationship
💡 Difficulty: easy | ✅ Correct: B

📖 Explanation: RPC with exactly-once semantics is designed specifically for distributed environments where network reliability is a concern. It provides a higher-level abstraction that handles message retransmission, acknowledgment, and execution guarantees, unlike raw sockets which require the application to manage all networking details. Shared memory doesn't work across machines, and ordinary pipes are limited to single-machine parent-child communication.

Q2. A student argues that 'RPC is essentially just a wrapper around socket communication that adds no significant value.' Which of the following correctly evaluates this statement?

A.The student is correct; RPC adds no value beyond raw sockets.
B.The student is partially correct; RPC only improves performance through faster data transfer.
C.The student is incorrect; RPC provides crucial abstractions like parameter marshalling, stub generation, and execution semantics that sockets lack. ✅
D.The student is correct for single-machine communication but wrong for distributed systems.
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: The student's statement reflects a common misconception. While RPC indeed uses message-passing underneath, it adds significant value by providing procedure call semantics that hide network complexity. Key features include automatic parameter marshalling/unmarshalling, stub generation for both client and server, handling of data representation differences, and implementation of 'at most once' or 'exactly once' execution semantics. These abstractions allow developers to invoke remote procedures nearly as simply as local ones, which raw sockets cannot provide.

Q3. When comparing the performance of communication mechanisms for large data transfers (e.g., 1GB file) between two processes on the same machine, which statement is most accurate?

A.Shared memory is generally fastest after setup because subsequent accesses require no kernel intervention. ✅
B.Message passing is always faster than shared memory for all data sizes.
C.Pipes provide better performance than both shared memory and message passing for large data.
D.RPC is the fastest because it bypasses the kernel entirely.
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: Shared memory provides superior performance for large data transfers between processes on the same machine because data copying is minimized. After the shared memory region is established (which requires kernel involvement), subsequent read and write operations are routine memory accesses without kernel intervention. Message passing and pipes require system calls for each transfer, copying data between kernel and user space multiple times. RPC also involves message passing overhead. The setup cost of shared memory is amortized over large data transfers, making it the most efficient.

Q4. Consider a client-server system where a client sends a request of 150 bytes and expects a response of 200 bytes. The server and client are on the same Windows machine. Which ALPC message-passing technique would Windows most likely use and why?

A.The port's message queue with copying, because messages are small (under 256 bytes). ✅
B.A section object (shared memory), because messages exceed typical threshold.
C.Direct address space access, because responses are large.
D.A combination of all three methods to maximize redundancy.
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: Windows ALPC selects the message-passing technique based on message size. For small messages up to 256 bytes, it uses the port's message queue and copies data between processes. Since both the request (150 bytes) and response (200 bytes) are under 256 bytes, this straightforward approach is selected. The section object method is used for larger messages, and direct address space access is only for extremely large data that doesn't fit in a section object. The choice optimizes performance while maintaining simplicity for small messages.

Q5. A remote procedure call fails due to a network timeout. The client receives no response. Under the 'at most once' semantics, what happens and why?

A.The RPC is retransmitted automatically until acknowledged, ensuring execution.
B.The client must manually resend the request because no ACK was received.
C.The server ignores the retransmitted request if it already processed it, preventing duplicate execution. ✅
D.The client assumes execution failed and returns an error to the application.
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: Under 'at most once' semantics, the server maintains a history of processed requests (e.g., using timestamps). When a retransmitted request arrives, the server checks its history and ignores the duplicate if already processed. This prevents duplicate execution. The client may resend after timeout, but the guarantee is that the request executes at most once. Unlike 'exactly once' which includes acknowledgment, 'at most once' doesn't guarantee the client learns of successful execution but does prevent duplicate processing, which is crucial for operations like financial transactions.

Q6. Analyze this scenario: A server crashes after executing an RPC call but before sending the acknowledgment back to the client. The client resends the request. Which semantic would prevent duplicate execution and why?

A.Exactly once, because the server sends ACK before execution.
B.At most once, because the server would detect duplicate via timestamp and ignore it. ✅
C.No semantic can prevent this scenario.
D.At least once, because duplicates are acceptable.
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: The 'at most once' semantic prevents duplicate execution even when the server crashes after execution. The server stores processed timestamps in persistent storage. When the server restarts and receives the retransmitted request, it checks the timestamp against its history and ignores the duplicate. While the client may not receive acknowledgment, the server won't execute the request twice. 'Exactly once' requires acknowledging after execution, but if the crash occurs before ACK, the client might resend. However, the server's history still prevents duplicate execution. This scenario highlights why persistent request history is critical for maintaining semantics across crashes.

Q7. What is the primary advantage of using a rendezvous daemon for RPC binding compared to fixed port addresses?

A.It eliminates the need for parameter marshalling.
B.It provides dynamic binding, allowing servers to change ports without recompiling clients. ✅
C.It speeds up communication by reducing the number of messages exchanged.
D.It guarantees exactly-once execution.
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: Fixed port addresses require compile-time knowledge of server ports, making the system inflexible. If a server changes its port, all clients must be recompiled. A rendezvous daemon provides dynamic binding where clients query the daemon (on a well-known port) for the current port of a service. The daemon returns the port, and the client can then communicate directly. This allows servers to change ports, move to different machines, or have multiple instances without affecting clients. While it adds an initial request overhead, the flexibility gain is significant for maintainable distributed systems.

Q8. Two processes on the same UNIX system need to exchange data in both directions simultaneously (full-duplex). Which communication mechanism would be most appropriate and why?

A.A single ordinary pipe, which supports full-duplex communication.
B.Two ordinary pipes, one for each direction, to achieve full-duplex communication. ✅
C.A named pipe (FIFO), which naturally supports full-duplex.
D.Shared memory, which always provides full-duplex by default.
💡 Difficulty: easy | ✅ Correct: B

📖 Explanation: UNIX ordinary pipes are unidirectional (half-duplex). To achieve two-way communication, two pipes are required, with data flowing in opposite directions on each. This is a common pattern where one pipe handles parent-to-child communication and the other handles child-to-parent. Named pipes (FIFOs) on UNIX also support only half-duplex despite being bidirectional, so two FIFOs are needed similarly. Shared memory can support full-duplex but requires explicit synchronization. For straightforward full-duplex communication with the pipe abstraction, two ordinary pipes are the standard solution on UNIX systems.

Q9. The table below shows the time (in ms) for different communication methods to transfer 10MB of data between processes on the same multicore machine: Setup: Shared Memory=50, Message Passing=5, Pipes=5. Transfer (per MB): Shared Memory=1, Message Passing=25, Pipes=30. Cleanup: Shared Memory=10, Message Passing=2, Pipes=2. Which method is most efficient for transferring 10MB if the setup and cleanup are done only once?

A.Shared Memory (70 ms) ✅
B.Message Passing (257 ms)
C.Pipes (307 ms)
D.Shared Memory, but only if setup is minimized
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: For 10MB transfer: Shared Memory = Setup(50) + Transfer(10×1=10) + Cleanup(10) = 70ms. Message Passing = 5 + (10×25=250) + 2 = 257ms. Pipes = 5 + (10×30=300) + 2 = 307ms. Shared memory is the clear winner for large transfers due to negligible per-MB transfer cost. The setup overhead (50ms) is amortized across the large transfer. Message passing and pipes incur per-transfer kernel intervention causing high per-MB costs. This explains why shared memory is preferred for large data transfers, despite higher setup overhead.

Q10. A web server listens on port 80. A client at IP 192.168.1.10 is assigned port 54321 for its connection. Another client at the same IP also connects. What will be the port assignment for the second client and why?

A.Port 54321, because the server identifies clients by IP address.
B.A port > 1024 other than 54321, to ensure a unique socket pair. ✅
C.Port 80, because both clients connect to the same server port.
D.Port 54322, because ports are assigned sequentially.
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: Each TCP connection requires a unique socket pair (client IP, client port, server IP, server port). If the second client used the same client port (54321), the socket pair (192.168.1.10:54321, server:80) would duplicate the first connection, violating uniqueness. The operating system's network stack assigns a new, unused ephemeral port (typically >1024) to each new connection from the same client to the same server. Even if the first connection closes, the port is only reassigned after the TIME_WAIT period to prevent confusion. This ensures all connections are uniquely identified.

Q11. A student proposes using ordinary pipes for communication between two processes on different machines in a distributed system. Why is this approach problematic?

A.Ordinary pipes are unidirectional and cannot support the required communication.
B.Ordinary pipes require a parent-child relationship and cannot span network boundaries. ✅
C.Ordinary pipes are too slow for network communication.
D.Ordinary pipes do not support data structures larger than 256 bytes.
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: The student's proposal reflects a fundamental misunderstanding of ordinary pipes. Ordinary pipes in both UNIX and Windows are limited to communication between processes that have a parent-child relationship (created via fork() or similar) and must reside on the same machine. They cannot be used across network boundaries because they are implemented using file descriptors within a single system's kernel. For cross-machine communication, sockets, RPC, or named pipes on Windows (which can work across machines) must be used. This is a classic example of using the wrong tool for the problem domain.

Q12. In the Java date server example (Figure 3.21), the server runs in an infinite loop: while(true) { accept connection; send date; close; }. What happens if a client connects but the network is slow and the date takes 5 seconds to send?

A.The server blocks on the slow client, preventing other clients from connecting. ✅
B.The server spawns a new thread for each client to handle slow connections.
C.The server continues accepting new connections because accept() is non-blocking.
D.The server times out the connection after 1 second.
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: The Java date server is single-threaded and synchronous. When a client connects, the server enters a loop and processes that client completely before returning to accept() for the next connection. If sending the date is slow (due to network latency), the server blocks in the write operation for that client. Other clients attempting to connect will wait in the listen queue but cannot be accepted because the server is occupied. This is a classic limitation of single-threaded servers. Q13. What does parameter marshalling in RPC accomplish, and why is it necessary?

A.It compresses data to reduce network bandwidth usage.
B.It converts data to a machine-independent format for transmission and reconstructs it at the destination. ✅
C.It encrypts data for security during transmission.
D.It caches data to improve performance on repeated calls.
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: Parameter marshalling is essential in RPC because different computer architectures represent data differently (e.g., big-endian vs. little-endian integers, different floating-point representations). Marshalling converts the procedure parameters from the client's machine-dependent format to a standard, machine-independent format like XDR (External Data Representation) before transmission. The server unmarshals the data, converting it to its local format. Without marshalling, the server might misinterpret integer byte order or other data representations, leading to incorrect results. This is transparent to the programmer, who calls the RPC as if it were a local procedure.

Q14. Two processes are communicating using a socket. If the server crashes and restarts, what happens to the established socket connection and why?

A.The connection remains established because sockets use connectionless UDP.
B.The connection is broken because TCP connections are tied to the server's IP and port. ✅
C.The client automatically reconnects because sockets are self-healing.
D.The connection continues but data is lost.
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: TCP socket connections are stateful and identified by the socket pair (client IP:port, server IP:port). The server's operating system maintains connection state. When the server crashes and restarts, it loses all TCP state information (sequence numbers, connection table, etc.). The client's socket is now connected to a non-existent server endpoint. Any further sends will result in errors (e.g., connection reset). The client must establish a new connection. Unlike connectionless UDP, TCP doesn't recover automatically because it maintains state for reliable, ordered delivery. This state is lost on crash.

Q15. A client-server system uses a named pipe on Windows. The server is on Machine A, and the client is on Machine B. They need to exchange large files. Which statement about this setup is correct?

A.Named pipes on Windows support full-duplex communication across machines. ✅
B.Named pipes on Windows cannot be used across machines; only ordinary pipes can.
C.Named pipes on Windows are unidirectional even across machines.
D.The client and server must have a parent-child relationship.
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: Windows named pipes are significantly more powerful than their UNIX counterparts. They support full-duplex communication (data can flow both ways simultaneously) and can be used for communication between processes on the same machine or across network boundaries. This makes them suitable for client-server communication where bidirectional data flow and cross-machine operation are needed. The client connects using ConnectNamedPipe(), and communication uses ReadFile()/WriteFile(). No parent-child relationship is required, unlike ordinary pipes. This rich feature set makes Windows named pipes a robust IPC mechanism.

Q16. A client attempts an RPC call but receives an error that the server's port has changed. Which binding mechanism would have prevented this issue and how?

A.Fixed port binding; it prevents ports from changing.
B.Dynamic binding via a rendezvous daemon; the client queries for the current port. ✅
C.No binding mechanism can handle changing ports.
D.Socket binding; ports are automatically updated.
💡 Difficulty: easy | ✅ Correct: B

📖 Explanation: Dynamic binding using a rendezvous daemon (matchmaker) solves this problem. The client first contacts the well-known rendezvous daemon port, sending the service name. The daemon returns the current port where the service is listening. The client then communicates directly on that port. If the server changes its port, the daemon is updated, and clients receive the new port on their next query. This provides flexibility and decouples clients from fixed server ports. Fixed port binding would require recompiling clients, which is impractical. The rendezvous daemon is a standard pattern in RPC systems for service discovery.

Q17. Compare the communication models: Sockets provide unstructured byte streams, RPC provides procedure call semantics, and Pipes provide simple producer-consumer data flow. Which offers the highest level of abstraction for distributed application development and why?

A.Sockets, because they give the most control over data.
B.RPC, because it abstracts network details and presents familiar procedure calls. ✅
C.Pipes, because they handle synchronization automatically.
D.All offer the same level of abstraction.
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: RPC provides the highest level of abstraction for distributed programming. It allows developers to invoke remote procedures using the familiar local procedure call syntax, hiding networking complexity like message formatting, transmission, retransmission, and data representation differences. Sockets require manual handling of message boundaries, serialization, and error recovery. Pipes are a simple streaming abstraction but don't work across networks. While sockets offer more control and are commonly used, RPC significantly reduces development effort by providing a higher-level programming model, which is why it's preferred for many distributed applications, despite potential performance trade-offs.

Q18. A server processes client requests but also must send notifications to clients spontaneously (not in response to a request). Which communication feature in Windows ALPC is designed for this scenario?

A.Connection ports, which allow any client to connect.
B.Communication ports with callback mechanism, allowing notifications. ✅
C.Section objects, for sharing large amounts of data.
D.The port's message queue, for queuing notifications.
💡 Difficulty: easy | ✅ Correct: B

📖 Explanation: Windows ALPC's callback mechanism allows clients and servers to accept requests and send notifications when they would normally be expecting a reply. This is designed for scenarios where the server needs to send unsolicited messages (like notifications) to the client. While normal ALPC communication follows a request-response pattern, the callback mechanism extends this to allow asynchronous server-initiated communication. The client must be prepared to receive these callbacks. This is more sophisticated than simple request-response and enables patterns like event notification from the server to clients.

Q19. A process uses a UDP socket (connectionless) to send data to a server. What fundamental difference from TCP sockets affects reliability and why?

A.UDP ensures reliable delivery through acknowledgments; TCP does not.
B.UDP does not establish a connection; TCP does, providing reliable ordered delivery. ✅
C.UDP provides flow control; TCP does not.
D.UDP and TCP are identical in reliability.
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: The fundamental difference between TCP and UDP sockets is the connection establishment. TCP is connection-oriented: it establishes a connection through a three-way handshake, maintains sequence numbers, and provides reliable, ordered delivery with retransmissions. UDP is connectionless: each datagram is sent independently, and there's no guarantee of delivery, ordering, or duplicate detection. This makes UDP faster and more lightweight but unreliable. The choice depends on requirements: TCP for reliability (e.g., web, file transfer), UDP for speed where some data loss is acceptable (e.g., streaming, gaming). This architectural difference at the protocol level directly impacts application behavior.

Q20. A client on a little-endian machine calls an RPC on a big-endian server. The integer 0x12345678 is passed as a parameter. Without marshalling, what would the server interpret and why?

A.0x12345678, because integers are the same on all machines.
B.0x78563412, because the byte order is reversed without proper conversion. ✅
C.0x00000000, because data is lost in transmission.
D.An error, because the call would not be accepted.
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: This illustrates the endianness issue in RPC. On a little-endian machine, the least significant byte is stored first: 78 56 34 12. On a big-endian machine, the most significant byte is stored first: 12 34 56 78. If the client sends its little-endian representation without marshalling, the server reads the bytes in big-endian order: 78 56 34 12, which is 0x78563412 - completely different from the intended value. Marshalling converts to a standard format (e.g., XDR) before transmission, and the server unmarshals to its format, ensuring correct interpretation. This is why marshalling is essential for heterogeneous systems.

Q21. What is the role of stub code in RPC implementations like Windows MIDL-compiled stubs?

A.Stubs provide error handling for network failures.
B.Stubs handle marshalling and unmarshalling of parameters and locate the remote procedure. ✅
C.Stubs improve performance by caching RPC results.
D.Stubs manage socket connections for the application.
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: Stubs are the key to RPC abstraction. On the client side, the stub (generated from an IDL specification) implements the remote procedure's interface locally. When the client calls the remote procedure, it actually calls the stub, which marshals the parameters, constructs the network message, sends it to the server, and waits for the reply. On the server side, a stub unmarshals the request, calls the actual procedure, and marshals the return value back. This transparently handles all networking details, allowing the client to call remote procedures just like local ones. MIDL-generated stubs are a concrete example of this pattern.

Q22. In the context of pipes, the UNIX command 'ls | more' uses an ordinary pipe. If ls produces 1MB of output and more reads slowly, what happens to the ls process and why?

A.ls completes and exits immediately, discarding output that more hasn't read.
B.ls blocks when the pipe buffer fills until more reads data, implementing flow control. ✅
C.ls continues running but outputs go to /dev/null.
D.The system crashes due to buffer overflow.
💡 Difficulty: easy | ✅ Correct: B

📖 Explanation: This is a classic demonstration of bounded buffer flow control. The pipe has a finite buffer (typically several KB). When 'ls' writes to the pipe and fills the buffer, the write() system call blocks the ls process. It cannot continue writing until 'more' reads data from the other end, freeing buffer space. This is a form of implicit synchronization: the producer (ls) is blocked when the consumer (more) can't keep up, preventing overflow. This demonstrates how operating systems use blocking I/O to implement flow control in IPC mechanisms, ensuring that data isn't lost and processes are properly synchronized.

Q23. A critical distributed service requires that an RPC executes exactly once, even if both the network and the server crash. Which combination of mechanisms is required?

A.At most once detection plus client-side retransmission and server-side persistent request history. ✅
B.Only client-side retransmission with acknowledgments.
C.Only server-side duplicate detection.
D.Exactly once cannot be guaranteed if the server crashes.
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: Guaranteeing exactly once execution in the presence of both network failures and server crashes requires multiple mechanisms working together. Client-side retransmission ensures the request eventually reaches the server even with network problems. Server-side duplicate detection (at most once) prevents duplicate execution on retransmission. Critically, the duplicate detection history must be persistent (on disk) so it survives server crashes. When the server restarts, it restores its history and can still detect duplicates from before the crash. Additionally, persistent acknowledgments ensure the client knows execution completed. Without persistence, a duplicate sent after server restart wouldn't be detected, leading to potential duplicate execution. This complexity is why exactly once is challenging to implement correctly.

Q24. A company has a distributed application where multiple clients send small control commands to a server, and the server broadcasts status updates to all clients. Which client-server communication model best fits this scenario?

A.Direct RPC for both commands and broadcasts.
B.Direct RPC for commands and multicast sockets for broadcasts. ✅
C.Message passing with mailboxes for both commands and broadcasts.
D.Sockets for commands and ordinary pipes for broadcasts.
💡 Difficulty: easy | ✅ Correct: B

📖 Explanation: This mixed communication pattern is best addressed with different mechanisms for each purpose. Commands (small, request-response) map well to RPC or direct sockets. Status broadcasts (one-to-many) map well to multicast sockets (UDP MulticastSocket in Java). This combines the reliability and simplicity of RPC for point-to-point communication with the efficiency of multicast for one-to-many distribution. Using RPC for broadcasts would be inefficient (N separate requests), while using multicast for commands would lack reliability. This scenario illustrates the practical need to combine multiple communication models for optimal distributed system design.

Q25. A process creates an ordinary pipe in UNIX and then forks. The parent closes the read end, and the child closes the write end. What happens if the child tries to write to the pipe after the parent closes the read end and why?

A.The write succeeds because the pipe is still open on the child's side.
B.The write fails with a SIGPIPE signal, because there are no readers for the pipe. ✅
C.The write blocks indefinitely waiting for a reader.
D.The child's write operation causes a system crash.
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: This tests understanding of pipe semantics. When all read ends of a pipe are closed, the pipe is broken. In UNIX, writing to a pipe with no readers generates a SIGPIPE signal, which by default terminates the process. This is a protection mechanism: if no process is reading the data, there's no point in the writer continuing. The correct protocol for pipes is to close the unused ends: the writer closes the read end, and the reader closes the write end. If the reader closes its end prematurely (as in this scenario), the writer should detect this and exit. This prevents orphaned writers from blocking indefinitely.

Q26. A student's program uses two ordinary pipes for bidirectional communication between a parent and child process. The parent writes to pipe1, child reads from pipe1. Child writes to pipe2, parent reads from pipe2. After the parent writes a message, it closes pipe1's write end and then waits for the child's response on pipe2. The child reads the message, then writes its response on pipe2. The child then closes pipe2. What is the correct order for closing the unused ends of pipes in both processes?

A.Parent closes read of pipe1 and write of pipe2. Child closes write of pipe1 and read of pipe2. ✅
B.Parent closes write of pipe1 and read of pipe2. Child closes read of pipe1 and write of pipe2.
C.Parent closes write of pipe2 and read of pipe1. Child closes read of pipe2 and write of pipe1.
D.No closing is necessary.
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: For correct pipe operation, each process should close the end of each pipe it doesn't use. Pipe1 is for parent-to-child: the parent writes, child reads. So, parent closes pipe1's read end (unused) and child closes pipe1's write end (unused). Pipe2 is for child-to-parent: the child writes, parent reads. So, child closes pipe2's read end (unused) and parent closes pipe2's write end (unused). This gives Parent: closes read of pipe1 (unused) and write of pipe2 (unused). Child: closes write of pipe1 (unused) and read of pipe2 (unused). This ensures data can flow properly and processes can detect EOF when the other side closes its end.

Q27. Which statement correctly compares the communication capabilities of ordinary pipes, named pipes (FIFOs), and sockets?

A.All three support bidirectional communication across network boundaries.
B.Only sockets support full-duplex communication across network boundaries. ✅
C.Named pipes support full-duplex across networks; ordinary pipes are unidirectional.
D.All three are limited to single-machine communication.
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: Sockets are the only mechanism among the three that universally supports full-duplex communication across network boundaries. Ordinary pipes are unidirectional and limited to parent-child communication on the same machine. UNIX named pipes (FIFOs) support bidirectional but half-duplex communication on the same machine (they cannot cross network boundaries). Windows named pipes are an exception: they support full-duplex across networks, but UNIX named pipes do not. This comparison highlights that choosing the right IPC mechanism depends on specific requirements like directionality, machine boundary, and process relationship.
