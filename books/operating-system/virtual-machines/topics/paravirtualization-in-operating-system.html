Q1. A system administrator notices that a paravirtualized guest performs I/O operations with significantly lower CPU overhead compared to a fully virtualized guest on the same hardware. What is the primary architectural reason for this difference?

🔹 A. Paravirtualized guests use a shadow page table that eliminates TLB misses
🔹 B. Fully virtualized guests must trap and emulate each I/O instruction, while paravirtualized guests use hypercalls for I/O
🔹 C. Paravirtualized guests dedicate a physical CPU core exclusively for I/O processing
🔹 D. Fully virtualized guests have a larger cache size allocated by the hypervisor

💡 Difficulty: medium | ✅ Correct: B

📖 Explanation:

The key difference is that full virtualization uses binary translation or hardware-assisted trap-and-emulate for privileged I/O instructions, causing a VM exit on each I/O operation. Paravirtualization replaces these with hypercalls—explicit calls from the guest to the hypervisor—which are lightweight function calls, not costly traps. This reduces the number of context switches and mode transitions, directly lowering CPU overhead. Options A, C, and D are incorrect because shadow page tables affect memory, not I/O, and CPU core dedication or cache allocation are not inherent to paravirtualization.

Q2. In a paravirtualized environment, a guest operating system's scheduler attempts to perform a privileged operation that would normally cause a trap. How does the paravirtualized kernel handle this to maintain performance?

🔹 A. It invokes a hypercall, passing the operation parameters to the hypervisor for safe execution
🔹 B. It emulates the operation in software using a binary translator within the guest
🔹 C. It temporarily switches the CPU to real mode to execute the instruction natively
🔹 D. It masks the interrupt and retries the instruction after a fixed delay

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation:

A paravirtualized kernel is explicitly modified to know it is running on a hypervisor. Instead of using unsafe privileged instructions that trap, it uses a hypercall—a software interrupt or similar mechanism—to request services from the hypervisor. This is a synchronous call, not emulation (B), and avoids the cost of a trap. Option C is impossible as real mode is not relevant to privilege levels in modern CPUs. Option D describes a retry mechanism, not how privileged operations are handled.

Q3. Consider a paravirtualized Linux system where the 'time' command on a compute-intensive task returns a lower 'system' CPU time compared to the same task on a fully virtualized system. Which component of the paravirtualized architecture is most directly responsible for this reduction?

🔹 A. The paravirtualized network driver, which offloads TCP checksumming
🔹 B. The paravirtualized timer and clock interrupt management, which reduces the number of asynchronous exits
🔹 C. The paravirtualized memory management unit that uses larger page sizes
🔹 D. The paravirtualized storage driver that uses scatter-gather I/O

💡 Difficulty: medium | ✅ Correct: B

📖 Explanation:

System CPU time measures time spent in kernel mode. In full virtualization, each timer interrupt causes a VM exit to the hypervisor, incurring high overhead. Paravirtualized guests often use a 'virtualized' timer where the hypervisor provides a time source and the guest schedules its own ticks, or uses a 'one-shot' timer to reduce interrupt frequency. This directly reduces the number of involuntary exits, lowering system CPU time. Options A, C, and D affect I/O or memory throughput, not CPU time measurement for compute tasks.

Q4. A developer debugs a paravirtualized guest and observes that a memory allocation routine returns a physically contiguous block of memory, but the guest's virtual addresses are fragmented. What paravirtualization feature enables this despite the lack of hardware IOMMU support?

🔹 A. The hypervisor presents a pseudo-physical memory map and uses a shadow page table that maps fragmented guest-physical to contiguous machine-physical
🔹 B. The guest uses a 'balloon' driver to deflate memory, forcing physical contiguity
🔹 C. The guest kernel uses a 'direct' mapping where virtual address = physical address + offset
🔹 D. The hypervisor uses binary translation to rewrite the memory allocation code

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation:

Paravirtualized guests operate on 'guest-physical' addresses (also called pseudo-physical). The hypervisor maintains a second-level translation (shadow page tables or nested page tables) from this pseudo-physical address to the actual machine-physical address. Thus, the guest can see a contiguous pseudo-physical region, while the hypervisor maps it to non-contiguous machine pages. This is a core aspect of memory virtualization. Option B describes memory ballooning for reclaiming memory, not for allocation contiguity. Option C is a simplification often used in early kernels, but not a feature to fix fragmentation. Option D is for instruction emulation, not memory.

Q5. A system with 4 CPU cores runs a paravirtualized guest that reports 8 virtual CPUs. The host scheduler shows that the guest's vCPUs are constantly migrating between physical cores. What is the MOST significant performance implication of this migration pattern for this paravirtualized system?

🔹 A. Increased cache misses and TLB flushes, as the guest's page tables and CPU caches are not automatically migrated
🔹 B. All vCPUs will run in lockstep to maintain cache coherency, reducing overall throughput
🔹 C. The hypervisor will force a VM exit on every migration to update the guest's CPUID information
🔹 D. The guest will be unable to use its paravirtualized spinlocks, causing deadlocks

💡 Difficulty: medium | ✅ Correct: A

📖 Explanation:

When vCPUs migrate, the physical CPU's L1/L2 caches and TLBs contain data from the previous vCPU. The new vCPU suffers cold-cache and TLB-miss penalties. The guest's page tables are virtual, but the hardware TLB caches machine-physical mappings; these must be refilled. Option B is false; vCPUs do not run in lockstep unless explicitly configured. Option C is incorrect; CPUID is a static feature set and does not trigger an exit on migration. Option D is false; paravirtualized spinlocks help with yielding, not migration.

Q6. Which statement accurately contrasts the memory management approach of a paravirtualized guest versus a guest using hardware-assisted virtualization (e.g., Intel EPT)?

🔹 A. Paravirtualization relies on shadow page tables maintained by the hypervisor, while EPT uses nested page tables managed by the CPU
🔹 B. Both technologies require the guest to maintain its own page tables and a shadow copy simultaneously
🔹 C. EPT requires the guest to be modified to use 2MB huge pages, whereas paravirtualization does not
🔹 D. Paravirtualization uses a single-level translation, while EPT uses a two-level translation without TLB caching

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation:

In shadow paging (classic paravirtualization), the hypervisor builds and maintains shadow page tables that map guest-virtual to machine-physical. This is software-managed. With EPT (Extended Page Tables), the CPU provides a second level of translation (nested) using hardware, reducing hypervisor overhead. Option B is incorrect because EPT does not require shadow tables. Option C is false because huge pages are optional for both. Option D is incorrect; both use multi-level translations and both use TLB caching.

Q7. A paravirtualized guest's network throughput drops drastically when the hypervisor enables 'checksum offloading' on the virtual NIC. The guest driver supports this feature. What is the most likely reason for this unexpected drop?

🔹 A. The guest's CPU is too slow to compute the checksum, causing a bottleneck
🔹 B. The hypervisor offloads the checksum, but the guest driver incorrectly re-calculates it, causing packet corruption and retransmissions
🔹 C. The physical NIC does not support checksum offloading, so the hypervisor emulates it in software, adding overhead
🔹 D. The paravirtualized network driver uses a ring buffer that is too small, causing packet drops

💡 Difficulty: hard | ✅ Correct: B

📖 Explanation:

This is a classic error. If the hypervisor offloads the checksum calculation to hardware (or computes it), the guest driver must NOT also compute it. If the guest driver erroneously calculates and inserts a checksum into a packet that already has one, the packet becomes corrupted. The receiver drops it, and TCP retransmits, causing a throughput collapse. Option A is unlikely as checksum is simple. Option C is plausible but the question specifies the hypervisor 'enables' it, implying support. Option D is a generic network issue, not specific to the described feature.

Q8. The graph shows CPU utilization (Y-axis) over time (X-axis) for a fully virtualized (FV) and a paravirtualized (PV) guest under a constant workload of 1000 I/O requests per second. The PV line shows periodic sharp spikes of 100% utilization while the FV line shows a steady 70%. Which architectural difference best explains the PV spikes?

🔹 A. The PV guest's 'idle loop' uses a hypercall to block until the next interrupt, causing a wake-up storm on the host when interrupts occur
🔹 B. The PV guest is processing interrupts at a higher frequency due to a misconfigured virtual timer
🔹 C. The PV guest is using a 'busy-wait' spinlock for I/O completion, yielding the CPU while waiting, which shows as 100% in the guest view but the host is idle
🔹 D. The FV guest is using hardware interrupt coalescing, while the PV guest is not, leading to more interrupts

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation:

A paravirtualized guest's idle loop often invokes a 'halt' hypercall, telling the hypervisor it's idle. When a device interrupt (like a network packet) arrives, the hypervisor must wake that vCPU. If many interrupts arrive, this causes a rapid series of wake-ups and context switches, showing high utilization on the guest's CPU counters (as it's always ready to run). Option B is a timer issue, not I/O. Option C is incorrect; spinlocks cause high CPU but don't 'yield'. Option D is about interrupt coalescence, but the core PV issue is the wake-up mechanism, not coalescence.

Q9. In a paravirtualized system, the 'event channel' mechanism is used for inter-domain communication. If a domain sends an event but the receiving domain is in a 'halted' state (idle), what is the correct sequence of operations?

🔹 A. The hypervisor delivers the event to a pending bitmask and immediately schedules the receiving domain
🔹 B. The hypervisor discards the event to prevent resource exhaustion
🔹 C. The hypervisor sets a pending bit in the receiver's event mask and injects a virtual interrupt on the next scheduling opportunity
🔹 D. The hypervisor blocks the sending domain until the receiver acknowledges the event

💡 Difficulty: hard | ✅ Correct: C

📖 Explanation:

Event channels are a lightweight notification mechanism. The hypervisor maintains a shared bitmap of pending events for each domain. When an event is sent, the hypervisor marks the corresponding bit. If the receiver is not running, the hypervisor will mark it as runnable (or wake it up) when it next goes through the scheduler. It does not immediately preempt the current vCPU to schedule the receiver (A) unless it has priority. It does not discard events (B). It does not block the sender (D); that would be a synchronous IPC, not an asynchronous event.

Q10. A team is porting a legacy operating system to run on a paravirtualized platform. They must modify the kernel's page fault handler. In a non-virtualized system, a page fault loads a page from disk. In this new environment, what fundamental change must the handler implement?

🔹 A. It must translate the faulting virtual address to a guest-physical address before invoking the hypervisor
🔹 B. It must use a hypercall to request a new page table from the hypervisor, as the guest cannot manage its own memory
🔹 C. It must disable interrupts before handling the fault to prevent a VM exit during the handler
🔹 D. It must call a hypercall to map a machine-physical page to the faulting virtual address, as the guest cannot directly manipulate hardware page tables

💡 Difficulty: medium | ✅ Correct: D

📖 Explanation:

In a paravirtualized system, the guest kernel is responsible for its own virtual memory management, but it does not have direct access to the hardware's page tables (the MMU). To map a virtual address to a physical frame, it must issue a hypercall (e.g., 'update_va_mapping') to the hypervisor, which then updates the shadow or nested page tables on behalf of the guest. Option A is a step, but the core action is the hypercall to actually change the mapping. Option B is false; the guest manages its own page tables logically. Option C is incorrect; disabling interrupts doesn't prevent VM exits.

Q11. What is a fundamental limitation of paravirtualization that does NOT apply to full virtualization using hardware-assisted virtualization (like Intel VT-x)?

🔹 A. Higher overhead for I/O operations due to the need for hypercalls
🔹 B. The requirement that the guest operating system kernel must be modified to be aware of the hypervisor
🔹 C. Inability to run multiple guests due to resource contention on the hypervisor
🔹 D. Lack of support for 64-bit guest operating systems on 32-bit hardware

💡 Difficulty: easy | ✅ Correct: B

📖 Explanation:

Paravirtualization relies on the guest OS knowing it is virtualized and cooperating with the hypervisor via hypercalls. This requires explicit modification of the guest kernel (or paravirtualized drivers). Full virtualization with VT-x/AMD-V runs unmodified guest OSes because the hardware handles privilege level trapping. Options A, C, and D are incorrect: I/O overhead is lower for PV, multiple guests are supported, and PV does support 64-bit on 64-bit hardware (or via emulation).

Q12. A paravirtualized guest is running a database workload that performs many small synchronous writes to a virtual disk. The administrator notices that the 'iowait' time on the guest is very low, but the overall transaction latency is high. Which paravirtualization mechanism is MOST likely masking the true I/O latency from the guest's perspective?

🔹 A. The hypervisor is using a 'write-back' cache on the virtual disk, acknowledging the write before it reaches physical storage
🔹 B. The guest's paravirtualized block driver is using a ring buffer that reorders writes, causing out-of-order completion
🔹 C. The hypervisor is throttling the guest's I/O bandwidth, but reporting completion to keep the guest's CPU busy
🔹 D. The paravirtualized clock is drifting, causing the guest to misreport time, making 'iowait' appear low

💡 Difficulty: medium | ✅ Correct: A

📖 Explanation:

In many paravirtualized storage setups, the hypervisor or the backend driver can use a write-back cache. The driver acknowledges the I/O as 'complete' as soon as it is placed in the hypervisor's internal queue, not when it reaches the physical disk. This makes the guest's iowait low, but the actual physical I/O latency (including disk seek, etc.) is hidden from the guest. Option B is a real phenomenon (reordering), but it wouldn't mask latency; it would affect ordering. Option C is possible but less common. Option D would affect time measurement, but not the actual I/O latency.

Q13. In a paravirtualized environment, which of the following is the MOST significant security concern that arises from the need to modify the guest kernel?

🔹 A. The modified kernel may introduce new vulnerabilities due to the added code for hypercalls
🔹 B. The hypervisor can directly access guest memory, bypassing the guest's own access controls
🔹 C. The paravirtualized drivers run in user space, making them susceptible to privilege escalation attacks
🔹 D. The hypervisor's event channel mechanism lacks authentication, allowing any guest to send events to any other guest

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation:

The primary security risk is the 'attack surface' introduced by the modifications. New system calls, hypercall handlers, and shared memory interfaces add complexity to the kernel. A bug in this hypercall handling code could lead to privilege escalation from user to guest kernel, or even allow a malicious guest to compromise the hypervisor via malformed hypercalls. Option B is a general virtualization concern, not specific to PV. Option C is false; PV drivers run in kernel space for performance. Option D is partially true but usually mitigated by hypervisor-level access control; it's a concern but less fundamental than the code complexity issue.

Q14. The graph plots the number of VM exits per second (Y-axis) against the workload intensity (X-axis) for a paravirtualized (PV) system and a hardware-assisted (HVM) system running the same application. The HVM line starts at 1000 exits/sec and scales linearly to 10000 exits/sec. The PV line starts at 100 exits/sec and remains flat. What is the most plausible interpretation of the PV flat line?

🔹 A. The PV guest is using a 'spin-and-exit' strategy, where it spins in user space to avoid exits, causing a flat line but high CPU usage
🔹 B. The PV guest has completely eliminated all exits by performing all privileged operations via hypercalls, and the number of hypercalls is constant regardless of workload
🔹 C. The PV system is I/O bound, and the flat line represents the rate of interrupts, not exits, which is capped by the hypervisor
🔹 D. The PV system is memory-bound, and the flat line shows that page faults are handled entirely within the guest, not requiring hypervisor involvement

💡 Difficulty: hard | ✅ Correct: B

📖 Explanation:

A flat line for VM exits suggests that the number of exits does not increase with workload. This is the ideal behavior of paravirtualization: most operations that would cause exits (e.g., I/O, privilege changes) are instead handled via hypercalls. If the workload is CPU-intensive, the number of hypercalls might be low and constant (e.g., timer updates). Option A describes a 'spin' which would cause exits, not reduce them. Option C is incorrect; I/O would cause hypercalls, but the flat line suggests the hypercalls themselves aren't counted as 'exits' in this graph, or they are constant. Q15. Consider a paravirtualized system where the guest's TCP/IP stack is modified to use a 'zero-copy' mechanism with the hypervisor's networking backend. What is the primary condition that must be met for zero-copy to actually reduce CPU usage?

🔹 A. The hypervisor must use a 'copy-on-write' strategy for the network buffers
🔹 B. The guest must use physically contiguous memory for the network buffers that can be accessed by the hypervisor's DMA engine
🔹 C. The network packet size must be smaller than the CPU's cache line size
🔹 D. The hypervisor must disable checksum offloading to prevent data corruption

💡 Difficulty: hard | ✅ Correct: B

📖 Explanation:

For true zero-copy, the hypervisor needs to be able to access the guest's memory buffers directly to send data to the physical NIC. This requires that the guest's buffer be mapped to a physical address that the hypervisor can pass to the DMA engine of the NIC. If the buffer is fragmented, the hypervisor must copy it. Option A is the opposite of zero-copy. Option C is irrelevant. Option D is false; checksum offloading can be used with zero-copy if implemented correctly.

Q16. A student argues that 'paravirtualization is always faster than full virtualization.' Which of the following scenarios provides a valid counterargument to this blanket statement?

🔹 A. When the paravirtualized guest is running a CPU-intensive task with no I/O, causing zero benefit from hypercalls but adding the overhead of the paravirtualization layer
🔹 B. When the hardware-assisted full virtualization (HVM) system uses a high-performance NIC with SR-IOV, while the paravirtualized system uses a legacy virtual NIC
🔹 C. When the paravirtualized guest has a bug in its hypercall handler that causes it to spin, while the HVM guest runs efficiently
🔹 D. All of the above scenarios provide valid counterarguments

💡 Difficulty: hard | ✅ Correct: D

📖 Explanation:

This is a classic error of overgeneralization. Paravirtualization's main benefit is reducing I/O and privileged instruction overhead. For pure CPU tasks (A), the hypercall overhead may be small but not zero, while HVM can run hardware-native instructions without modification. Scenario B shows that hardware features (SR-IOV) can give HVM a performance edge. Scenario C is a software bug scenario. Therefore, all are valid counterarguments. D is correct.

Q17. In a paravirtualized memory management system, the 'grant table' is used to share memory between domains. If a backend domain (driver domain) maps a page shared by a frontend domain (guest) with read-write permissions, what is a primary security implication?

🔹 A. The backend domain can corrupt the frontend's memory, potentially causing a crash, but cannot affect other domains
🔹 B. The frontend domain can revoke the page at any time, causing a use-after-free in the backend domain
🔹 C. The backend domain can use this mapping to directly access the hypervisor's memory, as the grant table bypasses hypervisor checks
🔹 D. The mapping is secure because the grant table uses a cryptographic hash to authenticate the frontend

💡 Difficulty: hard | ✅ Correct: B

📖 Explanation:

Grant tables operate on a 'share' and 'unshare' model. The frontend grants access to a page, and the backend can map it. However, the frontend holds the grant and can revoke it at any time. If the backend is holding a reference (e.g., a socket buffer) and the frontend revokes it, the backend will access invalid memory, leading to a use-after-free vulnerability. Option A is too narrow; corruption can affect the backend's state, which might impact other domains if the backend is shared. Option C is false; grant tables are hypervisor-mediated. Option D is false; they use identity-based permissions, not cryptography.

Q18. Why is the Time Stamp Counter (TSC) often considered an unreliable time source in a paravirtualized guest, necessitating a paravirtualized clock?

🔹 A. The TSC frequency changes with the physical CPU's power state, and the guest cannot control this
🔹 B. The hypervisor traps every read of the TSC to add a consistent offset, causing high overhead
🔹 C. The TSC is reset to zero on every VM exit, causing non-monotonic time
🔹 D. The guest's virtual TSC is not synchronized across multiple vCPUs, leading to negative time deltas

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation:

The TSC is a physical counter on the CPU. Its frequency can change due to power management (e.g., SpeedStep, C-states). A paravirtualized guest cannot trust the TSC to represent a stable, monotonic wall-clock time because the hypervisor may be migrating the vCPU between cores with different TSC frequencies or adjusting the time. To provide a stable time source, paravirtualized systems use a hypervisor-provided time source (e.g., via shared memory) that accounts for these changes. Option B is true for older systems but not the primary reason for unreliability. Option C is false; TSC is not reset on exit. Option D is a symptom of unsynchronized TSCs, which is part of the problem.

Q19. A developer is writing a paravirtualized driver for a new storage device. The hypervisor provides a ring buffer interface (shared memory) for commands and responses. To maximize performance, how should the driver handle the producer and consumer pointers?

🔹 A. The driver should use hardware atomic instructions to update the pointers to avoid data corruption without hypervisor intervention
🔹 B. The driver should update the pointers in shared memory and then issue a hypercall to 'notify' the hypervisor of new work, or check the 'event' flag for completions
🔹 C. The driver should update the pointers only after acquiring a hypervisor-provided spinlock to prevent multiple vCPUs from racing
🔹 D. The driver should copy all command data to a hypervisor-private buffer before updating the pointers to ensure isolation

💡 Difficulty: medium | ✅ Correct: B

📖 Explanation:

Paravirtualized ring buffers (like Xen's I/O rings) are designed for low overhead. The producer updates its pointer in shared memory. To signal the other side, it uses an event channel (notification). The consumer checks the pointer on interrupts or by polling. The hypervisor is not involved in the pointer update itself, which is the key to performance. Option A is partially true (atomic operations are needed), but the crucial step is the notification. Option C is incorrect because the hypervisor doesn't provide a spinlock for this; the driver uses its own or relies on the ring's semantics. Option D would copy data, defeating the purpose of shared memory.

Q20. In a paravirtualized environment, the hypervisor offers a 'balloon driver' to manage memory. If the host system is under memory pressure, what is the expected behavior of the balloon driver in the guest?

🔹 A. The balloon driver will inflate, allocating memory within the guest and pinning it, thus making it unavailable to the guest and returning physical pages to the host
🔹 B. The balloon driver will deflate, freeing guest memory to the guest's allocator, allowing the guest to use more memory
🔹 C. The balloon driver will trigger a guest kernel panic to protect the host from OOM conditions
🔹 D. The balloon driver will reduce the guest's CPU quota to slow down memory allocation

💡 Difficulty: easy | ✅ Correct: A

📖 Explanation:

The balloon driver is a key memory management feature. When the host needs memory, it 'inflates' the balloon inside the guest. The balloon driver allocates memory from the guest's OS (e.g., via kmalloc), effectively 'pinning' it and making it unavailable to guest applications. The hypervisor then reclaims the underlying machine pages. When memory pressure is low, the balloon 'deflates,' freeing memory back to the guest. Option B describes deflation. Option C is incorrect; it's a cooperative mechanism. Option D is about CPU, not memory.

Q21. A paravirtualized guest's 'idle' time is reported as 0% by the guest's 'top' utility, even though the system is clearly not busy. The hypervisor's metrics show the vCPU is often blocked on I/O. What is the most likely cause of this discrepancy in the paravirtualized context?

🔹 A. The guest's idle loop is using a 'halt' hypercall that blocks the vCPU, but the guest OS does not count this blocked time as 'idle' in its own accounting
🔹 B. The hypervisor is stealing CPU time from the guest to run other VMs, and the guest incorrectly counts this stolen time as user time
🔹 C. The guest's timer interrupts are not firing, causing the idle process to never be scheduled
🔹 D. The paravirtualized scheduler is broken and is always running the kernel 'swapper' process in a tight loop, never actually yielding

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation:

In a paravirtualized guest, the idle process does not actually spin-wait. It makes a hypercall to block. The guest's CPU time accounting is usually based on the amount of time the vCPU is running. When the vCPU is blocked (due to the 'halt' hypercall), the guest's timer interrupt doesn't increment the idle counter, because the vCPU is not executing. The hypervisor sees the vCPU as blocked and schedules someone else. Thus, the guest OS reports 0% idle, while the hypervisor sees the vCPU as not running. This is a known quirk. Option B is 'steal time', which is reported differently. Option C is unlikely. Option D is possible but less common than the accounting quirk.

Q22. What is the primary role of the 'hypercall' in a paravirtualized operating system, and how does it differ from a system call?

🔹 A. A hypercall is a request from the guest kernel to the hypervisor for privileged operations, whereas a system call is a request from user space to the guest kernel
🔹 B. Both are identical in function, but hypercalls are faster because they don't change the privilege level
🔹 C. A hypercall is used for I/O, while a system call is used for memory management
🔹 D. A hypercall is a request from the hypervisor to the guest kernel, whereas a system call is from guest user to guest kernel

💡 Difficulty: easy | ✅ Correct: A

📖 Explanation:

This is the foundational definition. A system call is the interface between user-mode applications and the kernel-mode guest OS. A hypercall is the interface between the guest kernel and the hypervisor, used for operations that require a higher privilege level or for making requests to the hypervisor. Option B is incorrect; hypercalls often change privilege level (from guest kernel to hypervisor). Option C is incorrect; both can be used for various operations. Option D reverses the direction.

Q23. A system administrator is tuning a paravirtualized Linux server. They observe that the 'st' (steal time) value in /proc/stat is often around 20%. What does this indicate about the system's condition and what is the most appropriate action?

🔹 A. The hypervisor is overcommitting CPU resources; the administrator should reduce the number of vCPUs per guest or increase host capacity
🔹 B. The guest is I/O bound, and the hypervisor is stealing time to process I/O; the administrator should increase the I/O ring buffer size
🔹 C. The paravirtualized clock is drifting, and the guest is misinterpreting time; the administrator should enable the 'no-steal' flag in the kernel
🔹 D. The guest is using a spinlock inefficiently, causing the hypervisor to preempt it; the administrator should disable paravirtualized spinlocks

💡 Difficulty: medium | ✅ Correct: A

📖 Explanation:

'Steal time' is the time the hypervisor has to run other VMs while the current vCPU wants to run. High steal time indicates CPU overcommitment or contention on the physical host. The appropriate action is to reduce the contention: reduce the number of vCPUs, move VMs to another host, or upgrade the host CPU. Option B is about I/O, which is not what 'st' measures. Option C is about time drift, not steal time. Option D is about spinlocks, which might cause preemption but not directly measured by 'st' in this context.

Q24. In a paravirtualized system, which of the following is a significant advantage of using a 'split driver' model (frontend/backend) for device virtualization over the emulation model used in full virtualization?

🔹 A. It reduces the number of context switches because the backend driver can run in the hypervisor's context, avoiding VM exits
🔹 B. It allows the guest to directly access the hardware registers, bypassing the hypervisor
🔹 C. It ensures that all devices are standardized, eliminating the need for device-specific drivers in the guest
🔹 D. It enables the guest to use zero-copy networking without any modifications to the guest kernel

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation:

The split driver model (e.g., Xen's netfront/netback) is a paravirtualization technique. The frontend driver in the guest communicates with the backend driver in the hypervisor (or driver domain) via shared memory and event channels. This is faster than emulation (e.g., QEMU emulating an E1000) because emulation requires the hypervisor to decode and execute each I/O instruction, causing a VM exit and context switch. In the split model, the communication is via hypercalls (or shared memory) which are lower overhead. Option B is false; guests don't access hardware directly. Option C is false; they still need drivers. Option D is false; zero-copy requires guest modifications.
