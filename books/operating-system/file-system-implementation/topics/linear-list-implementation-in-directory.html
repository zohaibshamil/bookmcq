What is Linear list Implementation in Directory?

Definition:
Linear list directory implementation stores entries as an unsorted array of ⟨name,inode⟩ \langle name, inode \rangle ⟨name,inode⟩ pairs requiring sequential search for lookups.

Example:

Q1. What term does a UNIX system use for the per‑process entry that references an open file?

A.file descriptor ✅
B.file handle
C.inode
D.directory entry
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: The correct answer is \file descriptor\ because UNIX assigns a small integer called a file descriptor to each open file in a process's table. \File handle\ is the Windows terminology, while an inode stores metadata on disk and a directory entry contains name information. Understanding the naming convention helps students recognize platform‑specific APIs and why code using descriptors works across UNIX environments.

Q2. Which component typically stores inode information for open files in a system‑wide structure?

A.superblock
B.open‑file table ✅
C.inode cache
D.block bitmap
💡 Difficulty: easy | ✅ Correct: B

📖 Explanation: The open‑file table holds the inodes and related data for files that are currently open. The superblock describes the overall file system, the inode cache may hold recently used inodes but is not the primary table, and the block bitmap tracks free blocks. Knowing the role of the open‑file table clarifies how the OS quickly accesses metadata without consulting disk each time.

Q3. Why does the operating system decrement the open‑count when a process closes a file?

A.To free the file’s disk blocks immediately
B.To track how many active references exist ✅
C.To delete the file from the directory
D.To reset the file’s permission bits
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: Decrementing the open‑count records how many processes still have the file open. When the count reaches zero, the system knows it can release cached metadata and write back any pending changes. It does not delete the file or alter permissions; those actions occur only on explicit system calls. Recognizing this reference‑counting mechanism explains resource cleanup in multi‑process environments.

Q4. How does caching file metadata improve performance in BSD UNIX systems?

A.It eliminates the need for any disk I/O
B.It reduces the number of disk reads by reusing recently accessed information
C.It speeds up network connections only ✅
D.It allows the OS to bypass permission checks
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: Caching metadata means the OS can answer queries about a file (size, timestamps, location) from memory instead of reading the inode from disk each time. This reduction in disk I/O accounts for the high cache‑hit rate (≈85 %). The cache does not eliminate all I/O nor affect network speed directly, and permission checks still occur. The benefit is faster file‑system operations for applications.

Q5. A program opens a file, reads data, then crashes without explicitly closing the file. What happens to the system‑wide open‑file entry?

A.It remains forever, causing a leak
B.The OS automatically decrements the open count when the process terminates ✅
C.The entry is immediately removed at the crash point
D.The file becomes read‑only until manually closed
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: When a process ends abruptly, the operating system reclaims its resources, including any open file descriptors. It decrements the open count and, if that count becomes zero, flushes metadata and removes the entry. The entry does not persist indefinitely, and the file’s mode does not change because of the crash. This automatic cleanup prevents resource leaks in a multitasking environment.

Q6. Two processes open the same file. Process 1 writes and closes it, while Process 2 remains open. When is the file’s metadata flushed to disk?

A.Immediately after Process 1 writes
B.Only after Process 2 also closes the file
C.When the system‑wide open count reaches zero ✅
D.Never, because caching prevents flushing
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: Metadata is written back only when the last reference to the file is closed, i.e., when the system‑wide open count becomes zero. Process 1’s close reduces the count but does not trigger a flush because Process 2 still holds the file open. This ensures that any further changes by remaining processes are not lost. Immediate flushing after a write would be inefficient, and caching does not block flushing entirely.

Q7. A network socket is opened using the same open‑file table as regular files. After the socket is closed, which effect occurs on the table?

A.The socket entry remains but is marked inactive
B.The entry is removed and the open count is decremented
C.The socket is converted into a regular file entry
D.The table size doubles to accommodate network entries ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: The unified open‑file table treats sockets like files; closing the socket causes the OS to decrement the open count and, when zero, remove the entry entirely. The entry is not retained as inactive, nor is it transformed into a file record. The table does not grow because of a single socket; it simply reclaims the slot. Understanding this uniform handling clarifies how the OS abstracts diverse resources.

Q8. Why is the file name not required in the per‑process open‑file table after locating the FCB on disk?

A.Because the name is stored in the inode
B.Because the FCB uniquely identifies the file for all operations
C.Because the name is irrelevant to the OS ✅
D.Because the name is cached elsewhere permanently
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: Once the file control block (FCB) is located, it contains all necessary identifiers (inode number, device, etc.) to perform reads, writes, and seeks. The name is only needed for name resolution during the open call; after that, operations use the FCB reference. Storing the name would be redundant and waste memory. This design streamlines per‑process tables and speeds subsequent file operations.

Q9. A system reports an 85 % cache‑hit rate. If 1,000 file accesses occur, how many disk reads are expected?

A.150 ✅
B.850
C.1000
D.0
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: With an 85 % hit rate, 15 % of accesses miss the cache. Expected disk reads = 1,000 × 0.15 = 150. Option A reflects this calculation. Options B and C ignore the miss proportion, and option D assumes perfect caching. Translating hit‑rate percentages into concrete I/O counts helps students assess performance impact in real workloads.

Q10. What is the primary advantage of using a single mechanism (open‑file table) for files, directories, devices, and network connections?

A.It reduces code size only
B.It provides a uniform interface for resource management ✅
C.It eliminates the need for permissions
D.It speeds up CPU clock cycles
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: A unified table lets the OS manage diverse resources with the same data structures and reference‑counting logic, simplifying implementation and reducing bugs. While code size may shrink and permissions still apply, the key benefit is the consistent interface that allows processes to treat sockets, files, and devices similarly. This uniformity is fundamental to modern operating‑system design.

Q11. A developer notices frequent open/close cycles for the same file and wants to reduce overhead. Which caching strategy is most effective?

A.Cache the file descriptor ✅
B.Cache the file’s data blocks
C.Cache the directory entry
D.Cache the process table
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: Caching the file descriptor (i.e., reusing the same open‑file entry) avoids repeated look‑ups and reference‑count updates, cutting the cost of opening the file repeatedly. Caching data blocks helps read performance but does not eliminate the open/close overhead. Directory entries and process tables are unrelated to this specific inefficiency. Selecting the descriptor cache directly addresses the observed overhead.
