📝 Direct file access Method in Operating System

📖 From Operating System • 11. File System Interface • 13 questions available

What is Direct file access Method in Operating System?

Definition:
Direct (or random) access allows immediate reading or writing of any record at logical position \( n \) without traversing previous records, typically calculated via \( offset = base + n \times record\_size \).

Example:
Database management systems use direct access on SSDs or HDDs to jump instantly to a specific B-tree node using its block number, bypassing irrelevant intermediate data.

Reason:
Modern interactive applications and databases require sub-millisecond response times for arbitrary data lookups, which sequential methods cannot provide due to cumulative seek delays.

Q1. A Java program must obtain an exclusive lock on the first half of a file named file.txt whose size is 2000 bytes. Which call to FileChannel.lock correctly acquires this lock?

A. ch.lock(0, 1000, false) ✅
B. ch.lock(0, 2000, false)
C. ch.lock(0, 1000, true)
D. ch.lock(1000, 1000, false)

💡 Difficulty: easy | ✅ Correct: A

📖 Explanation:

The first half of a 2000‑byte file spans bytes 0 through 999, which is a length of 1000 bytes. The lock method takes a start position, a length, and a boolean indicating shared (true) or exclusive (false). Option A matches these parameters, giving an exclusive lock on the correct range. Option B locks the entire file, option C requests a shared lock, and option D starts at the middle, leaving the first half unlocked. Using the correct call ensures only one process can modify that portion at a time, preserving data integrity.

Q2. Two threads need to coordinate file access: Thread 1 must obtain an exclusive lock on the first half of a file, while Thread 2 needs a shared lock on the second half. Which ordering of lock acquisition avoids a deadlock?

A. Thread 1 locks first half exclusively, then Thread 2 locks second half shared
B. Thread 2 locks second half shared, then Thread 1 locks first half exclusively
C. Both threads try to lock their portions at the same time
D. Thread 1 locks first half exclusively, releases it, then Thread 2 locks second half shared ✅

💡 Difficulty: medium | ✅ Correct: D

📖 Explanation:

If Thread 1 holds an exclusive lock on the first half and does not release it, Thread 2 can still obtain its shared lock because the regions do not overlap. However, a deadlock can arise only if each thread waits for the other’s lock. By releasing the exclusive lock before Thread 2 attempts its shared lock, the sequence guarantees that no thread is waiting on a lock held by the other, thus preventing deadlock while still protecting the first half during its use.

Q3. An operating system uses advisory locking. Process A acquires an exclusive lock on a log file. Process B later writes to the same file without explicitly acquiring any lock. What is the most likely outcome?

A. Process B’s write succeeds because advisory locks are ignored unless Process B also checks for locks ✅
B. Process B is blocked until Process A releases its lock
C. Process B throws an IOException immediately
D. Process B’s write corrupts the file but the OS allows it

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation:

Advisory locks rely on cooperation; the OS does not enforce them automatically. Therefore, a process that does not request or check the lock can still access the file, and its write will succeed. Option A reflects this behavior. Option B describes mandatory locking, which would block the write. Option C is not typical for advisory locks, and option D suggests silent corruption, which is not guaranteed. Understanding this distinction helps developers decide when to use advisory locks and when additional coordination is required.

Q4. What best describes the distinction between mandatory and advisory file locking mechanisms?

A. Mandatory locks are enforced by the operating system regardless of a process’s intent, while advisory locks require cooperating processes to honor them
B. Mandatory locks are optional and rely on application logic, whereas advisory locks are automatically applied by the OS ✅
C. Both mechanisms are enforced by the OS, but mandatory locks allow shared access while advisory locks do not
D. Advisory locks are a legacy feature and are no longer supported in modern operating systems

💡 Difficulty: easy | ✅ Correct: B

📖 Explanation:

Mandatory locking means the OS prevents any other process from accessing the locked region, even if that process never requests a lock. Advisory locking, by contrast, does nothing unless a process explicitly checks for existing locks and chooses to respect them. Option B captures this essential difference. Options A and C invert the roles, and option D incorrectly claims advisory locks are obsolete. Knowing this helps programmers choose the appropriate strategy for synchronizing file access.

Q5. Why does FileChannel.lock require a boolean parameter named shared?

A. It indicates whether the lock should be shared (true) or exclusive (false) for the specified region
B. It determines if the lock will be persistent across JVM restarts
C. It specifies whether the lock should be recursive for nested calls ✅
D. It sets the priority of the lock acquisition operation

💡 Difficulty: medium | ✅ Correct: C

📖 Explanation:

The boolean argument tells the underlying file system what type of lock to create: false creates an exclusive lock that blocks all other access, while true creates a shared lock that permits multiple readers but blocks writers. This distinction is essential for coordinating concurrent file operations. Options A, B, and D describe unrelated behaviors that the API does not provide. Recognizing the purpose of the shared flag enables developers to correctly manage read‑write concurrency.

Q6. If a program locks the first half of a file exclusively and the second half shared, how does this affect concurrent access by other processes?

A. Other processes can read the second half simultaneously but cannot read or write the first half while the exclusive lock is held ✅
B. All other processes are blocked from any access to the file until both locks are released
C. Both halves become read‑only for all other processes
D. The locks have no effect because they apply only to the owning process

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation:

An exclusive lock prevents any other process from reading or writing the locked region, so the first half is fully protected. A shared lock allows multiple processes to read the second half concurrently but still blocks writes. Therefore, option A correctly describes the mixed‑mode behavior. Option B would be true only if both halves were locked exclusively. Option C misstates the effect of a shared lock, and option D ignores the operating‑system enforcement of locks. This scenario illustrates how mixed locking can increase throughput while safeguarding critical sections.

Q9. Which programming pattern guarantees that both a FileChannel and its FileLock are released even if an IOException occurs during processing?

A. Nested try‑finally blocks that manually call release() in each finally clause
B. A single try block with no finally clause, relying on garbage collection
C. Try‑with‑resources that declare the channel and lock as resources ✅
D. Ignoring the release calls and allowing the program to exit

💡 Difficulty: hard | ✅ Correct: C

📖 Explanation:

The try‑with‑resources statement automatically invokes the close() method on any AutoCloseable resource, which includes FileChannel and FileLock, ensuring they are released regardless of exceptions. Option C therefore provides the safest guarantee. Option A can work but is more error‑prone and verbose. Options B and D leave resources unreleased, risking file‑lock leaks. Using this pattern is essential for robust file‑handling code.

Q10. What is the primary effect on data consistency when a thread releases its exclusive lock on the first half of a file before acquiring a shared lock on the second half?

A. It ensures that no other thread can modify the first half while the thread reads the second half
B. It allows other threads to modify the first half, potentially causing inconsistent reads of the second half
C. It guarantees that both halves are read atomically by the same thread
D. It has no impact because exclusive and shared locks are independent ✅

💡 Difficulty: medium | ✅ Correct: D

📖 Explanation:

Releasing the exclusive lock removes protection from the first half, so other threads may write to that region while the original thread holds a shared lock on the second half. This does not affect the data being read from the second half, but it does open the possibility of inconsistency if the two halves are logically related. Option D captures that the lock types act on separate regions and do not automatically provide atomicity across the whole file. Options A, B, and C misinterpret the relationship between the two locks.

Q11. If a program attempts to lock a region that starts at byte 1500 with a length of 600 on a file that is only 2000 bytes long, what exception is most likely thrown?

A. IOException ✅
B. OverlappingFileLockException
C. IllegalArgumentException
D. IndexOutOfBoundsException

💡 Difficulty: medium | ✅ Correct: A

📖 Explanation:

The lock method checks that the requested region does not extend beyond the file size. When the end position (1500 + 600 = 2100) exceeds the actual file length (2000), the method throws an IOException indicating an I/O error related to the invalid range. Option A reflects this behavior. OverlappingFileLockException occurs when a lock conflicts with an existing lock in the same JVM, IllegalArgumentException is used for negative arguments, and IndexOutOfBoundsException is not typical for file‑channel operations. Knowing the correct exception helps developers diagnose range errors.

Q12. Why can mandatory file locks lead to deadlock situations if not carefully managed, whereas advisory locks rely on process cooperation to avoid such problems?

A. Mandatory locks are enforced by the OS, so a process that holds a lock may block another process that also needs the lock, creating a circular wait; advisory locks only block when both processes agree to respect them
B. Mandatory locks automatically resolve deadlocks by releasing locks after a timeout, while advisory locks never cause deadlocks
C. Advisory locks are implemented in user space and therefore cannot cause deadlocks, unlike mandatory locks which are kernel‑level
D. Both types of locks behave identically with respect to deadlocks, so the statement is false ✅

💡 Difficulty: hard | ✅ Correct: D

📖 Explanation:

Mandatory locks are strict: once a process obtains an exclusive lock, the OS prevents any other process from accessing the locked region, even if that process does not intend to coordinate, which can create circular wait conditions. Advisory locks, by contrast, only affect processes that explicitly check for and honor the lock, reducing the chance of inadvertent blocking. Option D correctly states that the mechanisms differ in how they handle deadlock risk. Options A, B, and C contain inaccuracies about timeout handling and the nature of advisory locks.

Q13. Which finally block correctly releases both a FileLock named exclusiveLock and another named sharedLock, assuming they may be null?

A. if (exclusiveLock != null) exclusiveLock.release(); if (sharedLock != null) sharedLock.release();
B. if (exclusiveLock == null) exclusiveLock.release(); if (sharedLock == null) sharedLock.release();
C. if (exclusiveLock != null) exclusiveLock.release(); if (sharedLock != null) sharedLock.release(); ✅
D. exclusiveLock.release(); sharedLock.release();

💡 Difficulty: medium | ✅ Correct: C

📖 Explanation:

The safest pattern checks each reference for null before invoking release(), preventing a NullPointerException if a lock was never acquired. Option C implements this correctly. Option A omits the null check for the second lock, risking an exception. Option B reverses the condition, releasing only when the lock is null, which is incorrect. Option D blindly calls release() on both variables, also risking a NullPointerException. Properly handling null references ensures that resources are cleaned up without crashing the program.
