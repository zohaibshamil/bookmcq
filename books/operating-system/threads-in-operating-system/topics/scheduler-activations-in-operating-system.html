What is Scheduler activations in operating system?

Definition:
Scheduler activations provide communication mechanism between user-level thread library and kernel scheduler, enabling efficient many-to-many thread mapping. When kernel thread blocks or becomes available, it notifies user library through upcalls, allowing library to reschedule user threads onto available kernel threads dynamically, combining user-space scheduling flexibility with kernel-level resource management.

Working:
Kernel maintains activation records tracking kernel thread states. When event occurs (I/O completion, preemption), kernel sends upcall to user library passing activation record. Library examines ready user threads, assigns them to available activations, and resumes execution. This bidirectional communication enables library to make informed scheduling decisions based on actual kernel thread availability.

Example:
User library has \( 100 \) user threads mapped to \( 8 \) kernel activations. When kernel thread blocks on I/O, upcall notifies library. Library selects another ready user thread, assigns it to freed activation, continuing execution without wasting CPU. Solution: Efficient utilization maintaining \( 8 \) active threads despite blocking operations.

Reason:
Scheduler activations solve many-to-many mapping challenge by providing kernel visibility into user-level scheduling decisions, enabling library to optimize thread placement based on application knowledge, reducing unnecessary context switches, and allowing custom scheduling policies while leveraging kernel resource management capabilities.

Common Misconceptions:
Students think scheduler activations are widely used today, but most modern systems prefer simpler One-to-One models. Another misconception is that upcalls are regular function calls, when they're special kernel-to-user transitions requiring careful implementation. Some believe activations eliminate all scheduling overhead, ignoring upcall communication costs.

Exam Preparation Tips: How to prepare this topic
Understand upcall mechanism, study activation record structure, compare with other multithreading models, analyze performance trade-offs, and learn why scheduler activations declined in popularity despite theoretical advantages for many-to-many threading.

Key Terms:

  • Upcall - kernel notification to user library.
  • Activation - kernel thread representation in user space.
  • Many-to-Many - mapping multiple user threads to kernel threads.
  • Rescheduling - assigning user threads to available activations.

📝 All Scheduler activations in operating system MCQs

Q1. A user-level thread is blocked on a synchronous I/O operation. Under pure scheduler activations, what is the FIRST action the kernel takes to maintain processor utilization while preserving the thread's state?

A.It immediately creates a new kernel thread to replace the blocked one
B.It preempts the entire process and schedules another process
C.It notifies the process's scheduler activation handler with an 'upcall' about the blockage ✅
D.It saves the thread's registers to disk and switches to the next user thread
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: In scheduler activations, the kernel does not directly manage user-level threads. Its primary mechanism for communication is the upcall. When a thread blocks on I/O, the kernel's first action is to invoke the process's upcall handler (which is part of the user-level scheduler) via an upcall. This informs the user-level scheduler that a processor is now free because the thread is blocked. The user-level scheduler can then make a decision to run another ready thread on that processor. Options A and D are actions the user-level scheduler might take after the upcall, but the kernel's first action is the notification. Option B is incorrect because the process is not entirely preempted; it just loses one processor.

Q2. Consider a multi-threaded process using scheduler activations on a multiprocessor system with 4 processors. The kernel has allocated 4 activations to the process. If 3 threads are blocked on I/O and 1 thread is running CPU-bound, what is the ideal number of activations the kernel should maintain for this process to prevent processor waste?

A.1 ✅
B.2
C.3
D.4
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: The core principle of scheduler activations is to match the number of activations to the number of processors actually being used by the process. If 3 threads are blocked, they are not consuming CPU time. The running CPU-bound thread only needs one processor. The kernel should 'take back' the 3 unused activations and can reallocate them to other processes in the system. Maintaining 4 activations (Option D) would waste 3 processors as the process cannot use them. The process should only have the number of activations equal to its current parallel workload, which is 1.

Q3. Which of the following scenarios represents a fundamental weakness of the scheduler activations model that is NOT present in a pure 1:1 kernel-thread model?

A.Increased latency in handling thread blocking and unblocking
B.Complexity in implementing the upcall mechanism and stack management ✅
C.Inefficient handling of page faults due to lack of kernel knowledge
D.Poor performance on NUMA architectures
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Scheduler activations are designed to improve performance over both pure user-level and kernel-level threads. However, they introduce significant implementation complexity. A key weakness is the difficulty of managing the upcall stack. When an upcall occurs, the user-level scheduler must execute. The kernel must ensure the upcall has a safe stack to execute on, which is complex because the process may be in the middle of executing a user thread. Option A is incorrect because scheduler activations aim to reduce latency. Option C is incorrect as the kernel is aware of page faults and can handle them via upcalls. Option D is a more general memory management issue, not a specific weakness of the model.

Q4. A user-level scheduler using activations receives an upcall that a thread has become unblocked. The scheduler determines that all current processors are occupied by other threads. What should be the scheduler's MOST appropriate action to ensure the newly unblocked thread is eventually executed without violating the model's principles?

A.Immediately preempt the currently executing thread on a processor to run the unblocked thread
B.Queue the unblocked thread and wait for a future upcall indicating a processor is free ✅
C.Preempt the thread with the lowest priority and dispatch the unblocked thread
D.Request the kernel to create a new activation for the unblocked thread
💡 Difficulty: easy | ✅ Correct: B

📖 Explanation: The principle of scheduler activations is that the kernel provides activations representing processors. The user-level scheduler manages threads within these activations. If no activation (processor) is available, the user-level scheduler cannot run the thread immediately. It must queue it. The kernel will later issue an upcall when a processor becomes available (e.g., another thread blocks). The scheduler then has the responsibility to choose a thread to run on that newly free activation. This prevents thrashing. Option B is correct. Options A and C are incorrect because preempting a thread on a processor is the scheduler's prerogative, but it doesn't happen without an upcall from the kernel stating a processor is free. Option D is incorrect because the kernel does not grant activations on a per-thread basis; it manages them based on processor availability.

Q5. An operating system uses scheduler activations. The user-level scheduler is poorly implemented and does not handle upcalls quickly. What is the MOST direct macroscopic system-level consequence of this lag?

A.The overall throughput of the system will decrease due to increased I/O wait times ✅
B.The process will experience a catastrophic system crash
C.The kernel will automatically revert to a 1:1 threading model
D.The process will deadlock
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: Scheduler activations rely heavily on a responsive user-level scheduler. The kernel uses upcalls to delegate scheduling decisions. If the user-level scheduler is slow to process an upcall (e.g., a notification that a thread has blocked), the kernel will not get a prompt response on which new thread to run on the now-free processor. This delay in scheduling a new thread leads to processor idleness, which directly translates to lower CPU utilization and reduced system throughput. Option B is too extreme; a slow scheduler is an inefficiency, not a crash. Option C is not a feature; the kernel cannot unilaterally change the threading model. Option D is a specific situation, not a general system-level consequence.

Q6. In the context of scheduler activations, what is the primary difference between an 'upcall' and a traditional 'signal' in Unix?

A.Upcalls are always synchronous, while signals are asynchronous.
B.Upcalls are used for communication from user-space to kernel-space; signals are for kernel-space to user-space.
C.Upcalls are a mechanism for the kernel to request scheduling actions from the user-level scheduler; signals are for asynchronous event notification to a process. ✅
D.Upcalls can carry complex data structures, while signals can only carry an integer.
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: While similar in being asynchronous notifications, their purpose is different. A signal is a general-purpose mechanism to notify a process of an event. An upcall is a specific mechanism for scheduler activations where the kernel notifies the user-level scheduler of a scheduling event (e.g., a thread blocked, a new processor available) and asks it to perform a scheduling action. The key is the intent: an upcall is a request for scheduling action, not just a general notification. Option A is false; upcalls are typically asynchronous. Option B is reversed; upcalls are kernel-to-user. Option D is a minor implementation detail, not the primary purpose.

Q7. A process has 2 running threads and uses scheduler activations on a dual-core system. If one thread performs an I/O operation, the kernel will typically:

A.Block the entire process, suspending both threads.
B.Create a new kernel thread to handle the I/O.
C.Issue an upcall to the user-level scheduler and then grant the processor to another process. ✅
D.Immediately preempt the I/O thread and schedule another thread from a different process.
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: When a user thread blocks on I/O, the kernel is aware of this. Under scheduler activations, the kernel's responsibility is to manage processors, not the user threads directly. It will issue an upcall to the user-level scheduler, informing it that the activation/processor used by the blocked thread is now free. The kernel will then schedule some other work (either from another process or, as per the upcall response, a new thread from this process) on that processor. Option A is the behavior of a pure user-level threads model, not scheduler activations. Option B is 1:1 threading. Option D is incorrect because the kernel usually gives the user-level scheduler a chance to choose the next thread before scheduling another process.

Q8. Consider a system with scheduler activations. The kernel receives an interrupt for a completed I/O operation for a blocked thread. The kernel's next action is to:

A.Directly mark the thread as runnable.
B.Signal the process using a traditional signal like SIGIO.
C.Issue an upcall to the user-level scheduler to inform it of the unblocked thread. ✅
D.Create a new kernel thread to resume the I/O operation.
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: The kernel knows the thread is blocked at the user level, but it doesn't manage the user-level thread's state directly in its scheduler. Upon I/O completion, the kernel's responsibility is to notify the user-level scheduler via an upcall that the thread is now ready to run. This allows the user-level scheduler to decide when and on which activation to run this newly unblocked thread. Option A is how a kernel-level thread would be managed. Option B is an older, less efficient mechanism. Option D is incorrect as the I/O operation is already complete.

Q9. What is the key performance advantage of scheduler activations over a pure 1:1 kernel-thread model, especially in a system with frequent thread creation and destruction?

A.Lower CPU usage for scheduling interrupts.
B.Reduced overhead for thread creation by avoiding system calls for each new user thread. ✅
C.Better cache behavior due to thread affinity.
D.Faster I/O handling due to direct kernel support.
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: In a 1:1 model, each user thread corresponds to a kernel thread, so every creation/destruction requires a system call. Scheduler activations use an M:N model (or a variant), where the user-level scheduler can create, destroy, and manage threads entirely in user space without kernel intervention for each operation. It only interacts with the kernel when scheduling resources (processors/activations) are involved. This reduces system call overhead significantly for thread management. Option A is less significant. Option C is not a defining advantage. Option D is incorrect as I/O handling is more complex in M:N models.

Q10. A student argues: 'Because scheduler activations use upcalls, the kernel has no control over a process's CPU usage.' Which of the following BEST evaluates this statement's correctness?

A.The statement is correct, as upcalls delegate all scheduling control to the user.
B.The statement is correct, but this is the intended design for user-level control.
C.The statement is incorrect, as the kernel still manages the allocation of activations, granting it ultimate control. ✅
D.The statement is incorrect, as upcalls are a form of strict kernel control over user threads.
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: The student's statement contains a fundamental misconception. While the kernel delegates the *intra-process* scheduling decisions to the user-level scheduler via upcalls, it retains ultimate control over the *inter-process* resource allocation. The kernel decides how many activations (processors) to allocate to each process and can preempt or adjust this allocation at any time. Therefore, the kernel maintains complete control over a process's CPU usage. Option A is false. Option B is false because it's not the intended design for the kernel to lose control. Option D is incorrect because upcalls are not a mechanism for strict control, but for cooperation.

Q11. For a system using scheduler activations, the total number of activations across all processes in the system will always be:

A.Equal to the number of user-level threads.
B.Equal to the number of processors in the system.
C.Greater than or equal to the number of processors.
D.Less than or equal to the number of processors. ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: The kernel treats activations as 'virtual processors' or 'tokens' to execute on a physical CPU. The kernel's scheduler is responsible for managing these tokens across all processes. Since there are only a finite number of physical CPUs, the sum of all activations (tokens) allocated to all processes must be less than or equal to the number of processors. This prevents oversubscription of the physical CPUs and is a key principle. Option B is close but not absolute; the kernel could have fewer activations if a process is idle. Option C is incorrect. Option A is the definition of a 1:1 model.

Q12. In the scheduler activations model, if a user-level thread is blocked because it is waiting to acquire a mutex that is held by another thread within the same process, what does the kernel do?

A.It issues an upcall because the thread is blocked.
B.It does nothing, as this is a user-level blocking event. ✅
C.It escalates the mutex to a kernel-level lock to prevent deadlock.
D.It forces the mutex holder to yield its processor.
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: The kernel is only aware of events that cause the thread to enter the kernel, such as I/O or page faults. A user-level mutex lock is entirely managed within user space. When a thread blocks on such a mutex, the user-level scheduler is aware of it, but the kernel is not. The kernel continues to see the thread as 'runnable' and will not issue an upcall. This is a key difference between a blocking system call and a blocking user-level synchronization primitive. The user-level scheduler must manage this efficiently, often by scheduling another ready thread on the activation.

Q13. An application using scheduler activations is running on a multi-core system. The kernel preempts a process's activation to service a higher-priority process. What mechanism does the kernel use to inform the user-level scheduler that the activation has been taken away?

A.It sends a SIGSTOP signal to the process.
B.It revokes the activation without notification for efficiency.
C.It issues an 'involuntary preemption' upcall. ✅
D.It blocks the process entirely.
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: When the kernel preempts a process, it is not just taking away CPU time; it is taking away an activation (a virtual processor). The kernel must inform the user-level scheduler of this so the scheduler can update its internal state. It does this via a specific type of upcall, often called an 'involuntary preemption' upcall. This allows the user-level scheduler to save the state of the currently running user thread and mark the activation as unavailable. Option A is too heavy-handed. Option B would lead to corruption of the user-level scheduler's state. Option D would violate the principle of scheduler activations, which aims to keep the process running on available processors.

Q14. Compare the overhead of a context switch for two user-level threads within the same process under a 1:1 kernel-thread model versus the scheduler activations model.

A.1:1 model has lower overhead because it uses hardware contexts.
B.Scheduler activations model has lower overhead because it avoids a system call for the context switch. ✅
C.Overhead is identical because both require a context switch of registers.
D.Scheduler activations model has higher overhead because of upcall processing.
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: In a 1:1 model, a context switch between two user-level threads (which are kernel threads) requires a system call into the kernel to save and restore thread contexts. In scheduler activations, a context switch between two user-level threads within the same process is performed entirely in user space. The user-level scheduler saves the state of the current thread and restores the state of the next thread on the same activation. This avoids the overhead of a system call and kernel entry/exit, making it significantly faster. Option A is false. Option C is false. Option D is incorrect because an upcall is only needed when an activation is granted or taken away, not for every thread context switch.

Q15. A process using scheduler activations has 4 threads (T1, T2, T3, T4) and 2 activations. T1 and T2 are CPU-bound. T3 is blocked on I/O, and T4 is blocked on a user-level mutex. The user-level scheduler is running T1 and T2 on the two activations. What is the correct count of idle/available activations from the kernel's perspective?

A.0 ✅
B.1
C.2
D.3
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: The kernel is only aware of kernel-level blockages (like I/O). The user-level mutex block is invisible to the kernel. The I/O blocked thread (T3) has caused its activation to be blocked in the kernel. The user-level scheduler would have received an upcall for T3's I/O and would have informed the kernel that it is no longer using that activation. The kernel then takes that activation back. However, in this scenario, the scheduler is using both activations to run T1 and T2. The kernel sees both activations as busy. The fact that T4 is blocked is a user-level concern and doesn't free a kernel activation. Therefore, from the kernel's perspective, there are 0 idle activations.

Q16. Given the same state as the previous question (Process: 4 threads, 2 activations, T1/T2 running, T3 I/O blocked, T4 mutex blocked), the I/O for T3 completes. The kernel sends an upcall. How many activations will the kernel now expect this process to use immediately after the upcall?

A.0
B.1
C.2 ✅
D.3
💡 Difficulty: easy | ✅ Correct: C

📖 Explanation: When T3's I/O completes, the kernel sends an upcall to the user-level scheduler, effectively returning an activation to the process. The user-level scheduler now has its 2 activations back (the two it was originally allocated). The kernel expects the process to use these 2 activations to run its runnable threads. The user-level scheduler now has three runnable threads: T1, T2, and T3. It can run T1 and T2. It will queue T3. The kernel is not aware of T4's status and allocates activations based on the process's need, which is 2. Therefore, the kernel expects the process to use 2 activations.

Q17. What is the primary purpose of a 'preemption upcall' in scheduler activations?

A.To allow the kernel to completely terminate a process.
B.To inform the user-level scheduler that its activation has been revoked or is being taken away. ✅
C.To request the user-level scheduler to perform a CPU-intensive calculation.
D.To notify the user-level scheduler that a new hardware device is available.
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: A preemption upcall is the kernel's way of telling the user-level scheduler that it is taking back an activation. This is an involuntary preemption. The user-level scheduler must respond by saving the state of the thread currently running on that activation. The upcall gives the scheduler a chance to cleanly handle the preemption, ensuring no state is lost. Option A is incorrect; termination is not the purpose. Option C is incorrect; the kernel doesn't request such actions. Option D is irrelevant to the core scheduling model.

Q18. In the context of scheduler activations, what is the role of the 'idle thread'?

A.To perform background system maintenance tasks.
B.To be scheduled on an activation when a process has no runnable user-level threads, allowing the activation to be returned to the kernel. ✅
C.To handle page faults for other threads.
D.To act as a placeholder for the next upcall.
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: If a process has an activation (a processor) but no runnable user-level threads (e.g., all are blocked on I/O), it must return the activation to the kernel so the kernel can allocate it to another process. However, the process cannot simply 'give back' the activation; it must have a thread to run on it to maintain the model. The 'idle thread' is a special, low-priority, runnable thread that is scheduled when nothing else is ready. Its purpose is to be the thread that is running when the process yields the processor back to the kernel, effectively signaling that the activation is free. The kernel then preempts this idle thread and reallocates the activation.

Q19. A system with scheduler activations is running a highly parallel scientific application. The application performs many short, non-blocking operations. The user-level scheduler implements a simple round-robin policy. What potential performance bottleneck is MOST likely to occur?

A.High overhead from frequent upcalls. ✅
B.High overhead from frequent system calls for thread creation.
C.Poor cache utilization due to frequent thread migration.
D.Processor starvation due to kernel preemption.
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: Short, non-blocking operations often mean the threads are preempted by the kernel's time-sharing mechanism. Each time a thread's time quantum expires, the kernel will issue a preemption upcall to the user-level scheduler. If the quantum is very short, these upcalls can become very frequent. The overhead of handling these upcalls (saving state, making scheduling decisions, etc.) can become a significant performance bottleneck, potentially negating the benefits of user-level scheduling. Option B is less likely because threads are created once. Option C is possible but less likely than upcall overhead. Option D is incorrect as the process will still get CPU time.

Q20. Consider two scheduling models: (A) Pure user-level threads with an L:1 model and (B) Scheduler activations (M:N). A student claims, 'Both models suffer from the same problem of a thread blocking on a page fault causing all other threads in the process to block.' Is this claim correct?

A.Yes, because a page fault blocks the entire process.
B.No, because a page fault causes an upcall, allowing the user-level scheduler to run another thread on a different activation. ✅
C.No, because page faults are handled by the user-level scheduler directly.
D.Yes, because the kernel cannot distinguish page faults from other user-level operations.
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: The student's claim is incorrect. This is a fundamental advantage of scheduler activations over a pure L:1 model. In an L:1 model, a page fault traps to the kernel, which blocks the entire process, preventing all other user-level threads from running. In scheduler activations, the kernel handles the page fault and, if the thread must block, it issues an upcall to the user-level scheduler. This upcall informs the scheduler that the activation is now free, allowing it to schedule another runnable thread on that activation. The process continues to make progress. Option A is the behavior of an L:1 model. Option C is false; the kernel handles the page fault. Option D is false because the kernel is aware of the page fault.

Q21. A system using scheduler activations has 2 physical cores. The kernel has allocated 1 activation to Process A and 1 activation to Process B. Process A has 10 runnable user-level threads, and Process B has 1 runnable user-level thread. What will be the approximate CPU time distribution between the two processes?

A.Process A gets 100% CPU time because it has more threads.
B.Process B gets 100% CPU time because it is perfectly matched to its activation.
C.Both processes get approximately 50% of the CPU time. ✅
D.Process A gets 90% and Process B gets 10% of the CPU time.
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: The allocation of activations determines CPU time at a high level. The kernel scheduler is responsible for dividing the physical CPUs among the competing processes. Since each process has one activation, and there are two CPUs, each process will be scheduled on its own CPU. The kernel will give each activation roughly equal time (preempting them based on time quanta). Inside each process, the user-level scheduler determines how to distribute its allocated CPU time among its threads. The number of threads within a process does not change its allocation of activations (or processors) from the kernel's perspective. Therefore, both processes get equal CPU time.

Q22. In scheduler activations, the kernel's scheduler maintains a list of 'free' activations. These are activations that have been returned by a process (e.g., by running an idle thread). The kernel's primary use for this list is to:

A.Immediately assign them to the same process to avoid thrashing.
B.Use them to respond to future I/O completion upcalls.
C.Allocate them to processes that require more parallelism. ✅
D.Destroy them to save memory.
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: The kernel manages a pool of activations. When a process returns an activation (because all its threads are blocked), the kernel adds it to the 'free' list. The primary purpose of this list is to allow the kernel to dynamically reallocate processors based on demand. When a process's workload increases (e.g., an I/O completes and a thread becomes runnable), the kernel can take an activation from the free list and allocate it to that process, increasing its parallelism. This dynamic management is a key feature. Option A is incorrect; reallocating to the same process would cause waste. Option B is incorrect; upcalls are a separate notification mechanism. Option D is incorrect as the goal is reuse, not destruction.

Q23. A process running with scheduler activations has a user-level scheduler that uses a priority-based scheduling algorithm. The kernel is unaware of these priorities. What is the MOST significant consequence of this lack of kernel awareness?

A.The kernel may preempt a high-priority thread to run a low-priority thread from a different process, causing priority inversion. ✅
B.The user-level priorities become globally ineffective.
C.The kernel cannot enforce any fairness policies.
D.The system will experience more page faults.
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: The kernel's scheduler allocates activations (processors) to processes. It is unaware of the priorities of individual threads within a process. This can lead to a problem where a process with a low-priority thread is preempted, while a different process with a high-priority thread is running. However, the more critical scenario is the one described in Option A. If a high-priority thread is holding a resource needed by other threads, the kernel might preempt the *process* that contains this high-priority thread to run a low-priority thread in another process. From the user-level perspective, this is a severe form of priority inversion, as the high-priority thread is being delayed for a lower-priority one. Option B is too absolute. Option C is too broad. Option D is unrelated.

Q24. Which of the following is NOT a requirement for an operating system to support the scheduler activations model?

A.The kernel must support multiple levels of thread priorities. ✅
B.The kernel must be able to notify user-space of scheduling events via upcalls.
C.The kernel must not have a 'thread' concept for user-level threads.
D.The kernel must manage activations as a countable resource.
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: The core requirements for scheduler activations are: (1) The kernel has no knowledge of user-level thread creation. (2) The kernel manages 'activations' as virtual processors. (3) The kernel communicates with the user-level scheduler via upcalls for blocking, preemption, and unblocking events. (4) The user-level scheduler must be able to receive and process these upcalls. Support for multiple levels of thread priorities is a feature of the user-level scheduler, not a requirement from the kernel. The kernel's scheduler handles process-level priorities or a simple round-robin for activations. Therefore, Option A is not a requirement. Options B, C, and D are all core requirements or characteristics.

Q25. An operating system has 4 processors. Process P1 uses scheduler activations. It has 8 threads: 4 are CPU-bound, 4 are blocked on I/O. The kernel has allocated 4 activations to P1. The user-level scheduler is running the 4 CPU-bound threads. The kernel then preempts P1's activations to run a higher-priority process P2. What does the user-level scheduler do with the state of the 4 CPU-bound threads?

A.Destroys the threads as they are no longer running.
B.Saves their state and marks them as ready.
C.Moves them to a 'preempted' state and waits for an upcall to resume them. ✅
D.Does nothing, as the kernel saves the threads' state.
💡 Difficulty: easy | ✅ Correct: C

📖 Explanation: When the kernel preempts P1's activations, it issues a preemption upcall for each activation. The user-level scheduler must handle this. It cannot simply save the state and mark the threads as ready (Option B) because if it marks them as ready, its internal scheduler might try to run them on an activation that no longer exists. The correct response is to move the threads to a special 'preempted' state. They are not ready to run until the kernel returns an activation via a 'resume' upcall. The user-level scheduler manages the thread state, not the kernel, so Option D is incorrect. Option A would lose work.

Q26. Given the scenario from the previous question (P1 preempted with 4 preempted threads), a thread in P1 now completes its I/O. The kernel issues an upcall to P1. What is the MOST logical first step for the user-level scheduler of P1?

📖 Explanation: Scheduler activations support coordination between scheduling layers, but they do not define a universally fair application-thread policy. The runtime must implement an appropriate policy, and fairness is also affected by available processors, blocking, priorities, synchronization, and competing workloads.

Q61. A user-level runtime receives notification that a thread has blocked, but its internal queue incorrectly removes every thread that shares the same priority. Several unrelated runnable threads then stop making progress. What is the best diagnosis?

A.The kernel must have terminated every thread at that priority
B.Scheduler activations prohibit priority-based scheduling
C.The runtime has incorrectly coupled independent thread states during event handling ✅
D.The blocked thread has automatically become the owner of every execution context
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: A blocking event should update the relevant thread and resource state without incorrectly altering unrelated runnable threads. Removing all threads of the same priority introduces an application-level scheduling bug. Notifications provide event information, but the runtime must interpret and apply it correctly.

Q62. A team wants to reduce the delay between a thread blocking in the kernel and another runnable thread beginning execution. Which measurement would best evaluate the improvement?

A.Measure the time between the blocking event and the next useful user-thread execution, while controlling for workload and resource availability ✅
B.Count only the total number of source-code files
C.Measure the average size of thread identifiers
D.Count how many functions declare local variables
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: The relevant delay is the interval between a blocking event and useful execution of another runnable thread. Measuring this interval directly helps determine whether coordination reduces idle gaps. Controlling workload and execution-resource availability is important because both can affect the observed delay.

Q63. An application has a long-running CPU-bound thread and several short I/O-bound threads. The CPU-bound thread monopolizes the only execution context assigned to the application, while the I/O-bound threads repeatedly become runnable. What limitation remains even if blocking notifications are handled correctly?

A.The runtime can execute unlimited threads on one context without switching
B.The kernel must make every I/O-bound thread run before the CPU-bound thread
C.The runtime cannot maintain a runnable queue for mixed workloads
D.Only one thread can execute at a time on the single context, so scheduling policy and timely preemption or yielding still affect responsiveness ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: Scheduler activations provide coordination information, but one execution context still supports only one executing thread at a time. If the runtime does not switch or yield appropriately, a CPU-bound thread may delay other runnable threads despite correct handling of blocking notifications.

Q64. A system grants additional execution contexts to a process, but the process's runnable queue is empty. What should a well-designed runtime generally do?

A.Recognize that no user-level work is currently ready and avoid inventing runnable tasks ✅
B.Create duplicate copies of blocked threads and execute them immediately
C.Treat each new context as a runnable user thread
D.Mark every completed thread as ready again
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: Execution capacity is useful only when runnable work exists. If the runnable queue is empty, the runtime should maintain correct state and wait for new work or relevant events. A resource grant does not automatically create application tasks or make blocked threads runnable.

Q65. A researcher claims that improved throughput after introducing scheduler activations proves that context-switching overhead has disappeared. What is the strongest critique?

A.Throughput cannot be measured for multithreaded programs
B.A throughput increase always indicates more memory usage
C.Context switching occurs only when a process terminates
D.Higher throughput can result from reduced idle time even while switching and notification overhead remain ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: Better coordination can increase useful work by reducing periods when execution resources sit idle. That improvement does not imply zero context-switching or notification costs. A full evaluation should measure both useful throughput and overhead to understand the trade-offs.

Q66. A runtime maintains five runnable threads and two usable execution contexts. Thread A blocks, and a notification is processed. A third context then becomes available, but thread B holds a lock needed by threads C and D. Which statement best captures the situation?

A.The third context guarantees that all five threads can complete immediately
B.The extra context increases potential execution capacity, but lock dependencies can still prevent some threads from making progress ✅
C.The lock becomes irrelevant once scheduler activations are enabled
D.The kernel must transfer the lock to thread A
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: An additional execution context permits another thread to execute simultaneously, but it does not remove synchronization dependencies. If threads C and D need a lock held by B, they may remain blocked or spin until the lock becomes available, limiting the benefit of additional capacity.

Q67. A developer implements a callback for scheduler notifications. The callback updates the resource count but also performs a lengthy blocking file operation before returning. What is the primary concern?

A.The callback may delay scheduling-event processing and undermine timely coordination ✅
B.Blocking file operations always increase the number of execution contexts
C.The resource count becomes a thread identifier automatically
D.Scheduler notifications cannot be processed by runtime code
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: A lengthy blocking operation inside notification handling can delay the runtime's response to scheduling events. This can leave scheduling state outdated or delay the dispatch of runnable threads. Event handling should generally be designed to preserve responsiveness and avoid unnecessary blocking.
