What is Fork and exec system calls in multithreading?

Definition:
Fork creates a new process by duplicating the calling process, while exec replaces current process image with new program. In multithreaded contexts, fork behavior becomes complex since only calling thread survives in child process, potentially causing deadlocks if other threads held locks. Exec in multithreaded programs terminates all threads except caller before loading new program.

Working:
When fork() executes in multithreaded program, child process contains copy of parent's memory but only the forking thread continues execution. Other threads vanish, leaving locks in inconsistent states. Exec() syscall loads new executable, terminating all existing threads cleanly. Proper handling requires either forking before creating threads or using fork-exec carefully with async-signal-safe functions.

Example:
Parent has threads A, B, C with mutex locked by B. Thread A calls fork(). Child has only thread A with mutex still locked (by vanished thread B), causing deadlock if A tries acquiring it. Solution: Call fork() before creating threads, or use pthread_atfork() handlers to reset locks in child process.

Reason:
Understanding fork-exec in multithreading prevents subtle bugs from inconsistent state after fork. Since child inherits memory but not thread execution context, synchronization primitives may remain locked indefinitely. Careful design ensures child process starts cleanly without inherited locks or thread-specific data causing problems.

Common MisConceptions:
Students think fork duplicates all threads in child process, but only calling thread survives. Another misconception is that exec behaves differently in multithreaded programs, when it consistently terminates all threads. Some believe fork-exec is safe anywhere in multithreaded code, ignoring async-signal-safety requirements.

Exam Preparation Tips: How to prepare this topic
Study fork behavior with active threads, understand pthread_atfork() registration, practice identifying unsafe fork locations, learn async-signal-safe function lists, and analyze deadlock scenarios from inherited lock states in child processes after fork.

Key Terms:

  • Fork - system call creating duplicate process.
  • Exec - system call replacing process with new program.
  • Async-Signal-Safe - functions safe to call after fork.
  • pthread_atfork - registering fork handlers for lock cleanup.

📝 All Fork and exec system calls in multithreading MCQs

Q1. A multithreaded server needs to launch an external utility while preserving its existing service process. Which sequence most directly creates a separate process and replaces that new process with the utility?

A.Call exec first and then fork if execution fails
B.Call fork to create a child process, then call exec in the child ✅
C.Call a thread-creation function and assume it creates an independent process
D.Call wait before creating the child process
💡 Difficulty: easy | ✅ Correct: B

📖 Explanation: The fork system call creates a child process with a separate process identity, while exec replaces the calling process image with a new program. A common pattern is to fork first and then execute the external utility in the child, leaving the parent available to continue its work.

Q2. A process has four threads when one thread calls fork. On a typical POSIX system, which thread arrangement exists in the child immediately after fork returns?

A.The child contains copies of all four threads, each running independently
B.The child contains no thread until exec creates one
C.The child contains only the thread that called fork ✅
D.The child contains four threads but shares their execution stacks with the parent
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: In a multithreaded POSIX process, the child created by fork contains only the thread that called fork. The child's address space reflects the process state at the fork point, but the other parent threads are not reproduced as running child threads.

Q3. A multithreaded application calls fork, and the child immediately calls exec successfully. What happens to the child process's previous program image?

A.It is replaced by the new program image, and the new program begins execution ✅
B.It remains fully active alongside the new program image
C.It is copied into a second child automatically
D.It is merged with the parent's address space permanently
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: The exec family replaces the calling process's program image with a new executable. The process identity generally remains the same, but the old code, data, and stack image are replaced, and the new program starts according to its entry-point and runtime initialization.

Q4. A developer assumes that calling fork from a multithreaded process gives the child an independent copy of every thread's execution. Why is this assumption incorrect?

A.Fork is prohibited in every multithreaded process
B.The child always inherits only the main thread, regardless of which thread called fork
C.Fork transfers all parent threads to the child and removes them from the parent
D.The child has only the calling thread, even though process memory is inherited in a snapshot-like state ✅
💡 Difficulty: medium | ✅ Correct: D

📖 Explanation: POSIX fork semantics create a child process with only the calling thread represented in the child. Memory state is inherited, commonly using copy-on-write, but other threads' execution does not continue in the child. This difference can leave inherited synchronization state problematic.

Q5. A developer wants to start an external command from a multithreaded application and avoid running application cleanup code in the child before the new program starts. Which design is generally safer?

A.Call all application destructors and logging routines in the child before exec
B.Let every thread call exec simultaneously after fork
C.Acquire every mutex in the child before preparing the command
D.Keep the post-fork child path minimal and use async-signal-safe operations until exec ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: After fork in a multithreaded POSIX process, the child may inherit locks and runtime state associated with threads that no longer exist there. Restricting the child path to async-signal-safe operations and proceeding promptly to exec reduces the risk of deadlock or inconsistent library behavior.

Q6. A graph shows child startup times of 12 ms for fork followed by exec, 10 ms for a direct spawn API, and 40 ms for a design that copies a large amount of application data manually. Which conclusion is best supported?

A.The measured spawn approach is fastest in this test, but broader conclusions require representative workloads ✅
B.Fork followed by exec must always be faster than every spawn API
C.Manual copying is always required for a correct child process
D.The graph proves that exec performs no memory-management work
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: The measured values indicate that the direct spawn approach has the lowest startup time in this particular test. Performance depends on the operating system, implementation, memory state, and workload, so the graph cannot establish a universal ranking for every process-launching strategy.

Q7. A child process calls exec with an invalid executable path. Which outcome should the calling code normally anticipate?

A.The parent process automatically executes the invalid command
B.The kernel creates a valid executable image from the filename
C.The child is guaranteed to terminate without running any further code
D.The call fails and returns control to the child code that invoked it ✅
💡 Difficulty: medium | ✅ Correct: D

📖 Explanation: If exec cannot locate or load the requested executable, it returns an error to the calling code rather than replacing the process image. The child should inspect the failure, report or communicate the error safely, and exit or follow an appropriate recovery path.

Q8. A developer forks a process after several threads have updated a shared in-memory counter. What value does the child initially observe?

A.A guaranteed zero because fork resets shared variables
B.The counter's state as observed in the process memory snapshot at the fork point ✅
C.A live shared counter that automatically follows later parent updates
D.A random value because fork does not copy process memory
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: The child initially receives the process memory state associated with the fork point, commonly implemented through copy-on-write pages. Subsequent ordinary writes by parent and child are generally independent, so the child's counter does not automatically track later parent updates.

Q9. A multithreaded program forks, and the child attempts to use a complex logging library before exec. The library occasionally deadlocks. Which remedy most directly addresses the risk?

A.Increase the number of threads in the child before logging
B.Call fork repeatedly until the logging library succeeds
C.Avoid complex non-async-signal-safe library operations in the child before exec ✅
D.Make every parent thread wait on the same mutex before fork
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: Library internals may contain mutexes or other state held by threads that do not exist in the child after fork. Calling complex routines before exec can therefore deadlock or behave unpredictably. A minimal async-signal-safe child path is generally safer.

Q10. A developer believes that copy-on-write means fork immediately duplicates every physical memory page used by the parent. Which correction is most accurate?

A.Copy-on-write means the parent and child share one process identifier
B.Copy-on-write prevents either process from modifying memory
C.Copy-on-write requires all pages to be copied before fork returns
D.Copy-on-write can defer physical copying until a write requires a private copy ✅
💡 Difficulty: medium | ✅ Correct: D

📖 Explanation: Copy-on-write implementations can initially let parent and child map the same physical pages with suitable protection. When one process writes to a shared page, the operating system can create a private copy. This often reduces fork overhead, though actual behavior depends on the system.

Q11. A program's worker thread calls fork while the main thread is updating a shared data structure. The child sees a partially updated structure. What is the best interpretation?

A.Fork automatically waits until every application-level update is logically complete
B.The child reflects a process-memory snapshot that may capture an inconsistent application-level state ✅
C.The child has a live view of the main thread's future writes
D.The kernel guarantees atomicity for every multi-step data-structure update
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Fork captures memory state, but it does not automatically enforce application-level transaction boundaries across multiple writes. If another thread is partway through updating a data structure, the child can inherit a state that is internally inconsistent unless the program coordinates the fork appropriately.

Q12. A parent forks a child and immediately modifies a global variable. The child later reads its corresponding variable and sees the pre-modification value. Which explanation is correct?

A.The parent and child generally have separate memory views after fork, with writes not automatically propagated ✅
B.The child always reads variables directly from the parent's stack
C.Exec must have silently restored an older program version
D.Global variables cannot be inherited by child processes
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: After fork, parent and child have logically separate address spaces, even if copy-on-write allows physical pages to be shared initially. A parent write normally affects its own memory view and does not update the child's corresponding global variable.

Q13. A multithreaded application forks, and the child calls a function that tries to acquire a lock held by another parent thread at the fork instant. Why can the child remain blocked indefinitely?

A.The parent always transfers ownership of all locks to the child
B.The lock can remain marked as held even though its owning thread was not copied into the child ✅
C.The exec family disables every mutex in the system
D.Fork makes all locks permanently read-only
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: The child inherits relevant memory and synchronization state but only one surviving thread. A mutex held by a vanished thread may remain locked without a child thread capable of releasing it, so attempting to acquire it can block indefinitely.

Q14. A developer launches an external command and needs to redirect its standard output to a file. Which sequence best represents a common Unix process-launching design?

A.Call wait, then open the output file after the child has finished
B.Call exec in the parent and then attempt to restore the original program
C.Fork, configure the child's output file descriptor, and then exec the external program ✅
D.Create a new thread and assume its output descriptor belongs only to that thread
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: A common launch sequence forks a child, changes its file descriptors using appropriate system calls, and then executes the requested program. The parent retains its own process image. Correct error handling is required if descriptor setup or exec fails.

Q15. A developer forks a child and expects modifications to a global array in the child to become visible in the parent automatically. What should the developer change if this communication is required?

A.Rely on the inherited array because fork creates live shared memory
B.Use an explicit interprocess communication mechanism or deliberately shared memory ✅
C.Call exec after each array modification to synchronize the processes
D.Replace the array with a local variable in the child
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: Ordinary process memory is not automatically shared as a live mutable array between parent and child after fork. Communication requires an appropriate mechanism such as a pipe, socket, shared-memory mapping, or another supported interprocess communication facility.

Q16. A program forks while multiple threads are active. The child uses a buffered output routine before exec and the output unexpectedly appears duplicated. Which explanation is plausible?

A.Buffered library state may have been inherited, and flushing in multiple processes can duplicate buffered output ✅
B.Fork automatically clears every output buffer in all implementations
C.Exec duplicates the parent's output on every successful call
D.Output buffering is available only in single-threaded processes
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: Buffered output state can be inherited as part of process memory at fork. If buffered data has not been flushed, both parent and child may later flush copies of the same data. Carefully flushing before fork or avoiding unsafe child-side library operations can prevent duplication.

Q17. A developer uses fork to launch a child from a multithreaded service and then performs extensive memory allocation in the child before exec. What is a major concern?

A.Memory allocation always creates an extra child process
B.The allocator is guaranteed to use no synchronization
C.The child automatically inherits every allocator worker thread
D.Allocator locks or runtime state may be inconsistent because threads that held them are absent in the child ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: Memory allocators may use internal locks or other shared runtime state. After a multithreaded fork, the child lacks the other threads that may have held those locks, so complex allocation before exec can deadlock. A minimal safe child path is preferable.

Q18. A process has multiple threads and uses fork. The child must perform substantial preparation before launching a new program. Which alternative may be worth considering on systems that support it?

A.Create a thread in the child and let both threads call exec
B.Use fork repeatedly until the child inherits a consistent lock state
C.Use an appropriate spawn API that combines process creation and program launching under supported platform semantics ✅
D.Run the external program directly inside the parent's current address space
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: Some platforms provide spawn APIs that can simplify launching a new program without requiring an application to perform extensive post-fork work. Such APIs may reduce risks associated with inherited multithreaded runtime state, although their capabilities and semantics vary by platform.

Q19. A child calls exec after fork, but the parent observes that a signal handler behaves differently in the new program. Which detail is important when reasoning about signal behavior across exec?

A.All signal dispositions and masks are guaranteed to remain unchanged in every respect
B.Exec converts all pending signals into thread-creation requests
C.Signal handlers are copied into the new executable as ordinary application functions
D.Successful exec changes process image and resets caught signal dispositions according to applicable system rules ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: Exec replaces the program image, so signal behavior must be considered using the relevant POSIX rules. Caught signal dispositions are generally reset to default on successful exec, while other signal attributes may be preserved or treated differently according to the applicable rules.

Q20. A developer wants a child to report whether an external program launched successfully. Why is checking the return value of exec alone insufficient in the parent?

A.The parent receives the new program's return value directly from exec
B.The parent should use an appropriate communication mechanism for launch errors and wait status for eventual termination ✅
C.Exec always returns the child's final exit status
D.Fork automatically stores the launch result in every parent's global variable
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: Exec executes in the child, so its failure return is observed by the child code rather than directly by the parent. The parent can collect eventual termination status with wait or waitpid and can use a pipe or another communication channel to learn detailed launch errors.

Q21. A program's child executes a new program, but the developer expects the child to preserve all thread-local variables from the old executable. Which assessment is most accurate?

A.Thread-local variables are guaranteed to survive exec with their old values
B.Exec only replaces shared libraries and leaves every old thread stack intact
C.The old program's execution state is replaced, so the new program should not rely on old thread-local execution state ✅
D.Thread-local storage automatically becomes process-shared memory after exec
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: A successful exec replaces the old program image and does not continue its previous threads as the old program. The new program initializes its own runtime and thread-local state according to its execution environment rather than relying on the old program's thread-local variables.

Q22. A server uses a child process to execute an untrusted external utility. Which security practice is most relevant before executing the new program?

A.Carefully manage inherited file descriptors, credentials, environment, and other process state ✅
B.Assume exec automatically removes every privilege and open descriptor
C.Pass every parent environment variable without review
D.Use the parent process's memory as the child's shared communication channel
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: Launching an external program can expose inherited resources and environmental settings. Appropriate descriptor closure, privilege management, environment sanitization, and deliberate argument construction help reduce unintended access. Exec changes the program image but does not automatically eliminate every inherited capability or resource.

Q23. A developer calls fork in a multithreaded process and then the child calls exit after exec fails. In a program with buffered streams and registered cleanup handlers, what alternative is often safer for a minimal child failure path?

A.Call every application cleanup handler before returning
B.Use a new fork to flush all parent buffers
C.Restart the parent process from the child
D.Use _exit when appropriate to terminate the child without running inherited user-space cleanup handlers ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: After fork in a multithreaded program, inherited buffered streams and cleanup handlers may reflect state that should not be processed normally in the child. When exec fails and the child must terminate, _exit can avoid running inherited user-space cleanup routines or flushing duplicated buffers.

Q24. A parent process creates a child with fork and does not wait for it. The child terminates, but its termination status remains available for collection. What issue may arise if the parent never collects that status?

A.The child restarts automatically with its old threads
B.The terminated child may remain as a zombie until its status is collected ✅
C.The child automatically becomes a thread in the parent
D.The parent loses access to every file descriptor
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: A terminated child can remain as a zombie until its parent or another eligible process collects its termination status. Waiting or using an appropriate child-reaping strategy releases the associated process-table entry and prevents accumulation of unreaped children.

Q25. A team is choosing between directly executing an external program and launching it as a child from a multithreaded application. The application must continue serving requests while the external program runs. Which design best satisfies the requirement?

A.Call exec in the service process and expect its old code to continue
B.Replace the service's main thread with the external program while preserving its old process image
C.Fork or use a suitable spawn mechanism to launch the external program separately, then let the service continue ✅
D.Call exec from every service thread so the service remains available
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: A successful exec replaces the calling process image, so executing the external program directly in the service process would prevent the old service program from continuing. Creating a child or using a suitable spawn mechanism lets the service retain its own execution while the external program runs separately.

Q26. A child inherits a file descriptor for a pipe and then successfully executes a new program. The parent expects to receive end-of-file when it closes its own write end, but EOF never arrives. What is a likely cause?

A.The child or another process still holds an open write-end descriptor ✅
B.Exec always converts pipe descriptors into regular files
C.Fork automatically duplicates pipe data until the parent reads it
D.The pipe must be attached to the main thread before EOF can occur
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: A pipe reader normally observes EOF only when all write-end descriptors referring to that pipe have been closed. If the child inherits a write descriptor and exec preserves it, the pipe can remain open even after the parent closes its own copy. Close-on-exec or explicit closure can resolve this.

Q27. A multithreaded application requires a consistent snapshot of several related in-memory structures in its child process. Which strategy is most appropriate before creating that child?

A.Assume fork automatically makes every multi-step update atomic
B.Coordinate the relevant application state so fork occurs at a safe point, or use a suitable alternative design ✅
C.Call exec before the structures are initialized
D.Allow all threads to update the structures during fork without synchronization
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Fork does not automatically make a sequence of application-level updates atomic. If the child needs a consistent snapshot, the application should coordinate access to related state and choose a safe point or a suitable alternative process-launching design that avoids inheriting inconsistent runtime state.
