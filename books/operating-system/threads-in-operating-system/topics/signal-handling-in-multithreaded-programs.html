What is Signal handling in multithreaded programs?

Definition:
Signal handling in multithreaded programs involves delivering asynchronous notifications (signals) to specific threads or processes, requiring careful coordination since signals can interrupt any thread unpredictably. POSIX specifies that signals targeting process are delivered to one arbitrary thread, while thread-directed signals go to specific threads, necessitating robust signal masks and handlers to prevent race conditions and inconsistent states.

Working:
Each thread maintains signal mask blocking certain signals. Process-directed signals choose recipient from threads not blocking that signal. Thread-directed signals via pthread_kill() target specific threads. Signal handlers execute in context of receiving thread, potentially interrupting critical sections. Proper handling requires installing handlers before creating threads and using sigwait() for synchronous signal processing.

Example:
Main thread installs SIGINT handler, creates worker threads. User presses Ctrl+C sending SIGINT. OS delivers to main thread (not blocking it), handler executes cleanup. If worker thread blocked SIGINT, it won't receive signal. Solution: Use sigprocmask() to control which threads receive which signals appropriately.

Reason:
Signals provide mechanism for external events (keyboard interrupts, timer expiration) to notify programs. In multithreaded contexts, unpredictable delivery complicates reasoning about program state. Proper signal handling ensures clean shutdown, prevents corruption from interrupted critical sections, and enables responsive event-driven architectures.

Common MisConceptions:
Students believe signals always go to main thread, but POSIX allows delivery to any unblocking thread. Another misconception is that signal handlers can safely call any function, when only async-signal-safe functions prevent undefined behavior. Some think masking signals in one thread affects others, but each thread has independent signal mask.

Exam Preparation Tips: How to prepare this topic
Understand signal delivery rules, memorize async-signal-safe functions, practice using sigwait() for controlled signal handling, study signal mask inheritance, and learn proper handler installation timing relative to thread creation to avoid race conditions.

Key Terms:

  • Signal - asynchronous notification to process or thread.
  • Signal Mask - set of blocked signals per thread.
  • Sigwait - synchronous signal waiting function.
  • Async-Signal-Safe - functions safe in signal handlers.

📝 All Signal handling in multithreaded programs MCQs

Q1. A multithreaded server receives a signal indicating that its process should terminate gracefully. Which design best ensures that termination is coordinated without allowing arbitrary worker threads to perform conflicting cleanup?

A.Allow every thread to independently terminate the process
B.Arrange for a designated signal-handling thread to receive and coordinate the termination request ✅
C.Ignore the signal until all threads terminate naturally
D.Let whichever worker finishes first destroy all shared resources
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: A designated signal-handling thread centralizes the response to process-wide termination requests. It can notify workers, stop accepting new tasks, coordinate cleanup, and initiate orderly shutdown, reducing races caused by multiple threads independently managing shared resources.

Q2. Why can delivering a process-directed signal to an arbitrary eligible thread complicate the design of a multithreaded application?

A.Every eligible thread must execute the handler simultaneously
B.The signal is automatically converted into a thread-local event
C.The application may be unable to predict which thread's execution context will run the handler ✅
D.The operating system must create a new process for every signal
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: A process-directed signal may be delivered to an eligible thread selected by the operating system. If the application assumes a particular worker will handle it, the handler may run in an unexpected context and interfere with thread-specific state or synchronization.

Q3. A program blocks a particular signal in every worker thread and leaves it unblocked in a dedicated signal-waiting thread. What is the main benefit of this arrangement?

A.It makes the signal disposition different for each thread
B.It guarantees that all signals are queued indefinitely
C.It eliminates the need to decide how signals should be handled
D.It creates a predictable place for synchronous signal reception and response ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: Blocking the signal in workers and unblocking it in a designated receiver helps establish a controlled handling path. A synchronous waiting mechanism can receive the signal in that thread, where the application can coordinate responses without executing an asynchronous handler in arbitrary workers.

Q4. A developer assumes that blocking a signal in one worker prevents the entire process from receiving that signal. Which correction is most accurate?

C.A blocked signal is always discarded immediately
D.Signal masks only affect threads created after the mask is changed
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: Signal masks are maintained per thread. Blocking a signal in one worker changes that worker's eligibility, not necessarily the eligibility of every other thread. To direct signals predictably, a program must coordinate masks across its threads and understand the signal's delivery rules.

📖 Explanation: When multiple threads are eligible for a process-directed signal, an application generally cannot assume which eligible thread will receive it. Reliable designs use deliberate signal-mask policies and a documented receiving mechanism rather than relying on thread identity.

Q6. A worker handles a signal by updating a shared linked list while another worker modifies the same list. What is the principal risk if the handler interrupts the first worker during a list operation?

📖 Explanation: A signal handler can interrupt code while shared data structures are temporarily inconsistent. If it modifies the same structure, it may violate invariants or race with other threads. Handlers should avoid unsafe shared-state manipulation and defer complex work to ordinary thread context.

Q7. A program uses a synchronous signal-waiting function in a dedicated thread instead of executing a traditional asynchronous handler. What design advantage does this provide?

📖 Explanation: Synchronous signal waiting lets a dedicated thread receive selected signals through an ordinary function call. This can simplify coordination and error handling compared with asynchronous interruption, although the program must still configure masks correctly and handle the received signals appropriately.

Q8. A process-directed signal is generated while every thread blocks it. Under typical POSIX semantics, what should the application expect?

It may remain pending until delivery becomes possible, but exact pending behavior depends on the signal type and system rules, so the application should not assume unlimited queuing.

Q9. A programmer wants a signal to interrupt one specific worker rather than be handled by an arbitrary eligible thread. Which approach most directly expresses that intention in a POSIX-style environment?

📖 Explanation: Thread-directed signaling targets a particular thread, unlike process-directed signaling whose delivery may go to an eligible thread. The receiving thread must still be able to accept the signal, and the application must account for the targeted thread's mask and the signal's behavior.

Q10. A signal handler calls a routine that acquires a mutex. The signal interrupted a thread that already held that mutex. What is the most likely failure?

A.The mutex is automatically released before the handler starts

📖 Explanation: If a handler interrupts a thread that holds a mutex and then tries to acquire the same mutex, the handler may wait for a lock that the interrupted code cannot release until the handler returns. This creates a deadlock risk, so ordinary mutex operations are unsuitable in many asynchronous handlers.

Q11. A server's signal handler sets a suitable flag, and the main event loop checks that flag and performs shutdown outside the handler. Why is this often safer than performing shutdown directly inside the handler?

📖 Explanation: Asynchronous handlers can interrupt code at inconvenient points, so complex operations such as allocation, logging through unsafe routines, and mutex-based coordination can be dangerous. A minimal handler can record a request using an appropriate signal-safe mechanism, while the main loop performs orderly shutdown.

📖 Explanation: A process-wide signal disposition does not make handler execution safe in every thread context. A handler may interrupt code holding locks or manipulating shared state, and concurrent or repeated events can expose race conditions. Centralized reception or minimal signal-safe handling is generally more robust.

If workers leave the relevant signal unblocked, they may be eligible for asynchronous delivery, undermining the intended routing. The program should consistently block the signal in workers and unblock or synchronously wait for it in the receiver.

Q15. A multithreaded program receives a signal requesting a configuration reload. Which response best separates signal reception from potentially complex work?

Recording the request and delegating work to normal thread context allows standard error handling, locking, validation, and coordinated replacement of configuration data.

In C, volatile sig_atomic_t is a common mechanism for a simple handler-to-main-thread notification, but it is not a general-purpose interthread synchronization primitive.

Q17. A signal-handling design uses a handler that calls printf to record each event. Under heavy concurrent activity, what is the strongest concern?

Safer designs use minimal signal-safe notification and defer logging.

A minimal handler or controlled receiver should request the dump, while a coordinated diagnostic mechanism gathers information safely and documents any limitations in snapshot consistency.

Q41. A signal handler sets a flag, but a compiler optimization causes the main loop not to observe updates as expected. Which lesson is most appropriate?

A.All compiler optimizations must be disabled in every multithreaded application
B.A plain shared variable is always sufficient for communication with a signal handler
C.The flag must use a mechanism with the required signal-handler semantics and, where applicable, correct language-level synchronization ✅
D.Signal masks guarantee visibility of all ordinary memory writes
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: A compiler may optimize accesses to an ordinary variable when the language rules do not require it to observe asynchronous updates. A handler-to-main flag needs a suitable signal-safe type or mechanism, such as volatile sig_atomic_t in applicable C code, with broader synchronization handled separately where needed.

Q42. A program must handle a signal promptly but also preserve a strict ordering between the signal request and a shared-state update performed by a worker. What is the best design principle?

A.Assume signal delivery alone establishes every required memory-ordering relation
B.Use an explicit synchronization protocol to order the update and request processing, rather than relying on signal arrival alone ✅
C.Allow the handler to rewrite the worker's program counter
D.Block the signal only after freeing the shared state
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Signal delivery is not a substitute for a clearly specified synchronization protocol governing shared application data. If processing must occur after a particular update, use suitable atomic operations, mutexes in ordinary context, queues, or other synchronization that establishes the required ordering and ownership.

Q43. A service receives repeated requests to refresh the same cache. Refreshing is expensive, and only the latest configuration matters. Which signal-response strategy can reduce wasted work without losing the required final state?

A.Start a full refresh in every handler invocation and let all workers overwrite the cache
B.Create an unlimited number of refresh threads for every pending signal
C.Treat every ordinary signal as a guaranteed separate durable job
D.Coalesce redundant refresh requests in normal application logic and perform a coordinated refresh using the latest configuration ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: If only the latest configuration matters, processing every repeated notification as an independent job can waste resources. A receiver can record that refresh is needed and coalesce redundant requests, then perform a coordinated update in normal context. This application-level strategy complements, rather than depends on, signal coalescing.
