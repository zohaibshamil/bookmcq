What is Signal handling in multithreaded programs?

Definition:
In multithreaded programs, signals may be delivered to any thread or a specific one depending on type; synchronous signals target the faulting thread, while asynchronous signals require explicit masking or dedicated handler threads to avoid race conditions.

Example:
Using \( \texttt{sigwait()} \) in a dedicated thread safely handles \( \texttt{SIGINT} \) without disrupting computation threads.

Reason:
Default signal delivery is unpredictable in multithreaded contexts; controlled handling prevents undefined behavior and ensures reliable interruption or cleanup semantics.

Q1. In a POSIX multithreaded process, a signal generated specifically for a particular thread (e.g., via `pthread_kill`) is delivered to which context?

A.The signal is delivered to the process-wide signal handler, which then dispatches it to the target thread.
B.The signal is delivered directly to the specified thread, and only that thread's signal mask determines its disposition. ✅
C.The signal is placed in a global process queue, and the first available thread handles it.
D.The signal is ignored unless the target thread has a dedicated signal stack.
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: This question tests the fundamental conceptual difference between process-directed and thread-directed signals. A thread-directed signal is delivered to the specific thread identified by the `pthread_kill` call. The target thread's signal mask determines whether the signal is blocked or handled. The process-wide handler is irrelevant here; the signal bypasses the process-level queue and is directed to the thread's own internal data structure. This demonstrates a core principle of thread-aware signal handling.

Q2. Analyze the following code: Thread A blocks `SIGINT` in its mask. Thread B calls `raise(SIGINT)`. What is the immediate outcome?

A.Thread B will handle the signal immediately, as `raise` sends the signal to the calling thread. ✅
B.Thread A will receive the signal because it is part of the same process.
C.The signal is pending for the entire process and will be delivered to Thread A only.
D.The program will terminate because `SIGINT` is unhandled.
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: The `raise()` function sends a signal to the calling thread (Thread B) in a multithreaded process. Since the signal is not blocked for Thread B (only Thread A has it blocked), the default or installed handler for Thread B will execute. Thread A's mask is irrelevant. This is a common misconception that signals sent via `raise` always go to the main thread or the entire process, highlighting the importance of understanding thread-directed signal interfaces.

Q3. A multithreaded application uses asynchronous signal handlers for `SIGUSR1`. Which of the following is a guaranteed-safe operation inside the handler?

A.Modifying a global integer that is protected by a mutex.
B.Calling `printf()` to log the signal receipt.
C.Setting a volatile `sig_atomic_t` global flag to indicate signal receipt. ✅
D.Allocating memory using `malloc()` to store signal data.
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: The `sig_atomic_t` type is specifically defined for atomic access in asynchronous signal handlers, ensuring that reads and writes are not interrupted. Mutexes (`pthread_mutex_lock`) are not async-signal-safe; if the handler interrupts a thread holding the lock, it will deadlock. `printf` and `malloc` are not async-signal-safe due to internal locking and state. This question requires understanding the severe restrictions of async-signal-safe functions in a multithreaded, reentrancy-sensitive context.

Q4. A real-time application uses `sigwaitinfo()` to synchronously handle signals in a dedicated thread. What is the primary advantage over traditional asynchronous handlers in a multithreaded process?

A.It eliminates the need for a signal mask, simplifying the code.
B.It avoids the complexity and risks of async-signal-unsafe functions by processing signals in a normal thread context. ✅
C.It guarantees lower latency for signal delivery.
D.It allows the signal handler to run with elevated privileges.
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: Using `sigwait` or `sigwaitinfo` shifts signal handling from asynchronous interrupt context to synchronous function call context within a specific thread. This means the thread can safely call any standard library function (like `printf` or `malloc`) because the signal is not interrupting an arbitrary instruction stream. It doesn't improve latency or remove the need for masks; it primarily solves the safety and reentrancy problems inherent in async handlers.

Q5. Consider a process with three threads (T1, T2, T3). The signal mask for T1 and T2 includes `SIGTERM`, but T3 does not. A `SIGTERM` is sent to the process via `kill(pid, SIGTERM)`. How is this signal delivered?

A.It is delivered to T1 because it was created first.
B.It is delivered to any thread that does not have `SIGTERM` blocked, provided it is not ignoring the signal. ✅
C.It is delivered to T3, since it is the only thread not blocking it.
D.The signal is delivered to the main thread only.
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: This is the critical rule for process-directed signals. The kernel inspects the signal masks of all threads in the process. It selects a single thread that does not have the signal blocked in its mask. If only T3 has it unblocked, it goes to T3. If all have it blocked, it remains pending. It does not go to the first thread or to the main thread specifically. This demonstrates the interaction between process-level actions and per-thread signal masks.

Q6. Analyze this erroneous reasoning: 'If I block all signals in every thread except one dedicated handler thread, my application becomes completely signal-safe.' Which flaw exists in this statement?

A.Blocking signals in other threads does not prevent asynchronous signal handlers from interrupting the dedicated thread.
B.The handler thread will still be interrupted by signals, which are processed asynchronously, potentially causing deadlocks if it holds a lock. ✅
C.Blocking signals in all threads prevents the process from responding to critical signals like `SIGKILL` and `SIGSTOP`, which cannot be blocked.
D.The statement assumes that blocking signals prevents them from being delivered to the process, but only thread-directed signals are impacted.
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: The fundamental flaw is that the dedicated handler thread itself will receive and handle signals asynchronously. If that handler thread performs a `sigwait` and otherwise performs normal operations, it may be interrupted. If it holds a mutex while a signal handler that tries to lock the same mutex is invoked, a classic signal-induced deadlock occurs. Blocking signals in other threads does not protect the handler thread from its own signal delivery.

Q7. A multithreaded program uses a global flag `volatile sig_atomic_t stop_flag` set in a `SIGINT` handler. The main loop checks this flag. Consider a scenario on a multi-core system. What is a potential issue with this design?

A.The `volatile` keyword is redundant and creates a race condition.
B.Without a memory barrier, the main loop on another core might not see the updated value of `stop_flag` due to compiler or CPU caching. ✅
C.The `sig_atomic_t` type is not atomic on multi-core systems.
D.The `volatile` keyword guarantees atomicity across cores, so there is no issue.
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: `volatile` ensures the compiler reads the variable from memory every time, but it does not enforce memory ordering or cache coherence across CPU cores. On a multi-core system, the signal might be handled on one core, updating `stop_flag` in that core's cache. The main loop executing on another core might read a stale cached value. A proper solution uses atomic operations with memory barriers (e.g., `atomic_signal_fence` or `std::atomic` with relaxed ordering) to ensure visibility.

They are thread-directed and are delivered to that exact thread. This is crucial for debugging and error handling. If the thread has no handler and the signal is not blocked, the default action (termination) applies to that thread, though in many implementations it may lead to process termination depending on behavior and core dumps.

Q9. Two threads, T1 and T2, share a linked list. T1 is executing a `malloc` operation inside a `SIGUSR1` handler. T2 was interrupted by a `SIGUSR1` while holding a lock on the same heap structure. What is the most likely outcome?

If T1's handler calls `malloc` while T2's handler (which holds the heap lock) is interrupted, T1 will wait indefinitely for the lock held by T2, while T2 cannot proceed until its handler returns. 📖 Explanation: `pthread_sigmask` sets the signal mask for the calling thread. When a process-directed signal arrives, the kernel's selection algorithm only considers threads that have the signal unblocked. If the target thread has it blocked, the kernel simply excludes it from the list of potential recipients. The signal remains pending if all threads block it, but it is not discarded. This demonstrates the interplay between thread-local masks and process-wide signal routing.

📖 Explanation: The correct design is to block the signal in all threads except the dedicated one. Since process-directed signals go to a random thread that doesn't have the signal blocked, only the dedicated thread will be eligible to receive it. Simply installing a handler in the main thread is insufficient, as the signal could be delivered to any other non-blocking thread, causing unexpected reaps or races. `sigwait` is a good alternative, but the blocking strategy is the primary mechanism to control delivery to a single thread.

If the signal is ignored globally, this is safe. This avoids race conditions associated with signal masks and global disposition changes, offering a per-thread or per-connection control that is better for managing complex, high-performance servers.

Q14. A multithreaded program uses `pthread_mutex_lock` in a `SIGUSR1` handler. Under what specific condition is this operation strictly safe and guaranteed not to deadlock?

A.If the mutex is of type `PTHREAD_MUTEX_RECURSIVE`.
B.If the mutex is a process-shared mutex.

D.If the mutex is a spinlock used only in that handler.
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: This is a trap question. The correct answer highlights the core problem: it is impossible to guarantee the state of a mutex when an asynchronous signal handler runs. The handler could interrupt a thread that holds the mutex, causing a deadlock when the handler attempts to lock it. There is no mutex type or attribute that solves this fundamental asynchronous interruption problem. This is why async-signal-safe functions are defined; they avoid using any locking primitives that could lead to a deadlock with the interrupted context.

Q27. A program has thread T1 that owns a mutex M. A signal handler for `SIGUSR1` in T1 attempts to lock M. T2 sends `SIGUSR1` to T1. What is the state of T1, and what is the system's typical response?

A.T1 successfully locks M after the signal handler returns.
B.T1 deadlocks because it tries to re-acquire M without releasing it, leading to a hang. ✅
C.The kernel detects this as an invalid operation and sends a `SIGKILL` to T1.
D.The `pthread_mutex_lock` call returns `EINVAL` and the handler continues.
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: This is a classic recursive deadlock within a single thread. T1 holds mutex M. The signal arrives and interrupts T1. The handler executes and attempts to lock M. Since M is already held by T1 itself (and is not a recursive mutex), the lock operation will block indefinitely, waiting for T1 to release M. However, T1 cannot release M until the handler returns, and the handler cannot return until it acquires M. This results in a self-deadlock. The system has no way to resolve this, causing the thread to hang.

C.Use `fcntl` to set `O_NONBLOCK` on all sockets.
D.Increase the socket send buffer size to prevent `SIGPIPE`.
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: The best resolution is to block `SIGPIPE` and handle `EPIPE` errors from `send`/`write`. Using `pthread_sigmask` blocks the signal, preventing the default termination. The error is then exposed in the return value of the system call, allowing the thread to handle it gracefully (e.g., close the socket). Blocking globally with `SIG_IGN` is process-wide and less granular. `O_NONBLOCK` changes socket behavior but doesn't prevent `SIGPIPE`. Handling `EPIPE` is the standard, robust, thread-aware way to deal with broken connections.

Q29. In a multithreaded environment, what is the significance of the `SA_RESTART` flag in `sigaction`?

A.It ensures the signal handler is restarted if it is interrupted by another signal.
B.It automatically reissues blocking system calls that are interrupted by the signal, improving robustness in a multithreaded program. ✅
C.It prevents the signal handler from being called in a thread that is executing a system call.
D.It restores the signal mask to its original state before the handler returns.
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: The `SA_RESTART` flag is used to affect system call behavior. When a signal interrupts a blocking system call (like `read` or `write`), the system call typically returns `-1` with `errno` set to `EINTR`. If `SA_RESTART` is set, the kernel automatically reissues the interrupted system call after the signal handler returns, making it transparent to the application. This is highly beneficial in multithreaded programs where signals are common, reducing the complexity of manually checking for `EINTR` in every loop.

Q30. A thread blocks `SIGINT` and then calls `system(ping -c 1 google.com")`. The `ping` command itself sends a `SIGINT` to the calling process on interrupt. Is the `SIGINT` blocked during the `system()` call?"

A.Yes, because the thread's signal mask is inherited by the child process.
B.No, `system()` resets the signal masks for the duration of the call.
C.No, `system()` executes the command in a separate child process, which has its own signal mask. The parent's `SIGINT` mask remains blocked, but child processes ignore parent masks. ✅
D.Yes, but only for the parent thread; the child process inherits the blocked mask.
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: `system()` creates a child process via `fork` and `exec`. The `fork` call replicates the signal mask of the calling thread for the child process. However, after `exec`, the new program (the child) starts with default signal dispositions and masks, unless explicitly changed. So, while the parent thread has `SIGINT` blocked, the child `ping` process does not inherit the blocked mask after `exec`. It has default behavior. This tests the distinction between `fork` inheritance and `exec` behavior.

Q31. Consider a program where a thread T1 is blocked on a `sem_wait(&sem)`. Another thread T2 sends a process-directed `SIGUSR1`. If T1 is the only unblocked thread for `SIGUSR1`, what is the effect on `sem_wait`?

A.The signal is ignored because T1 is in a blocking state.
B.`sem_wait` will fail with `EINTR`, and the semaphore count will be guaranteed to be decremented.
C.`sem_wait` will return -1 with `errno` set to `EINTR`, and the semaphore state is unchanged. ✅
D.`sem_wait` completes successfully because the signal is delivered after the semaphore operation.
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: If a signal is delivered to a thread that is blocked in a POSIX semaphore wait (`sem_wait`), the system call is interrupted. It returns `-1` and sets `errno` to `EINTR`. Importantly, the semaphore count is not decremented. This is a key distinction from some other synchronization primitives. The caller must handle the `EINTR` error by restarting the `sem_wait` or taking appropriate action. This emphasizes that `sem_wait` is an interruptible system call with specific behavior.

Q32. A programmer wants to avoid `EINTR` headaches in a multithreaded server that uses `epoll_wait`. Which of the following strategies is most robust and why?

A.Wrap `epoll_wait` in a loop that continues on `EINTR`.
B.Set the `SA_RESTART` flag for all signals in the process.
C.Block all signals in the I/O threads using `pthread_sigmask`, and handle all signals in a dedicated thread using `sigwait`. ✅
D.Use `ppoll` instead of `epoll_wait` with a signal mask.
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: The most robust solution is to block all signals in the I/O threads. Since the I/O threads are not eligible for signal delivery, their system calls will never be interrupted by asynchronous signals. All signals are managed by a dedicated handler thread using `sigwait`. This eliminates `EINTR` completely for the I/O threads, leading to simpler code and predictable performance. Wrapping in a loop is common but adds overhead. `SA_RESTART` only works for certain signals and system calls. This is a gold-standard design pattern for high-performance servers.
