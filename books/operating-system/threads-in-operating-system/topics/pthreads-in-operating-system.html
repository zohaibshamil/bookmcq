What is Pthreads in operating system?

Definition:
Pthreads (POSIX threads) is a standardized C API defined by IEEE POSIX 1003.1c for thread creation, mutexes, condition variables, and attributes, typically implemented as one-to-one on Unix-like systems.

Reason:
As a cross-platform standard, Pthreads ensures portability of multithreaded C/C++ applications across Linux, macOS, and other POSIX-compliant systems.

Q3. Given a system with 2 cores, a program uses 4 threads that are CPU-bound and perform no I/O. Which scheduling policy would most likely cause the threads to experience starvation?

A.SCHED_FIFO with all threads at same priority ✅
B.SCHED_RR with all threads at same priority
C.SCHED_OTHER with default nice value
D.SCHED_BATCH
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: SCHED_FIFO (First-In-First-Out) with equal priorities does not preempt a running thread. If one thread enters a long computation, it will run to completion, causing the other 3 threads to starve until it finishes. SCHED_RR would time-slice, SCHED_OTHER uses timesharing, and SCHED_BATCH is for background jobs. This tests the application of scheduling policies to thread starvation scenarios.

Q4. In a multi-threaded program, a global variable `int counter = 0;` is protected by a mutex. Thread A locks the mutex, increments counter, and then calls a function `foo()` which attempts to lock the same mutex. What is the most likely outcome?

A.Deadlock ✅
B.Race condition
C.The program runs normally
D.Undefined behavior
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: This is a classic deadlock scenario if the mutex is not recursive. Pthreads mutexes by default are non-recursive. If a thread tries to lock a mutex it already holds, it will block indefinitely, waiting for itself to release the mutex. This results in deadlock. The outcome is not a race condition because the mutex prevents simultaneous access. It's a self-deadlock. This tests the concept of recursive vs non-recursive mutexes.

Q5. Consider a program with two threads that share an integer `x` initialized to 0. Thread 1 executes: `x = 5;` and Thread 2 executes: `x = 10;`. Without synchronization, which of the following is the most accurate statement about the final value of `x`?

Q9. A program has 3 threads: T1 (priority 10), T2 (priority 20), T3 (priority 30) under SCHED_FIFO on a single-core system. T3 is running and holds a mutex. T2 becomes ready and preempts T3 because T2 has higher priority?

Q12. In a program, Thread A and Thread B both attempt to lock two mutexes M1 and M2. Thread A locks M1 then M2; Thread B locks M2 then M1. What is the condition for deadlock?

💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: This is the classic dining philosophers / deadly embrace deadlock scenario. Deadlock occurs if Thread A locks M1, Thread B locks M2, and then each attempts to lock the other mutex. B.The new readers will be blocked to avoid writer starvation ✅
C.The writer will be allowed immediately
D.The system will deadlock
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Read-write locks typically prevent writer starvation by blocking new readers if a writer is waiting. This ensures that writers get a chance to acquire the lock. This is a common behavior to avoid writer starvation. The answer is B. This tests understanding of read-write lock semantics.

Q34. A multi-threaded program on a system with 4 cores uses 8 threads. The threads are compute-bound and the workload is evenly distributed. What is the maximum possible speedup?

A.8
B.4 ✅
C.16
D.2
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Amdahl's law and the practical limit: with 4 cores, the maximum speedup is 4 (if the workload is perfectly parallelizable and no overhead). With more threads than cores, speedup is still limited by the number of cores. So maximum speedup is 4. This tests the understanding that speedup is bounded by the number of cores, not threads.

Q35. A program has a memory leak because threads are created but not joined. Which of the following is the correct way to ensure resources are reclaimed without blocking the main thread indefinitely?

A.Call `pthread_detach` after creation ✅
B.Call `pthread_join` with a timeout
C.Use `pthread_cancel`
D.Call `pthread_exit` in the main thread
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: To avoid joining (which blocks), the thread can be detached using `pthread_detach(pthread_self())` or by creating it detached. This ensures that its resources are automatically reclaimed when it exits, without the need for another thread to join it. This is the correct approach. This tests the concept of detached threads.
