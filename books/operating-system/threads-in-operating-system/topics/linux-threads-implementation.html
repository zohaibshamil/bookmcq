Q1. A lightweight process (LWP) in Linux is best described as:

🔹 A. A user-level thread scheduled by the application
🔹 B. A kernel-level entity that serves as a scheduling context for user threads
🔹 C. A dedicated CPU core for thread execution
🔹 D. A memory region shared by all threads of a process

💡 Difficulty: hard | ✅ Correct: B

📖 Explanation:

An LWP is a kernel-schedulable entity that acts as a bridge between user-level threads and the kernel. It is not a user-level construct (A) nor a physical core (C). It provides the execution context that the kernel schedules, and multiple user threads can be multiplexed onto a smaller pool of LWPs. This design allows for efficient thread management while leveraging kernel scheduling capabilities.

Q2. Which of the following statements correctly differentiates the clone() system call from fork() in Linux?

🔹 A. clone() creates a new process while fork() creates a new thread
🔹 B. fork() copies the entire address space while clone() allows sharing of specific resources
🔹 C. clone() is used only for kernel threads whereas fork() is for user processes
🔹 D. fork() is implemented as a wrapper around clone() with all sharing flags disabled

💡 Difficulty: hard | ✅ Correct: D

📖 Explanation:

In modern Linux, fork() is indeed a library wrapper that calls clone() with flags that prevent resource sharing (like CLONE_FILES, CLONE_VM), creating a traditional process. Option B is partially true but incomplete and historically inaccurate; fork() originally copied the entire address space but now uses copy-on-write. clone() is versatile, used for both threads and processes, making C false. The correct answer highlights the implementation relationship.

Q3. Given a program with 4 user-level threads mapped to 2 LWPs on a dual-core system. What is the maximum level of parallelism that can be achieved?

🔹 A. 1 thread at a time
🔹 B. 2 threads simultaneously
🔹 C. 4 threads simultaneously
🔹 D. It depends on the thread scheduler

💡 Difficulty: easy | ✅ Correct: B

📖 Explanation:

This is a many-to-many model (N:M) with N=4 user threads and M=2 LWPs. The number of LWPs is the limiting factor for parallelism because each LWP represents a kernel-schedulable context. With only 2 LWPs, at most 2 threads can execute in parallel on a dual-core system. Option D is a distractor; while scheduling affects which threads run, the maximum parallelism is bounded by the number of LWPs, not the user scheduler.

Q4. A developer observes that creating 10,000 threads using pthread_create() on a standard Linux system causes performance degradation. What is the most likely primary bottleneck?

🔹 A. Kernel scheduler overhead from managing too many LWPs
🔹 B. Exhaustion of the process's virtual memory address space for stack allocation
🔹 C. CPU cache thrashing due to excessive context switching
🔹 D. Limited number of available file descriptors

💡 Difficulty: easy | ✅ Correct: B

📖 Explanation:

By default, each pthread gets a stack (typically 8 MB). 10,000 threads × 8 MB = 80 GB of virtual address space, which far exceeds the typical 2-3 GB user-space address limit on 32-bit systems and still poses significant pressure on 64-bit systems. While A and C contribute, the primary bottleneck is the address space exhaustion for stack allocation. This is a classic limitation of the 1:1 threading model used by NPTL.

Q5. An application using the older LinuxThreads implementation crashes when a thread exits. The developer finds that the process terminates instead of just the thread. What is the most likely cause?

🔹 A. A bug in the thread's exit handler
🔹 B. The LinuxThreads implementation used a manager thread and signals, leading to process termination on thread exit
🔹 C. The process was compiled without thread-safety flags
🔹 D. The hardware does not support thread-local storage

💡 Difficulty: medium | ✅ Correct: B

📖 Explanation:

The older LinuxThreads implementation used a signal-based manager thread to handle thread creation and cleanup. If the manager thread died or a thread exited in a certain way, it could result in the entire process receiving a SIGKILL or terminating unexpectedly. This was a major flaw that led to the development of NPTL. Options A, C, and D are less likely to cause the entire process to terminate in such a specific manner.

Q6. Which of the following graphs would best represent the relationship between the number of LWPs and the throughput of a CPU-bound application on a system with 8 physical cores?

🔹 A. Throughput increases linearly with LWPs up to 8, then plateaus
🔹 B. Throughput increases exponentially with LWPs
🔹 C. Throughput is inversely proportional to the number of LWPs
🔹 D. Throughput continues to increase linearly beyond 8 LWPs

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation:

For a CPU-bound application, throughput is limited by the number of physical cores (8). Adding more LWPs than cores provides no performance benefit as they cannot execute in parallel; they only introduce scheduling overhead. Thus, the graph shows a linear increase until 8, then a plateau. Option D is a common misconception that more threads always mean more speed. Options B and C are fundamentally incorrect models for this scenario.

Q7. A system has 4 CPU cores. An application uses the many-to-many threading model with 10 user threads and 3 LWPs. What is the maximum number of user threads that can be executing kernel code simultaneously?

🔹 A. 1
🔹 B. 3
🔹 C. 4
🔹 D. 10

💡 Difficulty: hard | ✅ Correct: B

📖 Explanation:

While 4 cores exist, the kernel can only schedule the 3 LWPs. Even if a user thread is in a system call, it is bound to an LWP. Therefore, at most 3 user threads can be executing kernel code (or any code) simultaneously. The number of cores (4) is a distractor; the LWP count is the limiting factor for simultaneous kernel-level execution in this model. This tests the understanding of the LWP as the scheduling entity.

Q8. Consider the following code snippet using clone(): clone(function, stack, CLONE_VM | CLONE_FILES | CLONE_SIGHAND, arg). This creates a new execution context that shares memory, file descriptors, and signal handlers with the parent. What is this context most accurately called?

🔹 A. A new process
🔹 B. A kernel thread
🔹 C. A user-level thread
🔹 D. A separate process with shared resources

💡 Difficulty: hard | ✅ Correct: C

📖 Explanation:

The combination of CLONE_VM, CLONE_FILES, and CLONE_SIGHAND creates an execution context that shares almost all resources with the parent, which is the definition of a POSIX thread (user-level thread) from the kernel's perspective. It is not a separate process (A, D) because it shares an address space. It is not a kernel thread (B) because it runs in user space, even though clone() is a system call.

Q9. A developer profiles an application and notices that 90% of the time is spent in the futex() system call. What is the most likely scenario?

🔹 A. The application is performing heavy file I/O
🔹 B. The application has high contention on a mutex used for synchronization
🔹 C. The application is creating and destroying many threads
🔹 D. The application is allocating large amounts of memory

💡 Difficulty: medium | ✅ Correct: B

📖 Explanation:

The futex() system call is the low-level mechanism for fast user-space mutexes in Linux. When a mutex is contended, threads must block and unblock using futex() calls in the kernel. High futex() usage directly indicates contention for a synchronization primitive. Options A, C, and D involve other system calls (read/write, clone, mmap) and are not the primary cause of futex() usage.

Q10. In the context of Linux threading, what is the primary purpose of the per-thread kernel stack?

🔹 A. To store the thread's local variables
🔹 B. To handle system calls and process signals while the thread is in kernel mode
🔹 C. To provide a separate memory area for heap allocations
🔹 D. To cache frequently accessed data

💡 Difficulty: hard | ✅ Correct: B

📖 Explanation:

Each thread has a kernel stack used only when executing in kernel mode (e.g., during system calls, interrupts, or signal handling). This is critical for isolation and security, as each thread's kernel stack contains sensitive data like register values and return addresses. Option A is incorrect because local variables are stored on the user-mode stack. Option C and D are incorrect functions.

Q11. An application uses a thread pool with a fixed number of worker threads equal to the number of CPU cores. The task queue uses a mutex and condition variable. If each task is CPU-bound and takes 10ms, what is the primary effect of increasing the number of worker threads beyond the number of cores?

🔹 A. Decreased throughput due to increased context switching overhead
🔹 B. Increased throughput due to better utilization of I/O wait time
🔹 C. No change in throughput as tasks are CPU-bound
🔹 D. The system will deadlock

💡 Difficulty: easy | ✅ Correct: A

📖 Explanation:

For CPU-bound tasks, the optimal number of threads is the number of cores. Adding more threads than cores introduces contention for the CPU and increases context switching overhead, which reduces overall throughput. Option B would be true for I/O-bound tasks. Option C is incorrect as overhead reduces throughput. Option D is not a guaranteed outcome. This tests understanding of Amdahl's law and threading overhead.

Q12. A student implements a producer-consumer queue using pthread mutexes and condition variables. The program sometimes runs correctly but occasionally hangs. The developer suspects a missed signal. Which of the following is the most robust fix for this scenario?

🔹 A. Replace the mutex with a spinlock
🔹 B. Add a timeout to the pthread_cond_wait() call
🔹 C. Use a pthread_cond_broadcast() instead of pthread_cond_signal()
🔹 D. Use a counting semaphore instead of a condition variable

💡 Difficulty: medium | ✅ Correct: C

📖 Explanation:

A missed signal occurs when a condition variable signal is sent before a thread is waiting on it. Using pthread_cond_broadcast() wakes all waiting threads, eliminating the risk of a signal being consumed by the wrong thread or missed entirely, though it can cause a 'thundering herd' problem. Option B adds a timeout, which masks the issue but doesn't fix the logic. Option A (spinlock) is for short critical sections and doesn't fix the signaling issue. Option D still requires careful signaling logic.

Q13. Given two systems: System A uses the NPTL (1:1 model) and System B uses a many-to-many model with 10 LWPs. Both have 4 CPU cores and run a heavily threaded I/O-bound application with 100 threads. Which system is likely to show better performance?

🔹 A. System A, because the kernel can schedule each thread optimally
🔹 B. System B, because it has more LWPs than cores
🔹 C. System A, because NPTL is the standard on Linux
🔹 D. System B, because it can handle more I/O without kernel intervention

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation:

NPTL's 1:1 model allows the kernel scheduler to make optimal decisions for each thread, as it has complete visibility. For I/O-bound tasks, having many threads is fine, and the kernel can efficiently block and unblock them. System B's 10 LWPs become a bottleneck: many user threads must be multiplexed, and when one blocks on I/O, its LWP is also blocked, reducing the number of available LWPs and thus parallelism. Option B is a distractor; more LWPs than cores is not beneficial. Option C is not a performance argument.

Q14. The 'thread-local storage' (TLS) feature in Linux relies on which hardware or architectural feature to provide efficient access?

🔹 A. A global system-wide hash table
🔹 B. The %fs or %gs segment registers on x86
🔹 C. A per-thread memory-mapped file
🔹 D. A dedicated cache line in the CPU

💡 Difficulty: easy | ✅ Correct: B

📖 Explanation:

On x86 architectures, the %fs and %gs segment registers are used to point to the thread's own data structure, allowing for fast access to thread-local variables without needing a system call or global lookup. This is a fundamental hardware feature leveraged by the kernel and libc. Option A would be too slow. Option C and D are not used for this purpose.

Q15. What is the primary reason the Linux kernel does not differentiate between a 'process' and a 'thread' at the scheduling level?

🔹 A. Both are represented by a task_struct structure
🔹 B. The scheduler does not care about resource sharing
🔹 C. Threads and processes are scheduled the same way in all operating systems
🔹 D. It would be too computationally expensive to differentiate

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation:

In Linux, both processes and threads are represented internally by the same data structure, struct task_struct. The scheduler operates on these structures, scheduling them based on their state and priority, regardless of whether they share memory with other tasks (threads) or not. This unified model simplifies the scheduler and is a core design principle of Linux. Option B is misleading; the scheduler does care about priority but not the distinction between process/thread for scheduling decisions.

Q16. A multithreaded server uses the epoll system call with the EPOLLONESHOT flag. A thread handles an event and then re-arms the file descriptor. What happens if the thread is preempted before re-arming the descriptor?

🔹 A. The descriptor is automatically re-armed after a timeout
🔹 B. The descriptor remains inactive until the thread re-arms it
🔹 C. The kernel re-arms the descriptor immediately upon preemption
🔹 D. The descriptor is permanently removed from the epoll set

💡 Difficulty: easy | ✅ Correct: B

📖 Explanation:

The EPOLLONESHOT flag ensures that a file descriptor is triggered for only one event. It is the responsibility of the user thread to re-arm it (using epoll_ctl with EPOLL_CTL_MOD). If the thread is preempted, the descriptor will not be triggered again until it is explicitly re-armed, which can lead to missed events or starvation. Option A is false, the kernel does not re-arm. Option D is false; it remains in the set but inactive.

Q17. A developer is debugging a crash in a multithreaded application. The crash occurs in a function that accesses a global variable. The developer sees that the variable is not declared volatile. What is the most likely reason for the crash if the code is optimized?

🔹 A. The compiler optimized away the global variable entirely
🔹 B. The compiler cached the global variable's value in a register, leading to stale data being read by other threads
🔹 C. The global variable was placed in a read-only section of memory
🔹 D. The compiler unrolled the loop incorrectly

💡 Difficulty: medium | ✅ Correct: B

📖 Explanation:

Without the volatile keyword, the compiler may optimize memory accesses by caching a variable's value in a register. In a multithreaded environment, another thread might update the variable, but the current thread continues to use the stale cached value, leading to inconsistent state and potentially a crash. Option A is too extreme; the compiler doesn't remove used variables. Option C is not a typical compiler optimization. Option D is unrelated.

Q18. Consider the following graph: X-axis = Number of LWPs, Y-axis = Context switch rate. The graph shows a linear increase until 8 LWPs, then a rapid exponential increase. This graph most likely represents what kind of application?

🔹 A. A CPU-bound application on an 8-core system
🔹 B. An I/O-bound application with high disk I/O
🔹 C. A memory-bound application with large working set
🔹 D. A network-bound application with many connections

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation:

The graph pattern is classic for a CPU-bound application. Up to the number of cores (8), each LWP has a CPU to run on, and context switches are minimal. Beyond 8, threads compete for CPU time, causing the scheduler to preempt and switch contexts frequently, leading to an exponential increase in the context switch rate as contention increases. Options B, C, and D would have different patterns influenced by I/O completion or memory latency rather than just LWP count.

Q19. A programmer wants to create a new thread but ensure it has a minimal stack size to save memory. Which of the following approaches is correct and safest?

🔹 A. Call malloc() to allocate a small stack and pass it to clone()
🔹 B. Use pthread_attr_setstacksize() with a very small value, e.g., 1KB
🔹 C. Use pthread_attr_setstack() with a stack allocated on the heap
🔹 D. Use the default stack size; the kernel will optimize it

💡 Difficulty: easy | ✅ Correct: A

📖 Explanation:

Creating a thread with clone() allows the programmer to directly pass a memory region for the stack. This is the intended way to provide a custom stack. Option B is unsafe because pthreads requires a minimum stack size (often 16KB) for its own bookkeeping; setting it too low will cause a crash. Option C is similar to A but using the pthread API. Option D doesn't save memory. The safest low-level way is to allocate the stack manually and pass it to clone() with correct alignment.

Q20. What is the fundamental difference in signal handling between the original LinuxThreads and the modern NPTL implementation?

🔹 A. LinuxThreads used a single signal handler for all threads; NPTL allows per-thread handlers
🔹 B. LinuxThreads sent signals to the entire process; NPTL targets a specific thread
🔹 C. LinuxThreads ignored all signals; NPTL implements full POSIX signal handling
🔹 D. Both implementations are identical in signal handling

💡 Difficulty: hard | ✅ Correct: B

📖 Explanation:

This is a key differentiator. LinuxThreads used a SIGUSR1/SIGUSR2-based manager thread and had broken signal semantics; signals were often delivered to the process, not the specific thread. NPTL correctly implements POSIX requirements, allowing signals to be delivered to a specific thread or the entire process as per the signal mask. Option A is incorrect because the concept of per-thread handlers is not the main differentiator; the delivery target is.

Q21. In a system using the one-to-one threading model (NPTL), which of the following is a direct consequence for thread creation and management?

🔹 A. Creating a thread is a very fast, user-space operation
🔹 B. Thread creation requires a system call (clone)
🔹 C. Thread synchronization is managed entirely in user space
🔹 D. The process cannot have more threads than the number of CPU cores

💡 Difficulty: easy | ✅ Correct: B

📖 Explanation:

In the 1:1 model, each user thread is backed by a kernel thread (LWP). Creating a new thread thus requires a kernel intervention via the clone() system call to create the corresponding kernel task. Option A describes the many-to-one model. Option C is false; synchronization often uses futexes which may involve the kernel for blocking. Option D is false; the system can have many more threads than cores.

Q22. A developer notices that their multithreaded application runs perfectly on a 4-core system but slows down significantly on an 8-core system. The application uses a global mutex heavily. What is the most likely explanation?

🔹 A. The 8-core system has slower CPU cores
🔹 B. The mutex contention increases, and the overhead of futex() system calls scales poorly with more cores
🔹 C. The memory bandwidth is lower on the 8-core system
🔹 D. The application is using too many threads, causing a deadlock on the 8-core system

💡 Difficulty: medium | ✅ Correct: B

📖 Explanation:

With more cores, more threads can run concurrently, leading to higher contention on the global mutex. This results in more frequent blocking and unblocking via futex() system calls. The overhead of these system calls and the resulting cache coherence traffic can cause performance to degrade, not improve, as contention increases. Option A is unlikely to be the reason for significant slowdown. Option C is a distractor. Option D is incorrect as more cores don't cause deadlocks; they expose contention.

Q23. Which of the following scenarios best describes a situation where using a spinlock would be more appropriate than a mutex in a Linux multithreaded program?

🔹 A. A long-running I/O operation in a single-threaded application
🔹 B. A short critical section in a real-time thread with a high priority
🔹 C. A critical section that involves blocking on a network socket
🔹 D. Synchronizing access to a file between multiple processes

💡 Difficulty: easy | ✅ Correct: B

📖 Explanation:

Spinlocks are best used for very short critical sections (a few instructions) where the cost of sleeping and waking (mutex) is higher than the cost of spinning. In a real-time thread with high priority, being preempted is undesirable, so spinning until the lock is available is often preferred for low-latency requirements. Option A has no concurrency. Options C and D involve blocking operations or inter-process synchronization, where mutexes or other primitives are better suited.

Q24. A program uses the clone() system call with the flag CLONE_THREAD but not CLONE_VM. What is the resulting execution context?

🔹 A. A thread that shares memory with the parent
🔹 B. A thread that has its own memory space but is part of the same thread group
🔹 C. A separate process
🔹 D. An invalid combination of flags

💡 Difficulty: hard | ✅ Correct: B

📖 Explanation:

CLONE_THREAD creates a new execution context that shares the same thread group ID (TGID) as the caller, making it appear as a thread to the process model. Without CLONE_VM, it does not share the address space, meaning it has its own memory space. However, because it's in the same thread group, it's not considered a separate process (A, C). The combination is valid (it creates a 'thread' with a private memory map).

Q25. The Linux kernel scheduler uses a 'fair' scheduling policy (CFS). For multithreaded applications, how does CFS treat threads belonging to the same process?

🔹 A. All threads are grouped together and receive a single scheduling quantum
🔹 B. Each thread is a separate task and is scheduled independently with its own vruntime
🔹 C. The main thread receives priority over all worker threads
🔹 D. Threads are scheduled together in a round-robin fashion

💡 Difficulty: easy | ✅ Correct: B

📖 Explanation:

CFS schedules individual tasks, and each thread is represented by a task_struct. Each has its own virtual runtime (vruntime) and is placed in the red-black tree independently. There is no grouping by process for scheduling purposes (unless using the 'autogroup' feature, but that is not the default for all scenarios). Options A, C, and D are incorrect descriptions of CFS behavior.

Q26. A developer is using strace to trace a multithreaded application. They see many calls to futex() with the FUTEX_WAIT operation. What does this indicate?

🔹 A. The application is creating new threads
🔹 B. A thread is trying to acquire a contended lock and is going to sleep
🔹 C. The application is destroying threads
🔹 D. The application is performing a memory allocation

💡 Difficulty: easy | ✅ Correct: B

📖 Explanation:

FUTEX_WAIT is the operation used by pthread_mutex_lock when the lock is already held by another thread. The calling thread is being put to sleep by the kernel until the lock is released (a FUTEX_WAKE). Option A would involve clone(). Option C involves termination. Option D involves mmap() or sbrk(). This is a direct application of understanding the futex system call.

Q27. Which of the following statements about thread-local storage (TLS) and process-wide global variables is true in Linux?

🔹 A. TLS variables are stored on the heap for each thread
🔹 B. Global variables are faster to access than TLS variables
🔹 C. TLS variables require a system call to access
🔹 D. TLS variables provide isolation, while global variables are shared, potentially leading to race conditions

💡 Difficulty: hard | ✅ Correct: D

📖 Explanation:

This is the fundamental trade-off. TLS variables are isolated to each thread (using the segment registers), preventing race conditions and data corruption. Global variables are shared and require synchronization. Option A is incorrect; TLS is not on the heap. Option B is incorrect; TLS access via segment registers is just as fast, if not faster. Option C is false; it's a hardware-optimized access.

Q28. A multithreaded application running on Linux crashes intermittently with a 'segmentation fault' inside a library function. The developer examines the core dump and sees that the stack pointer is corrupted. What is the most plausible root cause?

🔹 A. A stack overflow in the thread due to a small default stack size
🔹 B. An integer overflow in a counter variable
🔹 C. The application is using a stale file descriptor
🔹 D. The main thread terminated, causing all child threads to crash

💡 Difficulty: medium | ✅ Correct: A

📖 Explanation:

Stack corruption is a classic symptom of a stack overflow. The default thread stack size (8MB) is usually sufficient, but if a thread allocates large arrays on the stack or has deep recursion, it can overflow, corrupting the stack frame and leading to a segmentation fault. Option B would not directly corrupt the stack pointer. Option C and D have different symptoms (e.g., EBADF or a hang).

Q29. Consider two scheduling policies for threads: SCHED_OTHER (default CFS) and SCHED_RR (round-robin real-time). A system has a real-time thread and many normal threads. If the real-time thread never blocks, what happens to the normal threads?

🔹 A. They are scheduled in a round-robin fashion with the real-time thread
🔹 B. The normal threads will starve and get very little CPU time
🔹 C. The system will panic
🔹 D. The real-time thread will be preempted after its time quantum

💡 Difficulty: hard | ✅ Correct: B

📖 Explanation:

In Linux, real-time scheduling policies (SCHED_FIFO and SCHED_RR) have higher priority than the normal SCHED_OTHER policy. If a real-time thread is runnable, it will always be scheduled before any normal thread. If it never blocks, it will monopolize the CPU, causing normal threads to starve. Option A is incorrect because they are not scheduled on equal footing. Option D is incorrect; SCHED_RR real-time threads have a quantum but are still not preempted by SCHED_OTHER threads.

Q30. A developer wants to write a program that creates a new process that is a copy of the parent but shares the file descriptor table. Which flag(s) should be used with clone()?

🔹 A. CLONE_FS only
🔹 B. CLONE_FILES | CLONE_VM
🔹 C. CLONE_FILES
🔹 D. CLONE_PARENT | CLONE_FILES

💡 Difficulty: easy | ✅ Correct: C

📖 Explanation:

To create a new process that shares the file descriptor table with the parent, the CLONE_FILES flag is used. CLONE_VM would share the address space, creating a thread, not a process. CLONE_FS shares filesystem information (like cwd). CLONE_PARENT sets the parent PID. The correct answer is specifically the flag that controls file descriptor sharing.

Q31. In the many-to-one threading model (historical or used in some other systems), a thread performing a blocking system call will cause what effect?

🔹 A. The thread blocks, but other threads can continue
🔹 B. The entire process blocks, including all threads
🔹 C. The system call returns EINTR and the thread continues
🔹 D. The kernel moves the thread to another CPU

💡 Difficulty: hard | ✅ Correct: B

📖 Explanation:

In the many-to-one model, all user-level threads are scheduled on a single kernel thread (LWP). When one thread makes a blocking system call, the entire kernel thread blocks, which means no other user-level thread can run, effectively blocking the whole process. This is a major drawback of the many-to-one model and is why it is not used in modern Linux. Option A describes the 1:1 or many-to-many models.

Q32. An application using pthreads creates a high-priority thread that processes critical events. However, the thread often misses its deadline. Upon investigation, the developer finds that the thread's priority was set using pthread_setschedparam with SCHED_OTHER. What is the primary reason for the missed deadlines?

🔹 A. The thread priority is not being set correctly due to a bug in the API
🔹 B. SCHED_OTHER does not provide real-time guarantees; the priority is only a hint
🔹 C. The system has too few cores
🔹 D. The thread is being blocked by I/O

💡 Difficulty: medium | ✅ Correct: B

📖 Explanation:

SCHED_OTHER is the default CFS policy. While it supports 'nice' values to influence scheduling, it does not provide deterministic, real-time scheduling guarantees. If a thread misses deadlines, using SCHED_OTHER is the likely cause. The developer should use SCHED_FIFO or SCHED_RR. Option A is incorrect; the API call is successful but ineffective for real-time. Options C and D are possible but secondary; the primary issue is the scheduling policy.

Q33. A system is running a multithreaded database application. Performance monitoring shows a high amount of time spent in the kernel due to 'TLB shootdown' interrupts. What is the most likely cause?

🔹 A. High contention on a spinlock
🔹 B. Frequent creation and destruction of threads
🔹 C. The application is using memory-mapped files
🔹 D. The application is creating many threads that share the same address space and are migrated across cores

💡 Difficulty: hard | ✅ Correct: D

📖 Explanation:

TLB shootdown is a mechanism to invalidate Translation Lookaside Buffer entries across multiple CPUs when a process's page tables are modified or when a thread using the same memory space is migrated to a different core. With many threads sharing the same address space, migrating them frequently causes a high rate of TLB shootdowns, which is an expensive inter-processor interrupt. Option A (spinlocks) causes CPU spinning, not TLB shootdowns. Option B and C are less directly related.

Q34. What is the role of the pthread_cleanup_push() and pthread_cleanup_pop() functions in the context of Linux threads?

🔹 A. To allocate memory for thread-local storage
🔹 B. To set and get the thread's scheduling policy
🔹 C. To register cancellation handlers that are called when a thread is cancelled
🔹 D. To lock and unlock a mutex with a timeout

💡 Difficulty: easy | ✅ Correct: C

📖 Explanation:

These functions are used to manage thread cancellation. They allow a thread to 'push' a cleanup handler onto a stack. If the thread is cancelled (e.g., via pthread_cancel), the handlers are popped and executed in reverse order to release resources (like mutexes or free memory) before the thread exits. Options A, B, and D describe other pthread functions (pthread_getspecific, pthread_setschedparam, pthread_mutex_timedlock).

Q35. A developer decides to use a global variable for synchronization and uses __sync_synchronize() built-ins. Another developer argues that this is not sufficient for thread safety. What is the strongest argument against using only memory barriers for synchronization?

🔹 A. Memory barriers are too slow
🔹 B. Memory barriers only order memory operations; they do not provide mutual exclusion
🔹 C. Memory barriers are not supported on all Linux architectures
🔹 D. Memory barriers only work on variables in the cache

💡 Difficulty: hard | ✅ Correct: B

📖 Explanation:

Memory barriers (like __sync_synchronize) enforce ordering of memory accesses but do not provide the atomicity required for mutual exclusion. Two threads could still race to modify the global variable, leading to a lost update or corrupted state. A mutex provides both ordering and atomicity. Option A is false; barriers are generally fast. Option C is false; they are widely supported. Option D is misleading.

Q36. A multithreaded application has a performance bottleneck in the memory allocator. The developer notices that many threads are calling malloc() and free() frequently, leading to high contention on the process heap lock. Which of the following is the most effective solution to reduce this contention?

🔹 A. Increase the number of CPU cores
🔹 B. Use thread-local caching allocators like tcmalloc or jemalloc
🔹 C. Replace malloc() with mmap() for all allocations
🔹 D. Use a spinlock instead of a mutex for the heap lock

💡 Difficulty: easy | ✅ Correct: B

📖 Explanation:

Thread-local caching allocators (e.g., tcmalloc, jemalloc) reduce contention by maintaining per-thread caches of memory. Threads can allocate and free memory from their own cache without acquiring the global heap lock, drastically reducing contention. Option A is not a solution to contention on a single lock; it can make it worse. Option C is not practical for all allocations. Option D would cause more spinning and worse performance.
