What is Java Threads in operating system?

Definition:
Java Threads are objects of class \( \texttt{Thread} \) managed by the JVM, historically using green threads but now typically mapped one-to-one to OS threads via native libraries for true parallelism.

Example:
Extending \( \texttt{Thread} \) or implementing \( \texttt{Runnable} \) and calling \( \texttt{start()} \) initiates concurrent execution.

Reason:
JVM abstraction allows platform-independent threading while leveraging underlying OS capabilities, balancing portability with performance on modern multicore systems.

Q1. A Java program creates 5 user threads. The underlying operating system uses a 1:1 threading model. If the program is running on a quad-core processor and all threads are compute-bound with no I/O, what is the maximum number of threads that can execute in parallel at any single instant?

A.1
B.4 ✅
C.5
D.It depends on the thread scheduler
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: In a 1:1 threading model, each Java thread is mapped to a native OS thread. The OS scheduler determines which threads get CPU time. On a quad-core machine, a maximum of 4 threads can execute truly in parallel (simultaneously) because there are only 4 physical cores. While 5 threads can be scheduled, only 4 can run at the exact same time; the 5th will be context-switched. Option A (1) is incorrect as multi-core systems allow parallelism. Option C (5) is a common misconception that the number of threads equals the degree of parallelism. Option D is partially true but the maximum is hardware-limited.

Q2. Given the following code snippet: `Thread t = new Thread(() -> { while(true) { } }); t.setDaemon(true); t.start(); System.out.println("Main ends");`. What is the most accurate prediction of the program's behavior?

A.The program will print "Main ends" and then terminate immediately. ✅
B.The program will print "Main ends" and then hang indefinitely.
C.The program will print "Main ends", but the JVM will exit only after the daemon thread finishes its loop.
D.The program will not compile because the run method is not overridden correctly.
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: A daemon thread is a background thread that does not prevent the JVM from exiting. When the main thread (which is a non-daemon user thread) finishes executing `System.out.println("Main ends")`, the JVM checks if any non-daemon threads are running. Since the only other thread is a daemon, the JVM will terminate abruptly, killing the daemon thread. Option B describes the behavior of a user thread, not a daemon. Option C is the opposite of how daemon threads work. Option D is incorrect because the lambda expression implements the `Runnable` functional interface correctly.

Q3. A Java application uses a thread pool with 4 threads to process 20 CPU-intensive tasks. Each task takes 100ms to complete on a single core. Assuming a 1:1 threading model and an ideal OS scheduler with no overhead, what is the minimum total time required to process all 20 tasks on a dual-core machine?

A.500 ms ✅
B.1000 ms
C.2000 ms
D.100 ms
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: With a dual-core machine, only 2 threads can execute in parallel. The thread pool has 4 threads, but they compete for the 2 cores. The OS schedules these 4 threads over time. To complete 20 tasks, each requiring 100ms of CPU time, the total CPU time required is 20 * 100ms = 2000ms. With 2 cores, the work can be divided, so the wall-clock time is 2000ms / 2 = 1000ms. However, the thread pool has only 4 threads. In the best case, the scheduler runs 2 threads concurrently, each processing a task. After 100ms, those 2 tasks are done, and the next 2 tasks are assigned to the threads. This process repeats, processing 2 tasks every 100ms. To process 20 tasks, it takes (20/2) * 100ms = 1000ms. Option C (2000ms) is the total CPU time on one core. Option D (100ms) is the time for one task. Option A (500ms) is incorrect as it assumes 4 threads running in parallel, which is impossible on a dual-core system.

Q4. A student writes a program to increment a shared integer variable `count` using 10 threads, each incrementing it 1000 times. The code uses `synchronized(this)` block inside the `run()` method of a class that implements `Runnable`. However, the final value of `count` is still not consistently 10000. What is the most likely cause of this error?

A.The threads are not started simultaneously.
B.The `synchronized` block is locking on `this`, but each thread has its own `Runnable` instance. ✅
C.The `count` variable is not declared as `volatile`.
D.The OS scheduler is preempting the threads too often.
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: The `synchronized(this)` block locks on the current object instance. If each thread is created with a new instance of the `Runnable` class (e.g., `new Thread(new MyRunnable())`), then each thread locks on a different object. Therefore, the lock is not shared, and the critical section is not mutually exclusive, leading to race conditions. The correct approach is to use a shared lock object or synchronize on a static object. Option A (simultaneous start) is a common misconception; even if not simultaneous, the lock would prevent the race if it were shared. Option C (`volatile`) prevents visibility issues but does not solve the atomicity problem of `count++`. Option D (preemption) is the nature of threading but is not the primary cause here if the locking was implemented correctly.

Q6. Which of the following scenarios will ALWAYS lead to a deadlock in a Java program that uses multiple synchronized methods?

A.Thread A locks object X and then tries to lock object Y, while Thread B locks object Y and then tries to lock object X.
B.Thread A locks object X and then tries to lock object Y, while Thread B locks object X and then tries to lock object Z.
C.Thread A locks object X and enters a wait state, while Thread B locks object Y and tries to lock object X.
D.None of the above scenarios guarantee a deadlock. ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: Deadlock requires a cyclic wait condition. Option A is the classic deadlock scenario, but it does not guarantee a deadlock due to timing. Thread A must acquire X and then attempt Y, while Thread B acquires Y and then attempts X. If the OS scheduler runs A to completion before B starts, no deadlock occurs. Deadlock is a race condition that happens only when the interleaving is exactly right. Option B cannot deadlock because both threads try to lock X first; the second thread will block until X is released, preventing a cycle. Option C describes a scenario where Thread A might be waiting for a notification, but if it holds the lock on X, Thread B cannot lock X, so it will block, but this isn't a cyclic wait unless Y is involved. Thus, option D is the most accurate answer, highlighting that deadlock is a timing-dependent problem, not a guarantee.

Q7. An application uses `ExecutorService` with a fixed thread pool of 2 threads. It submits 10 tasks, each of which prints its thread's name and then sleeps for 1 second. How many distinct thread names will be printed throughout the execution?

A.10
B.2 ✅
C.Up to 2, but it could be more if threads are recreated.
D.1
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: A `FixedThreadPool` of size 2 reuses the same 2 threads for all submitted tasks. The threads are created once and are not destroyed after each task. Therefore, across all 10 tasks, only 2 distinct threads (and thus 2 distinct thread names) will be used. Option A (10) is a common misconception, assuming a new thread is created for each task. Q8. Consider two threads, T1 and T2, sharing a variable `int x = 0`. T1 executes `x = 5; System.out.println(x);` and T2 executes `System.out.println(x); x = 10;`. Without synchronization, which of the following outputs is NOT possible?

A.T1 prints 5, T2 prints 5
B.T1 prints 5, T2 prints 10
C.T1 prints 0, T2 prints 10
D.T1 prints 0, T2 prints 0 ✅
💡 Difficulty: easy | ✅ Correct: D

📖 Explanation: This problem tests understanding of interleaving and memory visibility. Let's trace possible interleavings. For T1 to print 0, its read of `x` must happen before T1's write of `x=5`, and after the initial `x=0`. If T1 prints 0, then T1's read happened before T1's write. Now, T2 could have printed 0 (if its read happened before T1's write) or it could print 5 (if its read happened after T1's write). It cannot print 10 because T2's print happens before its write of `x=10`. The only impossible output is T1 printing 0 and T2 printing 10. Option A is possible if T1 runs to completion first. Option B is possible if T1 sets x=5, then T2 reads 5, prints it, then sets x=10. Option C is possible if T2 prints 0, sets x=10, then T1 sets x=5 and prints 5. This is a classic example of analyzing thread interleaving.

Q9. In a Java program, a thread is in the `BLOCKED` state. Which of the following events will cause it to transition to the `RUNNABLE` state?

A.The thread's `sleep()` time expires.
B.The thread's `wait()` method is called.
C.The thread's `notify()` method is called.
D.The lock it is waiting on becomes available. ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: A thread enters the `BLOCKED` state when it attempts to enter a `synchronized` block or method but the lock is held by another thread. The thread remains blocked until the lock is released by the owning thread. Once the lock is available, the thread transitions back to the `RUNNABLE` state and can compete for the CPU. Option A (sleep expires) transitions from `TIMED_WAITING` to `RUNNABLE`. Option B (`wait()`) transitions to `WAITING`. Option C (`notify()`) transitions a thread from `WAITING` to `BLOCKED` (to reacquire the lock) or to `RUNNABLE` in some cases, but the direct transition from `BLOCKED` to `RUNNABLE` specifically happens when the lock is released.

Q10. A developer uses `Thread.yield()` to improve performance. Which statement accurately describes its effect on thread scheduling in a modern OS with a preemptive scheduler?

A.It guarantees that the current thread will be paused for a fixed time slice.

C.It forces the current thread to move to the `WAITING` state.
D.It prevents the current thread from being context-switched.
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: `Thread.yield()` is a hint to the scheduler that the current thread is willing to give up its current use of the CPU. The scheduler may choose to honor this hint and select another runnable thread, or it may ignore it, especially in a preemptive scheduler that is already managing time slices efficiently. Option A is incorrect because `yield()` does not involve a fixed time; it simply returns to the runnable state immediately. Option C is incorrect; it does not put the thread into a waiting state; it remains runnable. Option D is the opposite of its purpose. This question highlights the distinction between a hint and a guarantee in OS-level threading.

Q11. A Java program has 3 threads: Main, T1, and T2. T1 has priority 10 (MAX_PRIORITY) and T2 has priority 1 (MIN_PRIORITY). They are all runnable on a single-core system. Assuming a standard OS scheduler, which statement is most accurate?

A.T1 will always run before T2.
B.T2 will never get CPU time.

D.The scheduler will ignore the priorities and use a round-robin scheme.
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: Thread priorities are a hint to the OS scheduler. Higher priority threads are given preference for CPU time. However, modern schedulers implement fairness to prevent starvation of lower-priority threads (priority inversion is a related issue). On a single-core system, T1 will likely get a larger share of the CPU, but T2 will still be scheduled. Option A is too strong; T2 can run when T1 is blocked or in some scheduling slots. Option B is starvation, which is prevented. Option D is not entirely true; priorities do influence the scheduler, though they are not absolute. This question tests the nuance between 'preference' and 'guarantee'.

📖 Explanation: The primary issue with using a non-thread-safe collection like `HashMap` in a multi-threaded environment is not just visibility (`volatile` would help with that) but structural corruption. If two threads simultaneously modify the `HashMap` and cause a resize or create a cycle in the internal node chains, subsequent `get()` operations can traverse corrupted data structures, leading to infinite loops or `NullPointerException`. Option B is a partial issue but not the cause of a crash; it leads to stale data. Option C is unrelated. Q13. A `ReentrantLock` with a fairness policy set to `true` is used in a program. Four threads are blocked on the lock. When the lock is released, which thread gets the lock?

This reduces starvation but introduces overhead. The OS scheduler decides which thread gets CPU time, but the lock itself decides which thread is granted ownership when it becomes free. 📖 Explanation: The JMM defines a 'happens-before' order for operations. For a `volatile` variable, a write to the variable happens-before any subsequent read of the same variable. Q17. A program uses a `Semaphore` of capacity 1. Thread A calls `semaphore.acquire()`, and Thread B calls `semaphore.acquire()` a moment later. Thread B blocks. Thread A then calls `semaphore.release()`. What state does Thread B transition to after Thread A calls `release()`?

A.Thread B moves to `RUNNABLE` and is guaranteed to acquire the semaphore immediately.

D.Thread B moves to `WAITING`.
💡 Difficulty: easy | ✅ Correct: B

📖 Explanation: A `Semaphore` of capacity 1 acts as a mutex. When Thread A releases the semaphore, the OS scheduler wakes up Thread B, moving it from `BLOCKED` (or `WAITING`) to `RUNNABLE`. However, Thread B must compete with other runnable threads for the CPU. It is not guaranteed to run immediately; it becomes eligible for scheduling. Option A is incorrect because the OS decides which thread gets CPU time. Option C is incorrect because the `release` operation unblocks a waiting thread. Option D is incorrect because a thread waiting on a `Semaphore` is typically in a `WAITING` state, but after `release`, it transitions to `RUNNABLE`. The exact state is `RUNNABLE` after the OS marks it as such.

Q19. Which of the following correctly describes the `Thread.interrupt()` behavior on a thread that is currently blocked on a `synchronized` method?

A.The thread will immediately throw an `InterruptedException` and leave the blocked state.

Q20. A `Phaser` is used to synchronize 3 threads. Each thread calls `phaser.arriveAndAwaitAdvance()`. After all 3 have arrived, the phaser advances. What happens if one of the threads calls `phaser.arriveAndDeregister()` instead of `arriveAndAwaitAdvance()`?

A.The phaser will wait indefinitely because the registered party count is now 2, but it expects 3 arrivals.
B.The phaser advances when the remaining 2 threads arrive, as the deregistering party is no longer counted. ✅
C.The phaser throws an exception because a party cannot deregister mid-phase.
D.The deregistering thread is blocked until the other two arrive.
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: `arriveAndDeregister()` decrements the number of registered parties by 1 and indicates that this party has arrived at the barrier. The phaser advances when the number of arrived parties equals the current number of registered parties. In this case, the 3rd thread deregisters, reducing the registered count from 3 to 2. The phaser will then advance when the other two threads arrive, as the condition (arrived == registered) is met. Option A is incorrect because the phaser no longer expects the deregistered thread. Option C is incorrect; deregistration is allowed. Option D is incorrect; the thread proceeds without blocking. This question tests understanding of dynamic party management in `Phaser`.

Q21. Consider the following sequence of operations on a `ReadWriteLock`: Thread A acquires a read lock. Thread B attempts to acquire a write lock and blocks. Thread C attempts to acquire a read lock. If the lock is set to be fair, what happens to Thread C?

💡 Difficulty: easy | ✅ Correct: B

📖 Explanation: In a fair `ReadWriteLock`, the order of lock acquisition is roughly in the order of requests. This question tests the trade-off between fairness and throughput in read-write locks.

Q22. A multithreaded Java program is running on a system with a single CPU. Thread T1 has a priority of 5, T2 has priority 1, and T3 has priority 10. T1 is currently running. T2 and T3 are runnable. B.Cooperative scheduling
C.Time-sharing scheduling
D.Round-robin scheduling
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: In preemptive scheduling, the operating system can interrupt a currently running thread (even if it hasn't voluntarily yielded) and switch to another thread. In this case, T1 was running and was preempted by T3 due to an interrupt. The fact that the OS scheduler selected T3 based on priority is a characteristic of preemptive scheduling. This question is a direct recall of scheduling types.

Q24. A developer runs a Java application with 10 threads on a 2-core machine. The application uses a `synchronized` block extensively. The developer observes that CPU utilization is low, and threads are frequently in the `BLOCKED` state. Which approach is MOST likely to improve performance?

Option C would worsen the problem. This question tests performance analysis and tuning.

Q25. In the Java Memory Model, which of the following is NOT guaranteed by the `synchronized` keyword?

A.Mutual exclusion
B.Visibility of changes to other threads
C.Atomicity of a block of code
D.Prevention of thread reordering of instructions within the synchronized block ✅
💡 Difficulty: medium | ✅ Correct: D

📖 Explanation: The `synchronized` keyword provides mutual exclusion (only one thread can enter the block), visibility (changes are flushed to main memory before the lock is released), and atomicity (the code block is executed as one unit). However, it does not prevent the compiler or CPU from reordering instructions inside the block, as long as the reordering doesn't violate the semantics of the lock. The JMM only ensures that the actions within the block appear to happen in a certain order from the perspective of other threads (due to the lock/unlock operations). Option D is not guaranteed; reordering inside the critical section is allowed. This is a subtle distinction often confused by developers.

Q26. The graph below shows the number of context switches per second as a function of the number of threads in a Java application running on a 4-core system. The application performs a mix of I/O and CPU work. The graph shows an increasing trend, then a peak, and then a decline. What is the MOST likely reason for the decline after the peak?

A.The threads are all blocked, so the OS stops scheduling them.

💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: As the number of threads increases, context-switch overhead increases due to more competition for CPU cores. Eventually, the system reaches a point where the overhead of context switching (saving/restoring thread state) dominates, and the OS scheduler may actually reduce the rate of context switches or the application's progress stalls. The graph likely shows that after a certain point, the system is thrashing, and the context-switch rate may plateau or decline because the CPU is so busy with overhead that it cannot even perform the context switches as frequently. Option A is possible but less likely; if all threads are blocked, context switches would drop to near zero. Option B is too absolute. Option D is incorrect; garbage collection doesn't reduce context switches in this manner. This question requires interpreting a performance graph.

Q27. Which of the following statements is true about `ThreadLocal` in a web application running on a multi-threaded servlet container?

A.`ThreadLocal` variables are shared among all requests.
B.`ThreadLocal` variables provide a way to store per-thread data, but they must be cleaned up after the request to avoid memory leaks. ✅
C.`ThreadLocal` variables are automatically garbage collected when the thread finishes.
D.`ThreadLocal` variables are thread-safe for all operations.
💡 Difficulty: easy | ✅ Correct: B

📖 Explanation: `ThreadLocal` provides a separate copy of the variable for each thread. In a web application, the container typically uses a thread pool to handle requests. If a servlet stores an object in a `ThreadLocal` without removing it after the request, that object may be referenced by the thread for its entire lifetime in the pool, leading to a memory leak. Option A is incorrect; they are per-thread. Option C is true only if the thread dies, but threads in a pool are reused and never die. Option D is not accurate; `ThreadLocal` doesn't make the object itself thread-safe, just provides isolated storage. This is a critical real-world pitfall.

Q28. A `CyclicBarrier` is initialized with 3 parties. Thread A and Thread B arrive at the barrier. Thread C arrives 10 seconds later. After Thread C arrives, which of the following is true?

A.All three threads are released at the same time, and then the barrier's action runs.
B.The barrier's action runs first, and then all three threads are released. ✅
C.Thread C is not released because the barrier has already timed out.
D.Thread A and Thread B are released immediately, and Thread C is blocked.
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: A `CyclicBarrier` is designed to wait until a fixed number of parties have arrived. When the last party arrives, the barrier's action (if any) is executed, and then all threads are released simultaneously. The action is executed by the last arriving thread before it returns. Option A has the order reversed. Option C is incorrect unless a timeout was specified. Option D is the behavior of a `CountDownLatch`, not a barrier. This question tests the precise operational semantics of `CyclicBarrier`.

Q29. A program uses `AtomicInteger` for a counter. The counter is incremented by 100 threads, each performing the increment 1000 times. The final result is consistently 100,000. However, the performance is poor. What is the primary reason for the poor performance?

A.`AtomicInteger` uses `synchronized` internally, causing threads to block.

C.The `volatile` keyword used in `AtomicInteger` causes memory stalls.
D.The threads are not properly started, causing overhead.
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: `AtomicInteger` uses CAS operations, which are hardware-level atomic operations. Under high contention (many threads trying to update the same variable), many threads will fail their CAS attempt and retry in a loop, spinning. This spinning wastes CPU cycles, leading to poor performance. Option A is false; it does not use `synchronized`. Option C is false; `volatile` doesn't cause stalls in the way described. Option D is a poor explanation. This question requires understanding the implementation of atomic classes and their performance trade-offs.

Q30. A developer implements a thread-safe counter using `volatile int count`. Two threads increment the counter 1000 times each. What is the range of possible final values?

A.Always 2000
B.Between 1000 and 2000 ✅
C.Between 0 and 2000
D.Always 1000
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: The `volatile` keyword ensures visibility but not atomicity. The `count++` operation is a read-modify-write sequence. If two threads interleave, increments can be lost. If there is no interleaving, the result is 2000. If increments are lost, the result is less than 2000. It cannot be less than 1000 because each thread increments 1000 times, and even if all increments are lost from one thread, the other completes 1000 increments, so the minimum is 1000. Option A is the result with proper synchronization. Option C is too broad. Option D is incorrect. This question tests the combined effect of visibility and atomicity.

Q31. A `CountDownLatch` is initialized to 2. Thread T1 calls `latch.countDown()`, and Thread T2 calls `latch.await()`. Which of the following is true?

Q32. A `ReentrantLock` is used to protect a critical section. Thread A holds the lock and calls `lock.newCondition().await()`. Thread B then calls `lock.lock()`. What happens to Thread B?

💡 Difficulty: hard | ✅ Correct: C

Q34. A multi-threaded application uses an `ArrayList` to store results. Without synchronization, what is the most likely symptom of this bug during execution?

Q35. Consider the following code: `synchronized(lockA) { synchronized(lockB) { // do work } }` and another thread: `synchronized(lockB) { synchronized(lockA) { // do work } }`. To prevent a potential deadlock, which of the following is the BEST strategy?
