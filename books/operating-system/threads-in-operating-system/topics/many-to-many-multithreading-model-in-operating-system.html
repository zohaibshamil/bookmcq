Q1. What is the fundamental characteristic of the many-to-many threading model?

🔹 A. Many kernel threads map to one user thread
🔹 B. Many user threads multiplex to a smaller or equal number of kernel threads
🔹 C. One user thread maps to many kernel threads
🔹 D. Each user thread maps to a kernel thread

💡 Difficulty: easy | ✅ Correct: B

📖 Explanation:

The many-to-many model multiplexes many user-level threads to a smaller or equal number of kernel threads. This means multiple user threads are mapped to a pool of kernel threads, where the number of kernel threads is less than or equal to the number of user threads.

Q2. How does the many-to-many model compare to the many-to-one model in terms of concurrency?

🔹 A. Both provide the same concurrency
🔹 B. Many-to-many provides better concurrency
🔹 C. Many-to-one provides better concurrency
🔹 D. Concurrency depends on the operating system

💡 Difficulty: easy | ✅ Correct: B

📖 Explanation:

The many-to-many model provides better concurrency than the many-to-one model because it uses multiple kernel threads. While many-to-one allows only one kernel thread, many-to-many uses multiple kernel threads that can run in parallel, enabling true concurrency on multiprocessor systems.

Q4. What happens when a thread in the many-to-many model performs a blocking system call?

🔹 A. Thread migration is not supported
🔹 B. Thread migration is possible through kernel thread scheduling
🔹 C. Thread migration is automatic
🔹 D. Thread migration is handled in hardware

💡 Difficulty: medium | ✅ Correct: B

📖 Explanation:

Thread migration between processors in the many-to-many model is possible through kernel thread scheduling. The kernel scheduler can move kernel threads between processors, and user threads can migrate with their kernel threads. This allows the model to adapt to system load and maintain performance.

Q100. What is the relationship between the many-to-many model and thread locality?

🔹 A. Thread locality is not supported
🔹 B. Thread locality can be supported through binding
🔹 C. Thread locality is automatic
🔹 D. Thread locality is not important

💡 Difficulty: hard | ✅ Correct: B

📖 Explanation:

Thread locality can be supported in the many-to-many model through the two-level model's binding capability. By binding a user thread to a specific kernel thread, and keeping that kernel thread on the same processor, applications can maintain thread locality. This can improve cache performance and reduce migration overhead.

Q101. Which statement about the many-to-many model's blocking behavior is accurate?

🔹 A. All threads block together
🔹 B. Only the thread on the blocked kernel thread is affected
🔹 C. The process blocks
🔹 D. Threads are terminated

💡 Difficulty: medium | ✅ Correct: B

📖 Explanation:

In the many-to-many model, when a thread makes a blocking system call, only the thread on the blocked kernel thread is affected. Other user threads on other kernel threads can continue executing. This selective blocking maintains concurrency and is a key advantage over the many-to-one model.

Q102. How does the many-to-many model compare to the one-to-one model in terms of thread count limits?

🔹 A. Both have the same limits
🔹 B. Many-to-many allows more threads with lower overhead
🔹 C. One-to-one allows more threads
🔹 D. Limits are determined by hardware only

💡 Difficulty: hard | ✅ Correct: B

📖 Explanation:

The many-to-many model allows creating more threads with lower overhead compared to the one-to-one model. While the one-to-one model is limited by the overhead of creating kernel threads for each user thread, the many-to-many model can create many user threads because they are multiplexed onto fewer kernel threads. This makes the many-to-many model more scalable for thread-heavy applications.

Q103. What is the effect of the many-to-many model on application development practices?
