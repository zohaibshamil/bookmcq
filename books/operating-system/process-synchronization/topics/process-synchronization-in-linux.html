What is Process synchronization in Linux?

Definition:
Linux provides synchronization mechanisms such as mutexes, semaphores, spinlocks, and condition variables primarily through the POSIX Threads (Pthreads) library. These tools allow threads to coordinate access to shared data, ensuring mutual exclusion and proper ordering in multithreaded Linux applications.

Working:
Pthreads use `pthread_mutex_t` for locks, `sem_t` for semaphores, and `pthread_cond_t` for condition variables. Threads lock mutexes before accessing shared data. Semaphores control resource counts. Condition variables allow threads to wait for specific conditions, signaled by other threads.

Example:
Initialize mutex: `pthread_mutex_init(&mutex, NULL)`. Thread locks: `pthread_mutex_lock(&mutex)`. Access shared data. Unlock: `pthread_mutex_unlock(&mutex)`. This ensures only one thread accesses the data at a time in a Linux process.

Reason:
Linux relies heavily on Pthreads for user-space synchronization. These standards-compliant tools are portable and efficient. Spinlocks are used in the kernel for short waits. Understanding Pthreads is essential for developing multithreaded applications on Linux systems.

Common MisConceptions:
Students often think Linux semaphores are the same as System V semaphores. Pthreads semaphores are different. Also, they may confuse mutexes with spinlocks. Mutexes sleep, spinlocks busy-wait. Spinlocks are for kernel use or very short critical sections.

Exam Preparation Tips: How to prepare this topic
Memorize Pthread function names: pthread_mutex_lock, pthread_cond_wait. Understand the initialization requirements. Know the difference between process-shared and thread-private synchronization. Practice compiling and running simple Pthread programs.

Key Terms:

  • Pthreads - POSIX standard for thread synchronization.
  • Spinlock - busy-wait lock, used in Linux kernel.
  • Condition Variable - pthread_cond_t for thread signaling.

📝 All Process synchronization in Linux MCQs

Q1. A developer protects a shared counter with a process-private pthread mutex, but two separate processes still experience races. What is the most likely cause?

A.The mutex must be replaced with a spin loop in every process
B.Linux does not support mutexes for concurrent processes
C.The mutex is not configured and shared through suitable shared memory for interprocess use ✅
D.A mutex can protect only read-only variables
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: A default process-private pthread mutex is intended for threads within one process. Separate processes need a mutex stored in shared memory and configured with the process-shared attribute; otherwise, they do not coordinate through the same interprocess mutex mechanism.

Q2. A process creates a child using fork(). Both processes then update a normal global variable protected by their own mutex objects. Why can their updates still conflict?

A.After fork, ordinary private memory is not automatically one shared writable state between the processes ✅
B.fork() removes every mutex from the child
C.The parent and child always use different CPU architectures
D.A global variable is inherently atomic across processes
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: After fork, the parent and child have separate virtual address spaces, with copy-on-write behavior for ordinary private memory. Their global variables and private mutexes therefore do not provide shared interprocess state unless suitable shared memory and synchronization are deliberately used.

Q3. A Linux application must notify a waiting process that a particular operation has completed, without transferring a numeric resource count. Which primitive most naturally represents this notification?

A.A file descriptor number used as a counter
B.A mutex locked permanently by the notifier
C.A busy loop that checks an unrelated variable
D.An event-like mechanism such as a condition variable used with a shared predicate ✅
💡 Difficulty: medium | ✅ Correct: D

📖 Explanation: A condition variable can notify waiters that a shared predicate may have changed, while the predicate itself records whether the operation is complete. The waiter must check that predicate under its mutex because notifications alone do not store completion state.

Q4. A thread checks a condition variable's predicate, releases the mutex, and only afterward begins waiting. Another thread changes the predicate and signals during that gap. What failure is possible?

A.The signal automatically changes the predicate back to false
B.The waiting thread may miss the notification and sleep despite the predicate already being true ✅
C.The mutex permanently becomes recursive
D.Linux converts the condition variable into a semaphore
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: The separate predicate check and wait operation create a lost-wakeup window. Proper condition-variable usage atomically releases the associated mutex while entering the wait, then rechecks the predicate after waking, preventing reliance on a notification that occurred before waiting began.

Q5. A developer replaces a counting semaphore initialized to 4 with a binary semaphore initialized to 1. The application manages four independent network buffers. What is the principal consequence?

A.The buffers become accessible without synchronization

💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: A binary semaphore provides at most one permit at a time, so it serializes access even when four independent buffers could safely be used concurrently. A counting semaphore with four permits better represents four interchangeable available resources.

Q6. A program calls sem_wait() and receives an interruption-related error because a signal arrived before the operation completed. What should robust application logic generally do when acquisition remains necessary?

💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: sem_wait() can fail with EINTR when interrupted by a signal before acquisition completes. If the application still requires the permit, it should handle that error deliberately and retry rather than assuming acquisition succeeded or releasing a permit it never obtained.

Q7. Two threads lock mutex A and mutex B in opposite orders. One holds A while waiting for B; the other holds B while waiting for A. Which condition explains the resulting deadlock?

A.Both threads are executing atomic instructions
B.A circular wait exists while each thread retains a resource requested by the other ✅
C.The scheduler has selected the same thread twice
D.Both mutexes have been initialized as unlocked
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Each thread holds one mutex and waits for the other, creating a circular wait. Neither can proceed to release its held mutex, so the deadlock persists unless an external intervention or a design-level deadlock prevention strategy changes the situation.

Q8. A team imposes a global ordering on all mutexes and requires every thread to acquire them in increasing order. Which deadlock condition does this policy directly target?

A.Circular wait ✅
B.Mutual exclusion
C.Resource consumption
D.Context switching
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: A strict global lock order prevents threads from forming a cycle in the resource-allocation graph because every acquisition follows the same direction. This directly attacks circular wait, although other performance issues such as contention and starvation may still occur.

Q9. A process uses pthread_mutex_trylock() and receives EBUSY. Which interpretation is correct?

📖 Explanation: pthread_mutex_trylock() returns immediately rather than waiting for an unavailable mutex. EBUSY indicates that the lock was not acquired because it was already locked, so the caller must choose an appropriate retry, fallback, or failure-handling strategy.

Q10. A worker locks a normal pthread mutex and then attempts to lock the same mutex again without unlocking it. What is the safest general conclusion?

💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: A normal mutex is not designed for recursive acquisition by its owner. Re-locking it can deadlock, while the precise behavior depends on the mutex type and interface rules; code needing recursion must explicitly select and understand an appropriate recursive mutex.

Q11. A Linux program uses a robust mutex. The owner process terminates while holding it, and another process acquires it with an owner-death indication. What should the new owner do?

📖 Explanation: A robust mutex can report that its previous owner died while holding it, but it cannot automatically repair application data. The new owner must inspect and recover the protected state, then mark the mutex consistent if recovery succeeds.

Q12. A shared-memory data structure is accessed by multiple processes. A programmer places a process-shared pthread mutex in ordinary heap memory allocated separately by each process. Why does this fail to coordinate the processes?

📖 Explanation: Setting a mutex to process-shared does not make separately allocated copies identical. The mutex must reside in a memory region genuinely shared and mapped by all participating processes, and each process must refer to that same synchronization object.

Q13. A developer uses a POSIX named semaphore so independently launched programs can coordinate access to a shared service. What advantage does the named semaphore provide?

📖 Explanation: A named POSIX semaphore can be opened by independently launched processes using a common name, allowing them to coordinate without inheriting the same unnamed semaphore object. It does not itself share application data or eliminate every scheduling problem.

Q14. A producer increments a shared item count and signals a condition variable, but it modifies the count without holding the associated mutex. The consumer checks the count while holding that mutex. Why is the design unsafe?

💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: A condition variable is meant to coordinate changes to a predicate protected by a mutex. Updating the predicate outside that mutex allows concurrent checks and modifications to race, so the consumer's protected check cannot reliably establish a consistent relationship with the producer's update.

Q15. A thread wakes from pthread_cond_wait() and finds that the queue is still empty. Which explanation is valid?

📖 Explanation: A condition-variable wakeup does not promise that the associated condition is true. Spurious wakeups are permitted, and another thread may consume the available item first, so waiters should use a loop that rechecks the shared predicate while holding the mutex.

Q16. A Linux service has a critical section used by many threads, but lock contention is extremely low and the section sometimes blocks for disk I/O. Which choice is usually more appropriate than a spinlock?

A.A spinlock held across disk I/O

C.A sleeping mutex that allows contending threads to block ✅
D.Disabling interrupts from user space
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: A mutex is generally preferable when a critical section can block or remain occupied for a significant period. A spinlock wastes CPU cycles while waiting and is unsuitable for ordinary user-space code that may sleep during disk I/O.

Q17. A developer claims that marking a shared integer volatile makes increments atomic and eliminates races between Linux threads. Which evaluation is correct?

💡 Difficulty: medium | ✅ Correct: D

📖 Explanation: The volatile qualifier generally constrains certain compiler optimizations but does not turn an increment into an atomic operation or establish the synchronization guarantees needed between threads. Atomic types or suitable locks are required to prevent data races.

Q18. Two threads increment a shared counter using a C atomic fetch-add operation with relaxed memory ordering. What guarantee does this provide?

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: A relaxed atomic read-modify-write prevents lost updates to that atomic object and gives a well-defined modification order for it. Relaxed ordering does not create acquire-release synchronization for unrelated data, so it is insufficient when additional publication ordering is required.

Q19. Thread A writes a data structure and then performs a release-store to an atomic ready flag. Thread B observes that flag using an acquire-load and sees the released value. What follows when the synchronization is correctly established?

📖 Explanation: A release operation orders preceding writes before publication, and a corresponding acquire operation that observes the release establishes synchronization. This allows the receiving thread to observe the data initialized before publication, provided the program follows the memory model correctly.

Q21. A Linux application must wait until several worker threads finish before collecting their results. Which synchronization method most directly matches this requirement?

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: An unnamed POSIX semaphore used between processes must reside in shared memory and be initialized with the process-sharing setting. A semaphore in private memory is not a common synchronization object for parent and child, even though the child inherits an initial memory image.

Q43. A developer assumes that because Linux schedules one thread at a time on a single CPU, a shared counter increment needs no synchronization. Why is the reasoning wrong?

A.A single CPU prevents every context switch inside a statement
B.The kernel makes all multi-instruction operations indivisible
C.Only processes, never threads, can be interrupted
D.A thread can be preempted between the read and write steps of an increment, allowing another thread to intervene ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: Single-core execution does not make a multi-instruction read-modify-write operation atomic. The scheduler can switch threads between the read and write, allowing another increment to observe stale state and overwrite an update, so synchronization is still required.

Q44. A program's correctness depends on a signal arriving exactly once to indicate that work is available. Why is a condition-variable notification alone not a durable record of the work?

A.Condition variables automatically store an unlimited notification queue
B.Every notification is preserved until a future waiter consumes it
C.A signal may occur when no thread is waiting, so durable state must be represented by a protected predicate or counting primitive ✅
D.A signal always increments the condition variable's internal count
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: Condition-variable signals are notifications, not stored event counts. If no thread is waiting, a signal may have no lasting effect; therefore, the application must represent pending work in shared state protected by a mutex or use a counting semaphore when accumulated permits are required.

Q45. A developer compares a binary semaphore with a mutex for protecting a critical section. Which property is a meaningful reason to prefer a mutex when ownership matters?

A.A mutex always provides greater throughput than a semaphore
B.A mutex can never block a thread
C.A mutex automatically repairs all protected data after a crash
D.Mutexes have ownership semantics that support disciplined locking and unlocking by the owning thread ✅
💡 Difficulty: medium | ✅ Correct: D

📖 Explanation: A mutex is intended to provide mutual exclusion with ownership semantics, making it suitable for protecting a critical section. A semaphore represents permits and does not generally enforce the same owner-only release discipline, so the appropriate choice depends on the coordination problem.

Q46. A worker acquires a process-shared mutex and then crashes. The other process blocks forever because the mutex was not configured as robust. Which lesson is most accurate?

A.All pthread mutexes automatically recover after process death
B.Ordinary mutexes do not necessarily recover ownership after a process dies, so robust mutexes or an explicit recovery strategy may be needed ✅
C.A mutex must be stored in a CPU register to recover
D.The blocked process should repeatedly unlock the mutex without acquiring it
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: An ordinary mutex may remain locked if its owner terminates unexpectedly, leaving other participants blocked. Robust mutexes can report owner death and allow application-level recovery, but recovery must be designed explicitly and is not automatic for every mutex.
