What is Mutex Locks in Process Synchronization?

Definition:
A mutex lock is a synchronization tool that uses a boolean variable to indicate if a resource is available. Processes must acquire the lock before entering the critical section and release it afterward. It ensures mutual exclusion by blocking other processes from accessing the resource until the lock is released.

Working:
The lock has two operations: acquire() and release(). Acquire() waits until the lock is available (false) and sets it to true. Release() sets the lock to false. These operations must be atomic to prevent race conditions on the lock variable itself, often implemented using hardware instructions.

Example:
Process P calls `acquire(mutex)`. If mutex is false, it becomes true, and P enters. Process Q calls `acquire(mutex)`. Since mutex is true, Q waits. When P finishes, it calls `release(mutex)`, setting it to false. Q then acquires it and enters the critical section.

Reason:
Mutex locks are simple and easy to implement compared to semaphores. They are ideal for protecting simple critical sections where only one process needs access at a time. They form the basis for more complex synchronization mechanisms in modern operating systems.

Common MisConceptions:
Students often forget that the acquire and release operations themselves must be atomic. Another error is using mutexes for signaling between processes, which is better suited for semaphores. Mutexes are strictly for mutual exclusion, not for ordering events.

Exam Preparation Tips: How to prepare this topic
Practice implementing a mutex using TestAndSet. Understand the difference between spinlocks (busy waiting) and blocking mutexes. Identify scenarios where a mutex is appropriate versus a semaphore. Focus on the atomicity requirement of lock operations.

Key Terms:

  • Acquire - operation to gain ownership of the lock.
  • Release - operation to free the lock.
  • Spinlock - mutex that uses busy waiting to acquire lock.

📝 All Mutex Locks in Process Synchronization MCQs

Q1. Two threads share a bank balance. Each must check whether a withdrawal is affordable and then subtract the amount. Why should the check and subtraction occur within the same mutex-protected region?

A.A mutex makes every arithmetic instruction execute faster
B.The combined operation preserves the balance invariant by preventing another thread from changing the balance between checking and subtracting ✅
C.A mutex automatically restores the balance after an overdraft
D.The subtraction becomes atomic merely because the balance is an integer
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: The affordability check and subtraction form one logical transaction. Without protecting both steps, another thread could withdraw funds after the check but before the subtraction, causing an invalid balance even if individual reads and writes are correctly implemented.

Q2. Thread A acquires a non-recursive mutex and calls a helper function that attempts to acquire the same mutex. The helper cannot return until acquisition succeeds. What is the likely result?

A.Thread A may deadlock waiting for a mutex it already owns ✅
B.The mutex automatically recognizes the same thread and succeeds
C.Thread A releases the mutex when entering the helper
D.The operating system converts the mutex into a semaphore
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: A non-recursive mutex generally cannot be acquired again by its current owner before release. Since the helper waits for a lock held by the calling thread, that thread cannot reach the code that releases it, producing self-deadlock.

Q3. A program protects updates to two independent counters with one mutex. Profiling shows that threads frequently wait even though they usually update different counters. Which redesign is most likely to improve concurrency safely?

A.Remove all synchronization because counters are independent
B.Make the single mutex recursive
C.Use separate mutexes for the counters, provided no shared invariant requires atomic joint updates ✅
D.Acquire and release the original mutex twice around every instruction
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: A single mutex serializes all protected updates, including operations on independent counters. Separate mutexes can permit simultaneous updates, but if correctness depends on a relationship between both counters, that relationship still requires coordinated protection.

Q4. A developer assumes that because mutex acquisition is atomic, all threads waiting for the mutex will acquire it in arrival order. Which statement is correct?

A.Atomicity guarantees that the oldest waiter always wins
B.A mutex provides exclusive ownership, but fairness depends on its implementation and scheduling policy ✅
C.A mutex always selects the thread with the lowest identifier
D.Arrival order is guaranteed only when the critical section contains no writes
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: Atomic acquisition ensures that competing threads do not simultaneously obtain ownership. It does not inherently define which waiting thread wins next; fairness depends on the mutex implementation, operating-system scheduling, and any explicit queueing policy.

Q5. A thread acquires mutex M, then waits indefinitely for a network response while holding it. Other threads need M to update unrelated local data. What is the most appropriate improvement?

A.Make all waiting threads repeatedly attempt M more frequently
B.Increase the network timeout so the owner holds M longer
C.Move the potentially blocking network operation outside the critical section when correctness permits ✅
D.Allow every waiting thread to enter M concurrently
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: Holding a mutex during slow external I/O unnecessarily extends the critical section and blocks unrelated work. If the data can be safely prepared or checked under the lock and the network operation performed afterward, contention decreases without sacrificing the required invariant.

Q6. A mutex protects a shared list. A thread locks the mutex, obtains a pointer to an element, unlocks the mutex, and then reads that element. Another thread can remove and free the element. What is the main risk?

A.The mutex cannot protect linked lists
B.The pointer automatically becomes null when the mutex is released
C.Unlocking permanently prevents any later list updates
D.The element may be freed or changed after protection ends, making the pointer unsafe to use ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: The mutex protects the list only while the relevant operations are performed under its ownership. Once unlocked, another thread may remove or free the element, so using a saved pointer can cause a use-after-free or inconsistent read unless lifetime is managed separately.

Q7. A service uses a mutex to protect a cache. Measurements show average waiting time rises as the number of worker threads grows, while cache operations remain short. Which explanation is most plausible?

A.Increasing contention makes more workers compete for serialized access to the same protected cache ✅
B.A mutex automatically lengthens every cache operation as thread count rises
C.The cache becomes thread-safe only when every worker waits
D.The mutex must be releasing itself after every read
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: A mutex allows only one owner at a time for the protected cache. As more workers compete, time spent waiting and scheduling can rise even when each operation is short; reducing critical-section duration or contention can improve throughput.

Q8. Thread A owns mutex M and waits for a condition to become true. Thread B must acquire M to make that condition true. Neither thread can proceed. What is the fundamental design error?

A.The condition should always be represented as a floating-point value
B.The protocol waits for a state change while preventing the thread that can make it from acquiring the required mutex ✅
C.Thread B should repeatedly acquire M without checking ownership
D.A mutex cannot protect condition variables
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: The owner waits for a condition whose producer requires the same mutex. Because the owner never releases M, the producer cannot enter its protected code and change the condition. A condition-variable wait or a redesigned protocol must permit progress.

Q9. A thread attempts to acquire a mutex using a nonblocking try-lock operation and receives failure. What should it infer?

A.Another thread may own the mutex, so it must handle failure without entering the protected region ✅
B.The mutex is permanently corrupted
C.The calling thread now owns the mutex despite the failure
D.The operating system has released all locks in the process
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: A failed try-lock indicates that acquisition did not succeed, commonly because another thread holds the mutex. The caller must not access the protected state as if it owned the lock; it may retry, perform other work, or use a fallback strategy.

Q10. A thread acquires a mutex and then creates another thread that immediately tries to acquire the same mutex. The parent waits for the child to finish before unlocking. Why can the program hang?

A.Thread creation automatically transfers mutex ownership to the child
B.The child can unlock the parent's mutex without acquiring it
C.The parent and child share a mutex, so both must enter the critical section
D.The parent waits for a child that is blocked on a mutex the parent still holds ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: The child cannot complete its acquisition while the parent owns the mutex. Since the parent waits for the child before releasing that mutex, each waits on an event the other cannot provide. Unlocking before joining, where safe, breaks the cycle.

Q11. A shared object is always accessed under mutex M, but one logging function reads the same object's fields without acquiring M. Which statement best describes the problem?

A.The protected operations are sufficient because most readers use the mutex
B.The unprotected read can race with updates and observe inconsistent or unsafely accessed state ✅
C.The logging function cannot run while another thread is active
D.A mutex protects every reference to an object automatically
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: A mutex does not automatically protect an object merely because some code uses it. All conflicting accesses must follow a compatible synchronization protocol; an unprotected reader can overlap with writes and may observe inconsistent state or create a data race.

Q12. A programmer uses a mutex around a shared counter increment, but another thread performs an atomic increment without acquiring the mutex. What is the best assessment?

A.The atomic increment must wait because a mutex exists nearby
B.The mutex retroactively makes every operation on the counter mutually exclusive
C.The two protocols do not coordinate with each other, so the overall design may not preserve a larger invariant ✅
D.Atomic increment always fails when another thread owns any mutex
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: A mutex coordinates only threads that follow its locking protocol. An atomic increment may avoid a lost update to the counter itself, but it does not automatically coordinate with a mutex-protected compound operation or preserve related state invariants.

Q13. A thread locks M and then locks N. Another code path locks N and then M. Even if neither thread currently deadlocks, why is this design risky?

A.Different acquisition orders can create a circular wait under particular interleavings ✅
B.The mutexes automatically become recursive
C.The second lock acquisition always releases the first
D.Mutual exclusion requires all mutexes to have identical names
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: Different lock orders can produce a deadlock when each thread acquires one mutex and waits for the other. A consistent global ordering eliminates this particular circular-wait pattern and makes lock dependencies easier to review.

Q14. A function receives a mutex pointer and locks it, but the caller may pass a different mutex from the one used by other code accessing the same data. What is the likely result?

A.The operating system automatically merges both mutexes
B.The data becomes immutable after the first lock
C.Both mutexes protect the same memory simply because they are pointers
D.The code may have a synchronization gap because different mutexes do not exclude each other's owners ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: Mutual exclusion works only when competing accesses coordinate through the same synchronization object or a compatible protocol. Two distinct mutexes do not automatically exclude each other, even if their users believe they protect the same data.

Q15. A thread locks a mutex, modifies a shared structure, and unlocks it. Another thread then acquires the same mutex. Under a correctly implemented mutex with appropriate memory-ordering semantics, what should the second thread expect?

A.It must see every unrelated memory change made by every process
B.The prior owner's protected writes are made visible according to the mutex's synchronization guarantees ✅
C.It can see only the lock variable, never the structure
D.The mutex discards all changes when released
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Mutex acquisition and release typically establish synchronization ordering: writes performed by one owner before release become visible to a later owner after successful acquisition. This guarantee applies through the synchronization relationship, not indiscriminately to unrelated unsynchronized data.

Q16. A program protects a shared queue with a mutex but performs expensive sorting while holding it. Queue operations from other threads become delayed. What is the best general optimization?

A.Make the queue global so every thread can access it
B.Add another thread that holds the same mutex during sorting
C.Limit the critical section to the operations that actually require shared-state protection ✅
D.Remove the mutex only from the slowest operation without checking data dependencies
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: Long computations inside a critical section extend the time other threads must wait. If sorting can safely operate on a snapshot or local copy, the program can protect only the shared-state transfer and perform expensive work outside the mutex.

Q17. A thread locks a mutex and then invokes a callback supplied by external code. The callback may call back into the original component and attempt to lock the same mutex. What is the main concern?

A.The callback may trigger reentrant acquisition and deadlock or create lock-order problems ✅
B.Callbacks cannot execute while a mutex is held
C.The mutex becomes unlocked automatically during external calls
D.The callback must always run on another processor
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: Calling unknown or reentrant code while holding a mutex can introduce hidden lock acquisitions and unexpected dependency cycles. If the callback tries to reacquire the same non-recursive mutex, it can deadlock; minimizing external calls inside critical sections reduces this risk.

Q18. A developer assumes a mutex is unnecessary because each write to a shared integer is individually atomic on the processor. The program performs a read-check-write sequence. Why can the assumption still fail?

A.Atomic writes guarantee that the check and write are one operation
B.An integer cannot be read by two threads
C.The processor always serializes entire functions automatically
D.Individual atomic accesses do not make the multi-step decision and update indivisible ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: The correctness requirement concerns the entire read-check-write sequence, not merely the individual memory operations. Two threads can both read a condition as true before either writes, then both act on stale assumptions; a mutex or suitable atomic state transition is required.

Q19. A process holds mutex M while waiting for a condition variable. It calls a proper condition-wait operation that atomically releases M while sleeping and reacquires M before returning. Why is this design useful?

A.It allows the condition to be changed only by the sleeping thread
B.It lets another thread acquire M and update the condition while the waiter sleeps ✅
C.It permanently transfers ownership of M to the signaling thread
D.It guarantees the condition remains true after the wait returns
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: A condition-variable wait releases the associated mutex as part of entering the waiting state, allowing another thread to acquire it and update the condition. The waiter reacquires the mutex before resuming, then must check the condition again because wakeups do not guarantee it is true.

Q20. A thread waits on a condition variable while holding mutex M. After waking, it proceeds without checking the predicate again. Another thread may consume the resource first. What is the correct fix?

A.Use a loop that checks the condition while holding the mutex ✅
B.Remove the mutex from the condition-variable wait
C.Assume each wakeup grants ownership of the resource
D.Signal the condition variable twice before every resource use
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: Condition-variable wakeups may be spurious, or another thread may consume the resource before the awakened thread reacquires the mutex. Rechecking the predicate in a loop ensures the thread proceeds only when the required condition actually holds.

Q21. Two threads access a shared map. Thread A locks M and updates key X; thread B locks a different mutex N and updates key Y. Which condition would justify using separate locks?

A.Every map operation must be serialized regardless of key
B.Both threads must always update the same key
C.Operations are independent and no map-wide invariant or internal structure is left unprotected ✅
D.Different mutexes always synchronize with one another
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: Separate locks are safe only when the protected operations truly do not conflict and the map's internal representation remains correctly synchronized. If updating separate keys still mutates shared structural metadata, a broader lock or a more sophisticated concurrent map is needed.

Q22. A graph plots mutex wait time against critical-section duration. Wait time grows disproportionately as critical sections lengthen under high contention. Which interpretation is strongest?

A.Longer critical sections can keep the mutex unavailable for longer, amplifying queueing delays ✅
B.The graph proves that mutexes violate mutual exclusion
C.Critical-section duration has no possible effect on waiting
D.The operating system must be ignoring every lock release
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: When many threads contend for a mutex, each longer ownership interval delays those behind it. Queueing effects can make waiting time grow sharply, especially at high utilization; shortening protected work often improves latency more than simply adding threads.

Q23. A developer replaces a mutex with a busy loop that checks a shared Boolean without synchronization. The program occasionally misses an update. Which explanation is most accurate?

A.The Boolean becomes negative when threads compete
B.The loop's condition check is automatically protected by its repetition
C.Repeated reading guarantees that every write becomes visible
D.The unsynchronized access may have a data race or lack required visibility guarantees ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: Repeatedly reading a shared Boolean does not itself establish synchronization. Depending on the language memory model and hardware, the read may race with a write or fail to observe updates reliably; an atomic variable or proper synchronization is needed.

Q24. A mutex is initialized by one thread while another thread may already attempt to lock it. What is the primary concern?

A.Initialization is harmless because every lock operation initializes the mutex
B.Using the mutex before initialization completes can cause undefined or invalid behavior ✅
C.The second thread will necessarily initialize it correctly
D.The mutex is automatically initialized when its address is printed
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Synchronization objects must be initialized according to their API before concurrent use. Attempting to lock an uninitialized or concurrently initialized mutex can violate library requirements and produce undefined behavior, failed operations, or corrupted synchronization state.

Q25. A thread holds mutex M and needs mutex N. A second thread holds N and needs M. One thread uses a timeout and eventually abandons its attempt to acquire the second mutex. What does this change accomplish?

A.It guarantees that every operation completes successfully
B.It makes the mutexes unnecessary for future operations
C.It can break indefinite waiting if failure is handled safely, but the application must still recover its partial work ✅
D.It ensures both threads enter their critical sections simultaneously
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: A timed acquisition can prevent a thread from waiting indefinitely, but it does not automatically repair the application state. The thread must release resources it already holds when appropriate and safely retry, roll back, or report failure.

Q26. A developer uses a mutex to protect a shared counter and holds it while printing a large report. The counter update itself takes microseconds, but the report takes seconds. Which change is most appropriate?

A.Print the report while holding the mutex more frequently
B.Remove synchronization from the counter without further analysis
C.Make every thread print the same report simultaneously
D.Capture the required counter value under the mutex, then print from the local snapshot after unlocking ✅
💡 Difficulty: medium | ✅ Correct: D

📖 Explanation: If the report needs only a consistent counter value, the thread can copy that value while holding the mutex and release the lock before formatting or printing. This preserves the required snapshot while avoiding long periods of unnecessary exclusion.

Q27. A thread attempts to unlock a normal mutex that it does not own. Why is this generally a serious programming error?

A.It always transfers ownership to the thread with the oldest ticket
B.Mutex APIs generally require the owning thread to release the mutex, and violating this rule may be undefined or erroneous ✅
C.It is safe because any thread can release any mutex
D.The operating system will always infer the intended owner
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Mutex ownership rules are part of the synchronization contract. Releasing a mutex from a non-owner can be undefined behavior or produce an API error, depending on the mutex type and platform; it can also break assumptions about protected state and ownership.

Q28. A thread acquires M and N, updates shared state, then releases M before N. Another thread follows the same acquisition order but releases N before M. Which statement is correct?

A.Release order alone always creates deadlock regardless of execution
B.Both threads can safely ignore all acquisition rules
C.Consistent acquisition order is the primary way to prevent the common circular-wait pattern, while release order must still preserve each lock's ownership rules ✅
D.Mutexes require that all locks be released in alphabetical order
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: Deadlock prevention commonly relies on a consistent order for acquiring multiple locks. Releasing locks in different orders is not automatically a deadlock, but each release must be valid and the broader protocol must preserve data invariants and avoid exposing inconsistent state.

Q29. A program uses a mutex to protect a resource count. One thread checks that the count is positive, unlocks, and then decrements it after reacquiring the mutex. Another thread can consume the final resource in between. What is the correct diagnosis?

A.The check and decrement must be one protected transaction ✅
B.The mutex should be initialized to the resource count
C.The decrement must be replaced with floating-point subtraction
D.The operating system should delay all competing threads permanently
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: The resource-availability check and decrement are logically dependent. Releasing the mutex between them allows another thread to change the count, making the first thread's earlier check stale. Keeping both steps within one critical section preserves the resource-count invariant.

Q30. A system uses a mutex around a short operation, but a large number of threads repeatedly contend for it. Which alternative may be worth evaluating if the critical section is extremely short and the owner is unlikely to be preempted?

A.A condition variable without any predicate
B.A global interrupt disable that never ends
C.An ordinary shared Boolean with no synchronization
D.A carefully implemented spinlock, after measuring contention and CPU costs ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: A spinlock may be suitable when lock hold times are very short and the owner can run promptly, because blocking and waking may cost more than spinning briefly. Under heavy contention or preemption, however, spinning can waste substantial CPU time.

Q31. A mutex protects an object, but a function returns a reference to the object after releasing the lock. Callers then modify the object directly. What is the central design weakness?

A.Returning a reference always copies the object
B.The lock's protection ends before callers use the reference, allowing unsynchronized external mutation ✅
C.Mutexes can protect only integer values
D.The function must retain the lock for the entire lifetime of the program
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: The mutex protects operations performed while it is held, not future accesses through a returned reference. If callers can mutate the object after the lock is released, the object may be accessed concurrently without protection; APIs should preserve ownership or provide synchronized operations.

Q32. A thread holds mutex M while calling a function that waits for another thread to terminate. The other thread needs M to finish its final cleanup. What is the most direct resolution?

A.Make the waiting function acquire M a second time
B.Increase the number of shared variables
C.Release M before waiting when safe, or restructure cleanup so the terminating thread does not require the held mutex ✅
D.Require the terminating thread to wait for the first thread
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: The waiting thread prevents the other thread from acquiring the mutex needed to finish. Releasing the mutex before joining or waiting, when the program's invariants permit it, breaks the dependency cycle; otherwise the cleanup protocol must be redesigned.

Q33. A developer claims that adding a mutex guarantees a program will never deadlock. Which counterexample best refutes the claim?

A.Two threads acquire different mutexes in opposite orders and wait for each other's held mutex ✅
B.One thread locks a mutex and then unlocks it normally
C.A thread reads a local variable without synchronization
D.A mutex is initialized before any thread starts
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: A mutex enforces exclusive ownership of its own protected region but does not prevent circular waits across multiple locks. Opposite acquisition orders can create a deadlock even when every individual mutex correctly enforces mutual exclusion.

Q34. A mutex-protected function reads a shared value, computes a result, and writes it back. A reviewer proposes replacing the mutex with a single compare-and-swap loop. Under what condition is that replacement plausible?

A.The function calls arbitrary blocking I/O during the update
B.The operation depends on several unrelated shared objects that cannot be coordinated
C.The code assumes every compare-and-swap attempt must succeed
D.The entire state transition can be safely expressed as a retryable atomic update with correct handling of interference ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: Compare-and-swap can replace a mutex for some simple state transitions when the full update can be recomputed after a failed comparison. The approach is unsuitable without redesign if the operation has irreversible side effects, blocking work, or invariants spanning multiple locations.

Q35. A benchmark shows that a mutex has low wait time with two threads but high wait time with sixteen threads. The protected operation is unchanged. Which additional measurement would most help identify whether the bottleneck is lock contention rather than unrelated computation?

A.The number of source-code comments
B.The fraction of execution time spent waiting to acquire the mutex and the distribution of lock hold times ✅
C.The number of variable names in the program
D.The size of the executable's icon
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: Lock acquisition wait time and hold-time distributions directly indicate how much execution is delayed by serialization. If wait time rises with thread count while the protected work remains unchanged, contention is a likely bottleneck; other profiling can then identify the source.

Q36. Two threads update separate fields of a structure under separate mutexes, but a third operation must read both fields as one consistent snapshot. What must the design provide?

A.The third operation should read both fields without any lock
B.Each field should be updated only once during program execution
C.A synchronization strategy that coordinates both fields during the snapshot or otherwise guarantees a consistent version ✅
D.The two mutexes should be renamed to the same identifier
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: Separate mutexes permit independent field updates but do not automatically make a two-field read consistent. The snapshot may need to acquire both locks using a consistent order, or use a suitable versioning or transactional design that detects concurrent changes.

Q37. A mutex is held by a low-priority thread, while a high-priority thread waits for it and medium-priority work keeps the owner from running. Which scheduling issue may arise?

A.The high-priority thread automatically takes ownership of the mutex
B.The mutex converts the medium-priority thread to the highest priority permanently
C.Priority inversion, potentially mitigated by priority inheritance or related scheduling protocols ✅
D.The low-priority thread can never release a mutex under any circumstances
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: Priority inversion occurs when a high-priority thread waits for a lock held by a lower-priority thread that cannot run because medium-priority tasks preempt it. Priority inheritance can temporarily raise the owner's priority so it can release the mutex sooner.

Q38. A program uses one mutex for every operation in a large shared service. An engineer proposes replacing it with fine-grained mutexes. What is the most important trade-off to evaluate?

A.Fine-grained locks always eliminate deadlocks and races
B.They can increase concurrency but also add complexity in lock ordering, multi-resource operations, and invariant preservation ✅
C.They make every critical section execute atomically without hardware support
D.They remove the need to initialize synchronization objects
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Fine-grained locking can reduce contention by allowing independent operations to proceed concurrently. It also increases the number of lock dependencies and makes operations spanning multiple resources harder to coordinate, so correctness, lock ordering, and maintenance complexity must be evaluated.
