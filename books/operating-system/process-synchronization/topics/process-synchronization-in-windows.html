What is Process synchronization in Windows?

Definition:
Windows provides various synchronization mechanisms including mutexes, semaphores, events, and critical sections. These objects are kernel-level or user-level constructs that allow threads within processes or across processes to coordinate access to shared resources safely and efficiently in the Windows environment.

Working:
Kernel objects like mutexes and semaphores are named and can be shared across processes. User-mode critical sections are faster for intra-process synchronization. Events are used for signaling. Threads wait on these objects using WaitForSingleObject or similar APIs, blocking until the object is signaled.

Example:
Create a named mutex `CreateMutex(NULL, FALSE, \MyMutex\")`. Thread A calls `WaitForSingleObject(hMutex INFINITE)`. It acquires the lock. Thread B calls the same and blocks. Thread A releases with `ReleaseMutex(hMutex)`. Thread B then acquires it.

Reason:
Windows offers a rich set of tools tailored for its architecture. Kernel objects provide security and cross-process capability. User-mode objects offer performance for local threading. This flexibility allows developers to choose the right tool for the specific synchronization need.

Common MisConceptions:
Students often confuse critical sections with mutexes. Critical sections are faster but cannot be shared across processes. Mutexes are slower but can be named and shared. Also forgetting to close handles can lead to resource leaks in Windows.

Exam Preparation Tips: How to prepare this topic
Learn the key Windows API functions: CreateMutex WaitForSingleObject ReleaseMutex. Understand the difference between user-mode and kernel-mode synchronization. Know when to use events vs. mutexes. Focus on the naming aspect for cross-process sync.

Key Terms:

  • Critical Section - fast user-mode intra-process lock.
  • Mutex - kernel-object cross-process named lock.
  • Event - kernel-object for signaling thread state.

Q1. Two Windows threads increment a shared counter one million times each without synchronization. The final count is lower than two million. Which explanation best fits the result?

A.Windows automatically discards updates from lower-priority threads
B.The counter is guaranteed to be atomic because it is an integer
C.Concurrent read-modify-write operations can overwrite each other's updates, causing lost increments ✅
D.The scheduler must have terminated both threads early
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: An ordinary increment typically involves reading, modifying, and writing a value. If two threads interleave these steps, one write can overwrite the other's update. Mutual exclusion or an appropriate atomic operation is needed to prevent lost increments.

Q2. A Windows application protects a shared data structure with a critical section. Thread A enters it, and thread B attempts to enter the same critical section. What should normally happen?

A.Thread B waits until Thread A leaves the critical section before entering it ✅
B.Both threads enter because critical sections are intended for parallel execution
C.Thread B permanently terminates when it encounters the critical section
D.Thread A automatically transfers ownership of the critical section to every waiting thread
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: A critical section provides mutual exclusion among threads using the same critical-section object within a process. Thread B must wait or otherwise contend until Thread A leaves, helping ensure that protected data is not modified concurrently.

Q3. A developer creates two unrelated processes and initializes a separate critical-section object in each. Both processes access the same shared-memory region. Why is this insufficient for cross-process mutual exclusion?

A.Critical sections always synchronize every process on the computer
B.Shared memory automatically shares critical-section ownership
C.Critical sections are kernel objects that coordinate all processes by default
D.Each process has its own critical-section state, so the two objects do not automatically coordinate access across processes ✅
💡 Difficulty: medium | ✅ Correct: D

📖 Explanation: A Windows critical section is intended for synchronization among threads within the same process. Separate objects in unrelated processes have independent state, so cross-process shared memory generally requires a suitable interprocess synchronization mechanism, such as a named mutex.

Q4. Thread A owns a Windows mutex and then waits indefinitely for Thread B to perform an action. Thread B attempts to acquire the same mutex before performing that action. What is the likely outcome?

📖 Explanation: Thread A holds the mutex while waiting for Thread B, but Thread B cannot perform its required action until it acquires that mutex. This circular dependency can prevent both threads from progressing, illustrating why locks should not be held while waiting for dependent work.

Q19. A thread enters a Windows critical section twice from the same thread and leaves it twice. Under the documented recursive behavior of critical sections, what is generally expected?

Q42. A Windows application has a bounded queue and uses a semaphore for free slots plus another semaphore for available items. A producer reserves a free slot but fails before inserting the item. What must the error-handling protocol consider?

A.The queue is automatically repaired when the producer thread exits
B.The item semaphore should always be incremented even though no item exists
C.The reserved free-slot permit may need to be restored, and item permits must correspond only to successfully inserted items ✅
D.Both semaphore counts should be set to the queue capacity after every failure
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: Semaphore counts must remain consistent with actual queue state. If a producer reserves capacity and fails before insertion, the design needs a recovery path to restore that reservation without advertising a nonexistent item to consumers.

Q43. A Windows application has two threads that need to update related variables. One uses a critical section, but the other accesses the variables without entering it. Why is the data still unprotected?

A.Mutual exclusion works only when every conflicting access follows the same synchronization protocol ✅
B.A critical section automatically detects and blocks every unsynchronized access
C.The first thread's lock makes all variables process-wide atomic
D.The operating system prevents unsynchronized writes to shared variables
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: A lock protects data only when all accesses that can conflict use a compatible locking protocol. An unsynchronized thread can read or modify the variables while another thread holds the critical section, producing races despite the presence of a correctly used lock in one code path.
