📝 Process Synchronization in Solaris (36 MCQs)

Solaris Kernel Synchronization and Locking Architecture

Solaris provides synchronization mechanisms for coordinating kernel threads and protecting shared operating system data structures. Its traditional kernel synchronization facilities include adaptive mutexes, condition variables, readers-writer locks, and semaphores. These mechanisms support different resource-access patterns and execution contexts, allowing the kernel to protect shared state while balancing processor utilisation, blocking overhead, and multiprocessor concurrency.

Why Solaris Uses Multiple Locking Strategies

Kernel operations vary in duration and execution context. Some critical sections are extremely short and benefit from spinning, while longer operations should allow waiting threads to sleep. Read-heavy structures also require efficient simultaneous access. Solaris uses different synchronization mechanisms to avoid unnecessary blocking, protect shared resources, and support scalable execution across multiple processors.

Adaptive Mutexes, Condition Variables, and Read-Write Locks

An adaptive mutex can spin while its owner is running on another processor, then block if the owner is not progressing. Condition variables allow threads to wait for specified events while releasing an associated lock. Readers-writer locks permit concurrent readers but require exclusive writer access, while semaphores coordinate resource counts and event ordering.

Choosing an Adaptive Mutex for a Short Critical Section

Suppose kernel thread T1 holds an adaptive mutex for a short operation on one CPU, while T2 requests the same lock on another CPU. T2 may spin briefly while T1 continues executing. If T1 stops running or the wait becomes unsuitable for spinning, T2 can block until the lock is released.

Multiprocessor Efficiency and Priority-Aware Synchronization

Solaris synchronization mechanisms support concurrent kernel execution, memory management, and resource coordination. Adaptive behaviour can avoid unnecessary sleeping when lock owners are actively progressing. However, spinning wastes CPU time if critical sections remain occupied too long. Priority-related blocking, lock ordering, and synchronization overhead must also be managed to preserve system responsiveness.

Misconceptions About Solaris Locking Mechanisms

'An adaptive mutex always makes waiting threads sleep' is incorrect because it may spin while the owner runs. 'Readers-writer locks permit concurrent writers' is incorrect because writers require exclusive access. 'Spinning is always more efficient than blocking' is incorrect because prolonged contention wastes processor capacity.

Exam Focus: Adaptive Mutex and Read-Write Lock Behaviour

Explain how an adaptive mutex chooses between spinning and blocking, and compare it with a conventional sleeping mutex. Trace reader and writer access under a readers-writer lock. Questions may examine condition variables, semaphore operations, multiprocessor contention, and why synchronization primitives must match the duration and context of protected operations.

Key Terms of Solaris Synchronization

  • Adaptive mutex - Lock combining spinning and blocking.
  • Condition variable - Coordinates event-based waiting.
  • Readers-writer lock - Allows shared reads and exclusive writes.
  • Semaphore - Synchronization through resource permits.
  • Spin - Repeatedly checks a lock condition.
  • Lock contention - Competition for protected access.

Q1. A Solaris service runs four kernel threads that each add one to a shared counter 500 times. The final value is 1,842. Which explanation best accounts for the shortfall from 2,000?

A.The scheduler discards increments made by threads with lower priority
B.Concurrent read-modify-write sequences can overwrite one another when no synchronization protects the counter ✅
C.Each thread receives a private copy of every global variable whenever it is preempted
D.Integer counters stop accepting updates after a fixed number of context switches
💡 Difficulty: easy | ✅ Correct: B

📖 Explanation: An increment usually reads, changes, and writes the counter. Two threads can read the same old value and then overwrite one another's results. Protecting the complete update with a mutex or atomic operation prevents these lost increments.

Q2. Two Solaris processes map the same shared-memory queue, but each initializes a separate process-private mutex in its own address space. Why can both still modify the queue simultaneously?

A.The processes are not using the same synchronization object in genuinely shared memory with process-sharing configuration ✅
B.A mutex protects only integer variables and cannot protect queue structures
C.The operating system automatically merges separately allocated mutexes only after contention begins
D.A process-private mutex becomes shared whenever two processes use the same variable name
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: Mutual exclusion works only when all participants coordinate through the same underlying object. Separately allocated process-private mutexes remain independent, even when they guard the same shared data. Interprocess coordination requires shared storage and compatible process-sharing setup.

Q3. In a Solaris kernel, when is brief spinning on an adaptive mutex most likely to be useful?

A.When the lock holder is blocked indefinitely on disk I/O
B.When the protected operation must permit several writers at once
C.When the owner is running on another CPU and is expected to release the short-held lock soon ✅
D.When the waiting thread must enter a long sleep before attempting acquisition
💡 Difficulty: easy | ✅ Correct: C

📖 Explanation: Brief spinning can avoid sleep and wake-up overhead when the lock owner is actively running and likely to release the mutex soon. If the owner is not progressing, continued spinning wastes processor time and blocking is preferable.

Q5. A Solaris data structure is searched by many threads and modified only occasionally. Which access pattern best justifies considering a reader-writer lock?

A.Multiple readers can safely overlap, while a writer needs exclusive access ✅
B.Writers can modify the structure simultaneously with every reader
C.Every read operation changes the shared structure
D.Only one thread is allowed to read or write at any time, even when no writer exists
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: A reader-writer lock allows compatible read operations to overlap while excluding readers and other writers during modification. It is most useful when reads are frequent, writes are relatively rare, and the protected work justifies the added lock-management cost.

Q6. Readers R1 and R2 both hold a shared read lock when writer W requests exclusive access. What must be true before W can enter its protected write section?

A.W may enter immediately because readers do not modify the data
B.Both R1 and R2 must release their read locks so the writer can obtain exclusive ownership ✅
C.W can enter as long as it writes a different field
D.One reader must convert its shared lock into a semaphore permit for W
💡 Difficulty: easy | ✅ Correct: B

📖 Explanation: A writer requires exclusive access, so it cannot enter while existing readers hold the shared lock. The readers must leave first. Whether new readers may join ahead of the writer depends on the lock's documented fairness policy.

Q7. A Solaris consumer waits for a producer to place an item in a shared queue. Which condition-variable design correctly coordinates the consumer?

A.Treat each condition-variable signal as a permanent record of one queued item
B.Read the queue count without a mutex after every wake-up
C.Protect the queue predicate with a mutex and recheck it in a loop after waking ✅
D.Assume a wake-up guarantees that the queue still contains an item
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: The queue predicate records whether work actually exists; a condition variable only notifies a waiter that the state may have changed. The consumer checks the predicate while holding the mutex and repeats the check after each wake-up.

Q8. A consumer checks that a queue is empty while holding mutex M, unlocks M, and only afterward registers on condition variable C. A producer inserts an item and signals C in between. What flaw is present?

A.The producer has violated mutual exclusion by inserting an item
B.The condition variable has stored two notifications for one item
C.The consumer will necessarily consume the same item twice
D.The consumer can miss the signal and sleep even though the queue is no longer empty ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: The separate unlock and wait-registration steps create a lost-wakeup window. A producer can change the predicate and signal before the consumer becomes a waiter. The condition wait must atomically release the mutex while blocking, followed by predicate rechecking.

Q9. A Solaris producer signals a condition variable while no consumer is waiting. A consumer begins waiting later. What should the consumer rely on to determine whether work exists?

A.The protected queue state or predicate, because the earlier signal is not a stored permit ✅
B.The old signal, which every condition variable retains until consumed
C.The number of times the producer previously called signal, even without shared state
D.The mutex owner field, which records how many queue entries are pending
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: Condition-variable notifications are not generally accumulated like semaphore permits. A signal issued with no waiter may have no lasting effect. The durable information must be represented by shared state, checked under the associated mutex before waiting and after waking.

Q10. A Solaris semaphore represents six available identical devices. Four successful wait operations occur, followed by two successful post operations, with no other activity. What is the resulting permit count?

A.2
B.4 ✅
C.6
D.8

Q11. A Solaris worker successfully waits on a semaphore for a device, then terminates before posting the permit. Other workers later remain blocked. Which explanation best fits the behavior?

A.The semaphore automatically identifies the worker and restores its permit
B.The semaphore changes into a mutex owned by the terminated worker
C.The permit may remain consumed because a semaphore does not generally track ownership for automatic recovery ✅
D.The operating system doubles every remaining permit after a worker exits
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: A semaphore records permits, not necessarily which thread owns each one. If a worker exits after consuming a permit without returning it, the count can stay reduced. An application needs cleanup or recovery logic for such failure paths.

Q12. A semaphore starts at 8. Three tasks each perform one successful wait but mistakenly perform two posts before finishing. Assuming no maximum-count failure or other activity, what is the final count?

A.5
B.8
C.10
D.11 ✅

Q13. A Solaris application protects a counter and related status field with mutex M. One code path updates the counter using an atomic instruction without acquiring M. Why can the overall invariant still fail?

A.The atomic update does not follow the shared locking protocol and may interleave with the compound protected update ✅
B.Atomic instructions are ignored whenever a mutex exists in the same program
C.A mutex protects only status fields and cannot protect counters
D.An atomic instruction always waits until every mutex in the process is released
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: An atomic instruction protects its individual read-modify-write operation, not the relationship between the counter and status field. Mixing it with a separate mutex protocol can expose intermediate combinations. All conflicting paths must follow a compatible synchronization design.

Q14. A service uses one mutex for thousands of unrelated cache records. Profiling shows long waits but very short individual updates. Which redesign is most directly worth evaluating?

A.Remove the mutex and allow every thread to update any record
B.Partition records across appropriately chosen locks while preserving a consistent order for operations that touch several partitions ✅
C.Increase the number of threads while keeping the same single lock
D.Keep the mutex permanently locked after each record update
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: A single mutex serializes independent record updates and can become a scalability bottleneck. Partitioning the state can allow unrelated operations to proceed concurrently. Operations spanning partitions still need a consistent locking protocol to preserve invariants and avoid deadlock.

Q15. Two Solaris threads may need mutexes A and B. One path acquires A before B, while another acquires B before A. Which policy most directly prevents this circular-wait pattern?

A.Let each thread choose whichever order is fastest at runtime
B.Increase both mutex hold times to reduce acquisition frequency
C.Define and enforce one global order for acquiring both mutexes ✅
D.Allow a thread to unlock a mutex owned by another thread
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: A consistent global acquisition order prevents threads from forming the opposing dependency cycle in which each holds one mutex and waits for the other. It addresses this deadlock pattern, although contention and starvation may still require separate attention.

Q16. A thread acquires a Solaris mutex, but a different thread later attempts to release that mutex. What should the reviewer generally conclude about this design?

A.It guarantees FIFO fairness for all waiters
B.It converts the mutex into a counting semaphore
C.It is required whenever the lock protects shared memory
D.It violates ordinary mutex ownership rules and may be invalid for the mutex type ✅
💡 Difficulty: medium | ✅ Correct: D

📖 Explanation: A mutex normally represents ownership as well as exclusion. Releasing it from a non-owner is not a valid general protocol and may be rejected or produce undefined behavior, depending on the primitive. The acquiring thread should perform the matching release.

Q17. Thread T1 updates two fields while holding mutex M, then unlocks M. Thread T2 later locks the same M before reading both fields. Which guarantee is central to this sequence?

C.The mutex automatically rolls back partial updates if T1 is interrupted
D.The two fields must contain identical values after every update
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: The mutex provides mutual exclusion and a synchronization relationship between release and a later successful acquisition. When all conflicting accesses use the same protocol, T2 can observe T1's completed protected updates rather than an unsynchronized intermediate state.

Q18. A Solaris program protects writes to a configuration field with mutex M, but a reader accesses that field without M because reads are usually harmless. The writer occasionally changes it. What is the concern?

C.The mutex prevents the writer from changing the field

💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: A read-only operation can still conflict with a concurrent write. Since the reader bypasses the synchronization protocol, it may observe an inconsistent value or create a data race. Immutable publication, atomic access, or consistent locking is required.

Q19. A Solaris service publishes a new immutable configuration snapshot and immediately frees the old snapshot. Some readers may still hold pointers to the old version. What essential step is missing?

💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: Publishing a replacement does not prove that readers have stopped using the previous version. Reclamation must wait for a safe point, such as a grace period or equivalent lifetime protocol, or readers may dereference freed memory.

Q20. A producer-consumer queue stores both its items and a separate count. Which practice best prevents the count from drifting away from the actual queue contents?

📖 Explanation: The queue and count describe related state and must change consistently. Protecting both under one suitable protocol prevents consumers from relying on stale information and maintains the invariant that the count matches the number of available items.

Q22. A thread repeatedly requests a resource and is bypassed by other threads each time it becomes available. Those other threads continue completing work. Which problem does this describe?

📖 Explanation: Starvation occurs when a particular thread is continually denied access despite overall system activity. Unlike deadlock, other threads can keep progressing. Fair allocation, bounded waiting, or a revised acquisition policy may be needed to prevent it.
