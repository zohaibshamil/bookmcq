What is Process Synchronization in Solaris?

Definition:
Solaris offers a comprehensive set of synchronization primitives including mutexes, reader-writer locks, condition variables, and semaphores. It supports both user-level and kernel-level synchronization, with adaptive mutexes that optimize performance by switching between spinning and blocking based on contention.

Working:
Adaptive mutexes spin for a short time if the lock is held by a thread on another CPU, then block if not acquired. Reader-writer locks allow multiple readers or one writer. Condition variables work with mutexes for signaling. Semaphores provide counting capabilities for resource management.

Example:
Use `pthread_mutex_lock` for mutual exclusion. For read-heavy data, use `rw_rdlock` for readers and `rw_wrlock` for writers. This allows concurrent reads while ensuring exclusive write access, improving performance in Solaris multi-threaded applications.

Reason:
Solaris is designed for high-performance server environments. Adaptive mutexes reduce context switch overhead for short critical sections. Reader-writer locks maximize concurrency for read-dominated workloads. These features make Solaris robust for enterprise-level synchronization needs.

Common MisConceptions:
Students may think adaptive mutexes always spin. They only spin briefly. Also, they may assume reader-writer locks are always faster; they have higher overhead than simple mutexes, so they are only beneficial when reads vastly outnumber writes.

Exam Preparation Tips: How to prepare this topic
Understand the concept of adaptive mutexes. Know when to use reader-writer locks. Familiarize yourself with Solaris-specific optimizations. Compare Solaris synchronization with Linux and Windows to highlight differences in approach and performance.

Key Terms:

  • Adaptive Mutex - spins then blocks based on contention.
  • Reader-Writer Lock - allows multiple readers or one writer.
  • Context Switch - overhead saved by spinning briefly.

📝 All Process Synchronization in Solaris MCQs

Q1. A Solaris application uses a shared counter updated by several threads. The final value is consistently smaller than the total number of increments. Which explanation best accounts for this result?

A.Solaris automatically rounds shared counters to the nearest integer
B.Concurrent read-modify-write operations can overwrite updates when no suitable synchronization protects the counter ✅
C.Every thread maintains a mandatory private copy of every global variable
D.The scheduler prevents threads from executing arithmetic instructions concurrently
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: An increment commonly involves reading a value, calculating a new value, and writing it back. Concurrent threads can read the same old value and overwrite one another's updates, so a shared counter needs an appropriate mutex or atomic operation.

Q2. A Solaris program protects a shared data structure with a mutex, but a second process still accesses the same structure without coordination. What is the most likely design flaw?

A.The mutex is too small to protect a structure
B.The structure must be copied before every read
C.The second process does not use the same properly shared synchronization object and locking protocol ✅
D.Solaris mutexes can protect only integer variables
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: Mutual exclusion works only when every relevant participant coordinates through the same synchronization object. If the second process accesses shared data without acquiring that object, the first process's mutex cannot prevent conflicting access.

Q3. A developer chooses a spin mutex for a critical section that may wait for a disk operation. Why is this usually a poor choice?

A.The thread may waste CPU cycles spinning while the operation blocks or takes a long time ✅
B.Spin mutexes automatically release themselves during disk operations
C.A spin mutex permits unlimited writers into the critical section
D.Disk operations cannot be performed by Solaris processes
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: Spin-based synchronization is appropriate only when waiting is expected to be extremely brief and the execution context permits spinning. A critical section that can block for disk I/O can waste CPU time and may violate the assumptions required by spin-based locking.

Q4. A Solaris service protects a shared resource with a mutex. A second thread repeatedly tries to acquire the mutex without blocking and immediately receives a busy result. Which strategy is generally more sensible under sustained contention?

A.Assume the mutex has been acquired despite the busy result
B.Use an appropriate blocking lock operation or a bounded retry strategy suited to the workload ✅
C.Unlock the mutex even though the thread did not acquire it
D.Remove all synchronization so both threads can proceed
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: A nonblocking lock attempt that reports the mutex is busy has not granted ownership. Under sustained contention, repeated immediate retries can waste CPU cycles, so blocking acquisition or carefully bounded retries may provide better progress.

Q5. A program replaces a mutex with a reader-writer lock because its shared data is read frequently and updated rarely. Which workload characteristic most strongly supports this decision?

A.Reads can safely overlap, while writes must remain exclusive and locking overhead is justified ✅
B.Every read changes the shared object
C.Writers must always execute concurrently with readers
D.The program requires every operation to be performed by one thread only
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: Reader-writer locks can improve concurrency when many operations are genuinely read-only and can overlap safely. They still require exclusive access for modifications, and their additional bookkeeping may provide little benefit if the critical section is very short or writes are frequent.

Q6. A producer modifies a queue while holding mutex M and signals a condition variable. A consumer uses the same mutex and waits while the queue is empty. What property makes this pattern reliable?

A.The signal alone stores the number of queued items
B.The producer and consumer must always execute on the same processor
C.The predicate is protected by the mutex, and the waiter checks it again after waking ✅
D.The condition variable automatically prevents every possible application error
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: The queue state is the durable record of available work, while the condition variable helps notify waiting consumers. Protecting the predicate with the same mutex and checking it in a loop prevents missed coordination and incorrect assumptions about the meaning of a wakeup.

Q7. A developer signals a condition variable before changing the shared predicate, without holding its associated mutex. A waiter may check the predicate and begin waiting during this sequence. What is the main concern?

A.The notification and predicate update are not coordinated safely, creating a potential lost-wakeup race ✅
B.The condition variable automatically converts the predicate to true
C.The mutex becomes recursive after the signal
D.The waiting thread is guaranteed to run before the producer
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: A condition-variable signal is not a durable stored event. If the predicate is updated outside the mutex protocol, a waiter can observe the old state and miss the notification before sleeping. Updating the predicate under the associated mutex and using a wait loop avoids this race.

Q8. A worker successfully decrements a semaphore representing an available resource, then exits before returning the permit. Which consequence should the designer anticipate?

A.The semaphore automatically identifies the dead worker and restores its permit
B.All remaining permits are doubled
C.The permit may remain consumed, reducing capacity and potentially leaving future workers blocked ✅
D.The semaphore becomes a robust mutex automatically
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: Semaphores generally do not track ownership in the same way as mutexes. If a process exits after consuming a permit without posting it, the resource count can remain reduced, potentially causing indefinite waiting when the remaining permits are exhausted.

Q9. A Solaris application uses a mutex to protect a shared counter, but the counter is also updated by an atomic instruction outside the mutex. Why can this mixed strategy be incorrect?

A.The atomic update does not follow the mutex protocol, so concurrent operations may still violate the intended compound invariant ✅
B.An atomic instruction automatically locks every mutex in the process
C.A mutex cannot protect a counter containing positive values
D.Solaris disables atomic instructions whenever a mutex exists
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: An atomic update may prevent lost updates to the counter itself, but it does not automatically coordinate with code that accesses related state under a separate mutex. All operations must follow a compatible synchronization design, especially when correctness depends on multiple variables or compound invariants.

Q10. A service has one heavily contended mutex guarding unrelated records. Profiling shows that threads wait far longer than they spend updating individual records. Which optimization is most directly worth evaluating?

A.Remove locking from all record updates
B.Increase the number of threads without changing the shared design
C.Partition the protected state or shorten the critical sections while preserving invariants ✅
D.Make the mutex remain locked after each update
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: A single mutex serializes operations even when different records could be modified independently. Splitting the state into appropriately designed locks or shortening the critical sections can reduce contention, but the redesign must preserve consistency when operations touch multiple records.

Q11. A developer initializes a process-private synchronization object in one process and expects an unrelated process to coordinate through its own separately allocated object. Why is the expectation wrong?

A.Separate objects do not coordinate merely because they have the same variable name; participants need a shared synchronization object and suitable process-sharing configuration ✅
B.All synchronization objects with matching names are automatically linked
C.A process-private mutex is always visible in every process
D.The operating system merges private memory after a process starts
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: Synchronization requires participants to refer to the same underlying object and use a compatible protocol. Separately allocated process-private objects remain distinct, so interprocess coordination requires an appropriate shared-memory arrangement and a synchronization primitive configured for that use.

Q12. A producer-consumer program has a shared queue and uses a condition variable to notify consumers. Why must the queue state remain the source of truth rather than the notification itself?

A.Condition variables store every item added to the queue
B.Every notification remains pending until consumed
C.A signal always means exactly one queue item is available
D.A signal can occur without a waiter, so consumers must inspect the protected queue predicate ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: Condition-variable signals notify waiting threads but are not a durable queue of events. A consumer may begin waiting after a signal has occurred, so the queue contents must record available work and be checked under the associated mutex.

Q13. A program uses a mutex for a critical section, but one thread unlocks it after another thread acquired it. What should the reviewer conclude?

A.This always improves fairness
B.Unlocking by a non-owner is not a valid general strategy for an ordinary mutex and may violate its rules ✅
C.The mutex automatically transfers ownership to the unlocking thread
D.The operation guarantees that no other thread can block
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Ordinary mutexes have ownership semantics, and a thread should follow the documented acquisition and release rules. Unlocking a mutex from a non-owner can be invalid or undefined depending on the type, undermining the mutual-exclusion protocol.

Q14. A thread acquires mutex A, updates one record, and then acquires mutex B to update another. Another thread acquires B before requesting A. What is the best preventive policy if both locks may be needed together?

A.Allow every thread to choose lock order dynamically
B.Release every lock before changing any data
C.Replace both mutexes with busy loops
D.Define and enforce one consistent global order for acquiring the two locks ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: A consistent global lock order prevents the two threads from forming a circular wait by requiring all participants to acquire the locks in the same direction. It does not eliminate all contention, but it directly addresses the deadlock risk created by inconsistent ordering.

Q15. A thread obtains a mutex, modifies two related fields, and releases the mutex. Another thread then obtains the same mutex before reading both fields. What guarantee is central to this pattern?

A.The two fields must always have identical values
B.The synchronization orders the protected updates before the subsequent protected reads ✅
C.The operating system never preempts the first thread
D.The mutex automatically rolls back partial updates after a crash
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: A mutex protects the critical section and establishes synchronization between a successful unlock and a subsequent successful lock. The second thread can observe the first thread's completed protected updates, assuming all relevant accesses obey the same locking discipline.

Q16. A program repeatedly polls a shared flag in a tight loop while waiting for another thread to finish work. CPU utilization remains high even though the waiting thread does no useful work. What is the most likely issue?

A.The flag is automatically a counting semaphore
B.The waiting thread has necessarily deadlocked every other thread
C.Busy-waiting is consuming CPU cycles and a blocking or event-driven strategy may be more efficient ✅
D.The operating system has disabled all interrupts
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: A tight polling loop can consume CPU resources while waiting for a state change, particularly when the wait is long. A condition variable, semaphore, or other appropriate blocking mechanism can let the waiting thread sleep until progress is possible.

Q17. A developer protects a data structure with a mutex but accesses one field outside the lock because the field is usually read-only. The writer occasionally updates that field under the mutex. What is the concern?

A.The unsynchronized read can race with the writer because all conflicting accesses must follow a compatible synchronization strategy ✅
B.A mutex prevents all writes to the structure
C.Read-only operations never need synchronization even when writers exist
D.The field becomes private to the writer automatically
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: A read that overlaps a write without appropriate synchronization can create a data race or inconsistent observation. The fact that reads usually occur without updates does not guarantee safety; immutable publication, atomic access, or consistent locking is required.

Q18. A developer wants to coordinate a producer and consumer using a shared count of available items. Which design principle prevents the count from drifting away from the actual queue contents?

A.Allow the producer to increment the count before deciding whether it inserted an item
B.Update the count and queue consistently under the same synchronization protocol, and check the count before consuming ✅
C.Let every consumer decrement the count twice to avoid underflow
D.Reset the count whenever a condition variable is signaled
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: The queue and its availability count represent related state and must be updated consistently. Protecting both under a suitable mutex and checking the count before removal prevents consumers from acting on stale information and helps maintain the invariant that the count matches available items.

Q19. A Solaris service has a semaphore limiting concurrent requests to eight. A bug posts the semaphore twice for each single successful wait. What failure can result?

A.The semaphore becomes a mutex with eight owners
B.Every request is automatically rejected
C.The permit count can exceed the intended capacity, allowing more than eight concurrent requests ✅
D.The operating system caps the semaphore count at the original value in every case
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: A semaphore represents available permits, so extra posts can inflate its count beyond the application's intended resource limit. Subsequent requests may acquire permits even when the real service capacity is exhausted, violating the concurrency bound.

Q20. A Solaris program uses a read-copy-update-style design to allow readers to access a configuration snapshot while a writer publishes a replacement. What additional concern remains essential?

A.Readers must be serialized by holding the writer's lock for every field access
B.The old snapshot must be reclaimed only when no reader can still access it ✅
C.The writer must modify both snapshots simultaneously
D.The configuration must never be read by more than one thread
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Snapshot publication can reduce reader contention, but safe reclamation remains essential. If a writer frees an old snapshot while a reader still references it, the reader can access invalid memory; the design needs a grace-period, reference-counting, or equivalent lifetime protocol.

Q21. A program uses a synchronization primitive that sleeps while waiting. Compared with continuous spinning, what is its main advantage during long contention periods?

A.It guarantees that no thread can be starved
B.It ensures every critical section is executed in constant time
C.It can let blocked threads stop consuming CPU cycles until they can make progress ✅
D.It removes the need to protect shared data
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: Blocking synchronization can suspend a waiting thread instead of repeatedly consuming processor time. This is often beneficial during long waits, although sleep and wakeup overhead means that blocking is not automatically superior for every extremely short critical section.

Q22. A thread is waiting for a resource, and the resource becomes available. Another thread repeatedly acquires it first, so the original thread never proceeds. Which problem does this describe most directly?

A.A lost update
B.A spurious wakeup
C.A successful barrier rendezvous
D.Starvation caused by unfair resource allocation ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: Starvation occurs when a thread is continually denied access to a resource despite ongoing system activity. Unlike deadlock, other threads may continue making progress, so fairness policies, bounded waiting, or a redesigned allocation strategy may be needed.

Q23. A process creates multiple threads that update a shared linked list. One thread inserts a node while another traverses the list, and neither uses synchronization. What is the most serious concern?

A.Concurrent mutation can expose inconsistent links or invalid memory accesses during traversal ✅
B.The list automatically becomes a circular list
C.The scheduler guarantees that traversal finishes before insertion starts
D.The list nodes become immutable after allocation
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: A linked-list insertion changes multiple pointer relationships, and an unsynchronized traversal can observe an intermediate state or access a node whose lifetime is not protected. A suitable locking or safe concurrent data-structure design must coordinate mutation, traversal, and memory reclamation.

Q24. A service uses a mutex to protect a critical section, but logging inside the section can block on a slow output device. Why should the design be reconsidered?

A.Logging automatically releases every held mutex
B.The slow operation extends lock hold time, increasing contention and potentially interacting badly with other locks ✅
C.A mutex cannot protect data if logging is enabled
D.The operating system guarantees that output never blocks
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Slow logging extends the duration for which the mutex is held, making other threads wait longer. Logging can also acquire other internal locks, creating lock-order risks, so moving slow work outside the critical section is often beneficial when correctness permits.

Q25. A monitoring graph shows throughput rising as thread count increases, then flattening while lock-wait time rises sharply. Which interpretation best fits the pattern?

A.Adding threads guarantees linear throughput indefinitely
B.The graph proves that the program has no shared mutable state
C.Lock contention is likely limiting scalability, so reducing serialized work may help more than adding threads ✅
D.The operating system has stopped scheduling all threads
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: Initial thread additions can improve parallelism, but a heavily contended lock creates a serialized bottleneck. Rising wait time and flattening throughput suggest that shortening critical sections, partitioning shared state, or reducing unnecessary synchronization may improve scalability.

Q26. A team needs a reusable synchronization point where several threads finish one phase before any proceeds to the next. Which primitive most directly models this requirement?

A.A single-owner mutex held for the entire program
B.A counter that is read without atomicity
C.A sleep interval chosen by estimating execution time
D.A barrier configured for the participating threads ✅
💡 Difficulty: medium | ✅ Correct: D

📖 Explanation: A barrier coordinates a group of participants at a phase boundary and releases them after the required number arrive. Unlike a guessed sleep interval or a single-owner mutex, it directly expresses the requirement that the group reach the synchronization point before continuing.

Q27. A developer concludes that because every critical section is protected by a mutex, the whole program cannot deadlock. Which reasoning correction is best?

A.Mutexes prevent data races but do not eliminate deadlocks caused by lock ordering, nested acquisition, or unreleased locks ✅
B.A deadlock is impossible whenever the program has fewer than ten threads
C.Deadlocks occur only when a semaphore is used
D.Every mutex automatically imposes a global lock order
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: Mutexes can prevent conflicting simultaneous access to protected data, but they do not guarantee progress. Deadlocks can still arise when locks are acquired in inconsistent orders, when a thread waits for a resource held by another, or when cleanup paths fail to release locks.
