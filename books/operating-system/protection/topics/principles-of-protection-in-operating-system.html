What is Principles of Protection in Operating System?

Definition:
The principles of protection establish design guidelines such as least privilege, separation of privilege, and open design to create secure and verifiable access control systems within an OS.

Example:
A web server runs with minimal permissions so that even if compromised, the attacker cannot access /etc/shadow \text{/etc/shadow} /etc/shadow or modify kernel files.

Reason:
Adhering to these principles minimizes the attack surface and limits the damage caused by software vulnerabilities or insider threats.

📝 All Principles of Protection in Operating System MCQs

Q1. What is the definition of the principle of least privilege?

A.Every user must have administrator rights at all times. ✅
B.Each program receives exactly the permissions needed to perform its intended function.
C.All processes share the same set of system privileges.
D.Privileges are granted only after a security audit.
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: The correct answer states that each program receives exactly the permissions needed for its function, which captures the essence of least privilege. Option A is wrong because it describes an opposite extreme where users have too many rights. Option C is inaccurate because it suggests uniform privileges for all processes, violating the principle. Option D adds an unrelated audit step; while audits are useful, they do not define the principle itself. This definition guides designers to limit access, reducing potential damage if a component is compromised.

Q2. Why does applying the principle of least privilege reduce the impact of a compromised component?

A.It isolates the component so that failure cannot affect other parts.
B.It grants the component full system access to detect problems quickly.
C.It forces the component to request additional privileges at runtime. ✅
D.It eliminates the need for authentication altogether.
💡 Difficulty: easy | ✅ Correct: C

📖 Explanation: Option C is correct because requiring a component to request extra privileges at runtime limits its default power and makes any misuse easier to detect, thereby reducing impact. Option A sounds plausible but isolation is a separate technique; least privilege does not automatically isolate components. Option B is the opposite of the principle, giving too much power. Option D removes authentication, which would increase risk, not decrease it. By limiting default rights, systems contain damage when a component is compromised.

Q3. A web server daemon runs with root privileges. An attacker exploits a bug and gains control of the daemon. Which outcome best illustrates the danger of not following least privilege?

A.The attacker can modify any file on the system, including system binaries. ✅
B.The attacker can only read the server’s log files.
C.The attacker can restart the web service but cannot affect other processes.
D.The attacker is limited to sending malformed HTTP responses.
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: Option A is correct because a daemon running as root can manipulate any system resource, demonstrating the severe damage possible without least privilege. Option B understates the impact; root access would allow more than just log reading. Option C limits the attacker’s power, which would be the case if the daemon had restricted rights. Option D also limits the effect. This scenario shows why designers should run services with the minimal necessary rights to contain breaches.

Q4. How does the principle of least privilege help contain the effects of a buffer‑overflow in a system daemon?

A.It ensures the daemon runs in a separate virtual machine.
B.It limits the daemon’s access rights so overwritten code cannot affect other resources. ✅
C.It disables all system calls while the daemon is active.
D.It encrypts the daemon’s stack to prevent code execution.
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: The correct answer is that limiting the daemon’s access rights (option B) prevents overwritten code from performing privileged actions, thereby containing the overflow. Option A describes isolation via virtualization, which is a separate defense layer. Option C would halt functionality entirely, which is impractical. Option D suggests encrypting the stack, which is not a typical mitigation for overflow. By granting only the necessary privileges, even if a buffer overflow occurs, the malicious code cannot exploit broader system capabilities.

Q5. A file system is being designed. Which permission scheme best follows the principle of least privilege?

A.All users get read/write/execute on every file.
B.Users receive read‑only access to public files and no access to private files. ✅
C.Each user is granted read/write only on files they own and read‑only on shared files.
D.All users are denied all permissions by default.
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: Option B correctly limits users to read‑only on public data and denies private data, embodying least privilege. Option A gives excessive rights, violating the principle. Option C grants write access to owned files, which may be appropriate, but also gives read‑only on shared files—still broader than necessary for many scenarios. Option D is overly restrictive, preventing legitimate use. The chosen scheme balances usability with minimal rights, reducing the chance that a compromised account can alter sensitive data.

Q6. A mobile app requests permission to access the camera, contacts, and location. Which response aligns with the principle of least privilege?

A.Grant all three permissions because the app may need them later.
B.Grant only camera access and deny contacts and location.
C.Deny all permissions until the user explicitly requests each one. ✅
D.Grant contacts and location but not camera, as camera is risky.
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: Option C follows least privilege by granting permissions only when the user explicitly requests them, ensuring the app receives no more access than necessary. Option A provides excessive rights upfront, increasing risk. Option B arbitrarily denies needed permissions without justification; the app might legitimately need contacts. Option D denies camera access, which could be essential for the app’s core function. By prompting the user for each permission, the system enforces minimal access and limits potential abuse.

Q7. How does the principle of least privilege differ from the need‑to‑know principle in security design?

A.Least privilege restricts system calls, while need‑to‑know restricts network traffic.
B.Least privilege limits user rights, whereas need‑to‑know limits information exposure to those who require it.
C.Both principles are identical and interchangeable.
D.Least privilege applies only to operating systems, need‑to‑know only to databases. ✅
💡 Difficulty: medium | ✅ Correct: D

📖 Explanation: Option D is correct: least privilege is a general design rule applied across operating systems, applications, and hardware, while need‑to‑know is a concept focused on restricting access to sensitive information, often in classified environments. Option A incorrectly ties each principle to specific technical mechanisms. Option B reverses the definitions; both actually limit access, but least privilege concerns rights, whereas need‑to‑know concerns information. Option C claims they are identical, which is false. Understanding this distinction helps architects apply the right control in the appropriate context.

Q8. A system call interface offers functions A, B, C, and D. Function C allows a process to change its own UID to any user ID. Which function most clearly violates the principle of least privilege?

A.Function A: read a file
B.Function B: write to a log ✅
C.Function C: change UID arbitrarily
D.Function D: query system time
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Function C is the correct answer because allowing a process to change its UID arbitrarily gives it far more authority than needed for most tasks, directly contravening least privilege. Function A merely reads a file, which is a limited operation. Function B writes to a log, a low‑impact activity. Function D merely queries the time, which does not affect permissions. By restricting UID changes to only privileged processes, the system reduces the risk of privilege escalation.

Q9. A daemon suffers a stack‑overflow that could allow code execution. Which mitigation aligns best with the principle of least privilege?

A.Run the daemon as root but enable address space layout randomization.
B.Compile the daemon with stack canaries and run it in a restricted user account. ✅
C.Disable all network interfaces while the daemon runs.
D.Allow the daemon to load any shared library it requests.
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Option B is correct because combining stack canaries (which detect overflow) with execution under a restricted user account limits the daemon’s privileges, embodying least privilege. Option A keeps the daemon as root, increasing risk despite ASLR. Option C removes network capability, which may not be necessary and does not address privilege levels. Option D permits unrestricted library loading, potentially introducing malicious code. Together, canaries and reduced privileges ensure that even if overflow occurs, the impact is constrained.

Q10. Why is granting administrative rights to every user contrary to the principle of least privilege, and how does it affect the system’s attack surface?

A.It simplifies user management and reduces the need for audits.
B.It expands the attack surface because any compromised account can perform any privileged operation.
C.It has no effect on security because users can still be monitored. ✅
D.It only affects performance, not security.
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: Option C is correct because giving every user admin rights dramatically enlarges the attack surface: a single compromised account can execute any privileged command, making the system far more vulnerable. Option A incorrectly suggests simplification is a benefit, ignoring security impact. Option B describes the correct effect but frames it as a benefit, which is misleading. Option D claims only performance impact, which is false. By limiting admin rights, the system reduces the number of potential entry points for attackers, adhering to least privilege.

Q11. In a cloud environment, Role X can read storage buckets, Role Y can write to compute instances, and Role Z can manage network firewalls. Which assignment best follows least privilege for a developer who only needs to deploy code?

A.Assign Role X and Role Y to the developer.
B.Assign Role Z only.
C.Assign Role Y only. ✅
D.Assign no role and rely on default permissions.
💡 Difficulty: hard | ✅ Correct: C

📖 Explanation: Option C is correct because deploying code typically requires write access to compute instances (Role Y) but not read access to storage or firewall management, thus granting the minimal necessary rights. Option A gives extra read permission on storage, which is unnecessary. Option B provides firewall control, far beyond the developer’s needs. Option D leaves the developer without needed privileges, preventing deployment. By assigning only Role Y, the system adheres to least privilege, limiting potential misuse.

Q12. How does the principle of least privilege influence the design of secure kernels?

A.Kernels are built to run all components with full system authority.
B.Kernels expose a single API that grants every process complete access.
C.Kernels enforce fine‑grained permission checks for each system call and isolate privileged code. ✅
D.Kernels rely on user‑space applications to enforce security policies.
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: Option C is correct because secure kernels implement fine‑grained checks for each system call and isolate privileged code, ensuring that processes receive only the rights they need. Option A suggests giving full authority, which directly violates least privilege. Option B describes a monolithic API that grants all access, also contrary to the principle. Option D shifts responsibility to user space, which is insufficient for kernel‑level security. By embedding least‑privilege checks within the kernel, designers limit the damage a compromised process can cause.
