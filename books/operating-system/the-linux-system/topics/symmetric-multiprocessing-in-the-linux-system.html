What is Symmetric multiprocessing in The Linux System?

Definition:
Symmetric multiprocessing in The Linux System treats all CPUs identically, allowing any processor to execute any task or handle interrupts with shared memory and coordinated scheduling across cores.

Example:
The scheduler migrates tasks between CPUs based on load balancing algorithms, while per-CPU variables avoid cache line contention for frequently updated counters like .

Reason:
SMP maximizes hardware utilization and scalability by distributing work evenly, but requires careful synchronization to maintain coherence and avoid bottlenecks in shared resources.

Q1. Which system call creates a new task that shares the same memory space when the CLONE_VM flag is used?

A.clone() ✅
B.fork()
C.exec()
D.wait()
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: The clone() system call creates a new task, and when the CLONE_VM flag is supplied the child shares the parent’s virtual memory area. Fork() always creates a separate memory space, exec() replaces the current process image, and wait() does not create new tasks. Because the memory is shared, both tasks see the same variables, which is essential for thread‑like behavior. This directly matches the definition of clone() with CLONE_VM.

Q2. Why can Linux treat processes and threads without a formal distinction?

A.Because Linux stores each part of a task’s context in separate substructures ✅
B.Because threads are inherently lightweight
C.Because the scheduler uses the same algorithm for both
D.Because fork() always shares resources
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: Linux separates a task’s context into independent structures such as the file‑system context, descriptor table, signal‑handler table, and virtual‑memory context. The main task structure only holds references to these substructures, so a task can share any of them with another task. This design lets a thread and a process appear the same to the kernel, unlike systems that keep a single monolithic process record.

Q3. How does sharing the file‑descriptor table (CLONE_FILES) affect communication between a parent and its child task?

A.It isolates file operations between them
B.Both tasks see the same file offsets and descriptor states ✅
C.It prevents signal delivery across tasks
D.It duplicates the memory space of each task
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: When CLONE_FILES is set, the parent and child use the same open‑file table, meaning any read/write operation updates the shared file offset. Consequently, data written by one task is immediately visible to the other, facilitating coordinated I/O. The other options describe effects of different flags: isolation occurs without CLONE_FILES, signal handling relates to CLONE_SIGHAND, and memory sharing concerns CLONE_VM.

Q4. A developer wants a thread that shares memory and open files but keeps its own signal handlers. Which flag combination should be used?

A.CLONE_VM | CLONE_FILES ✅
B.CLONE_FS | CLONE_SIGHAND
C.CLONE_VM | CLONE_SIGHAND
D.CLONE_FILES | CLONE_SIGHAND
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: CLONE_VM shares the virtual memory area, and CLONE_FILES shares the open‑file table, giving the child the same memory and file descriptors as the parent. By omitting CLONE_SIGHAND, each task keeps its own signal‑handler table, satisfying the requirement. CLONE_FS would share the current working directory, which isn’t needed, and CLONE_SIGHAND would force shared handlers, contrary to the goal.

Q5. A parent process opens a log file, then calls clone() with CLONE_FILES. The child writes a message, and the parent reads from the file descriptor afterward. What is the most likely outcome?

A.The parent sees the child’s write because the file offset is shared ✅
B.The parent sees nothing because offsets are independent
C.The child gets a separate file descriptor that the parent cannot access
D.The call fails with an error
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: With CLONE_FILES, the parent and child share the same open‑file table, including the file offset. When the child writes, the offset advances, so a subsequent read by the parent starts from the new position and can retrieve the written data. If the offsets were independent, the parent would not see the write, but sharing causes the observed behavior.

Q6. A programmer uses clone() without any flags to run parallel tasks, then modifies a global counter in the child expecting isolation. What problem is most likely to occur?

A.The child sees a separate copy of the counter
B.The child shares memory, causing a race condition on the counter ✅
C.The child cannot access the counter at all
D.The child process crashes immediately
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: When no flags are supplied, clone() behaves like fork(): the child receives a copy‑on‑write view of the parent’s memory. However, any write to a global variable forces a private copy, so the child’s update does not affect the parent, leading to inconsistent results if the programmer assumes isolation. The real issue is that memory is not truly shared, producing race‑like behavior rather than isolation.

Q7. What does the CLONE_FS flag cause the child task to share with its parent?

A.The current working directory and other filesystem information ✅
B.The virtual memory space
C.The signal‑handler table
D.The set of open files
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: CLONE_FS explicitly shares the filesystem context, meaning both tasks see the same current working directory, root directory, and mount points. This allows them to operate on the same pathnames without changing each other’s view. The other options correspond to different flags: CLONE_VM shares memory, CLONE_SIGHAND shares signal handlers, and CLONE_FILES shares open files.

Q8. A server creates a new task for each client connection using clone() with only CLONE_FILES. After many connections, memory usage spikes. Which flag should be added to reduce memory consumption?

A.CLONE_VM ✅
B.CLONE_FS
C.CLONE_SIGHAND
D.CLONE_FILES
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: Using only CLONE_FILES means each new task gets its own virtual memory area, so the memory footprint grows with every connection. Adding CLONE_VM makes all tasks share the same memory space, dramatically lowering per‑task memory usage. The other flags affect filesystem context, signal handling, or file descriptor sharing, which do not directly impact memory consumption.
