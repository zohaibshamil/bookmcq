📝 Passing of data among processes in The Linux System (8 MCQs)

Definition of Passing of data among processes in The Linux System:

Passing data among processes in Linux is achieved through interprocess communication mechanisms that exchange information between separate execution environments. These mechanisms include pipes, message queues, shared memory, and sockets. Without IPC, independent processes would require indirect file-based methods or external coordination to exchange information.

How Passing of data among processes in The Linux System Works:

The communicating processes select a compatible IPC mechanism. One process writes data to the communication channel, while another reads it. Shared memory provides a common region, but cooperating processes must add synchronization to prevent conflicting access.

Passing of data among processes in The Linux System Example:

Process A writes the text hello into a pipe, and process B reads from its receiving end. The pipe transfers five data bytes through a kernel-managed communication channel between the processes.

Why Passing of data among processes in The Linux System Matters:

IPC enables efficient cooperation compared with repeatedly writing temporary files. Pipes suit streams, message queues preserve message boundaries, shared memory supports fast data sharing, and sockets support local or network communication.

Common Misconceptions About Passing of data among processes in The Linux System:

'Shared memory automatically synchronizes processes' ignores race conditions. 'Pipes preserve individual message boundaries' overlooks their byte-stream behavior. 'Sockets require separate computers' ignores local Unix domain sockets.

Exam Tips for Passing of data among processes in The Linux System:

Compare pipes, FIFOs, message queues, shared memory, and sockets. Trace data movement between processes. Exams commonly ask about IPC selection, synchronization requirements, communication direction, and performance trade-offs.

Key Terms in Passing of data among processes in The Linux System:

  • IPC - Mechanisms for communication among processes.
  • Pipe - Kernel-managed byte-stream communication channel.
  • Message queue - IPC mechanism preserving separate messages.
  • Shared memory - Memory region accessible to multiple processes.
  • Unix domain socket - Local communication endpoint between processes.

📝 All Passing of data among processes in The Linux System MCQs

Q1. What is the primary characteristic of a Unix signal in interprocess communication?

A.It carries arbitrary data between processes
B.It only indicates that an event has occurred without carrying data ✅
C.It synchronizes access to shared memory
D.It establishes a persistent communication channel
💡 Difficulty: easy | ✅ Correct: B

📖 Explanation: The correct answer is B because a signal merely notifies a process that something happened; it does not include additional information. Option A is wrong since signals cannot transport arbitrary data. Option C describes synchronization primitives, not signals. Option D refers to a communication channel like a socket, which is unrelated. Understanding that signals are simple notifications helps students choose the right mechanism when only event awareness is needed.

Q2. In Linux kernel programming, what best describes a wait queue?

A.A list of processes that are ready to run
B.A mechanism that stores messages for later retrieval
C.A structure where processes sleep until a specific event occurs ✅
D.A type of semaphore used for mutual exclusion
💡 Difficulty: easy | ✅ Correct: C

📖 Explanation: Option C is correct because a wait queue holds processes that have voluntarily blocked and will be awakened once a particular event finishes. Option A describes the run queue, not a wait queue. Option B sounds like a message queue, which holds data, not sleeping processes. Option D is about semaphores, which control access rather than block for events. Recognizing the purpose of wait queues is essential for kernel‑mode synchronization.

Q3. Why does the Linux kernel avoid using signals to notify kernel‑mode processes about events?

A.Signals are too slow for kernel operations
B.Signals cannot be delivered to processes in kernel mode
C.Kernel‑mode processes rely on wait queues and scheduling states for event notification ✅
D.Signals are only for user‑space debugging
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: The kernel chooses option C because kernel‑mode code uses wait queues and scheduling states to sleep and wake, providing efficient event handling without the overhead of signals. Option A is inaccurate; speed is not the main issue. Option B is false—signals can be sent to any process, but the kernel prefers other mechanisms for internal events. Option D mischaracterizes signals, which also serve user‑space purposes. Knowing the kernel's preferred mechanisms guides developers in writing efficient kernel code.

Q4. A server process needs to be notified when incoming data is ready on a network socket. Which IPC mechanism should it rely on to efficiently wait for this event?

A.POSIX signals
B.Wait queue mechanisms provided by the kernel ✅
C.Shared memory segment
D.Message queue
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: Option B is correct because the kernel places the server process on a wait queue associated with the socket, allowing it to sleep until data arrives, which is more efficient than polling or using signals that cannot carry the data. Option A (signals) cannot convey the arrival of data and would require extra handling. Option C (shared memory) is for data exchange, not event notification. Option D (message queue) adds unnecessary overhead for a simple readiness event. Selecting wait queues matches the kernel’s design for asynchronous I/O.

Q5. When a parent process wants to detect that one of its child processes has finished execution, which signal is typically delivered by the kernel?

A.SIGKILL
B.SIGSTOP
C.SIGCHLD ✅
D.SIGUSR1
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: The correct answer is C because the kernel sends SIGCHLD to the parent whenever a child terminates, allowing the parent to reap the child’s status. SIGKILL (A) forcibly terminates a process and is not used for notifications. SIGSTOP (B) stops a process, not a termination notice. SIGUSR1 (D) is a user‑defined signal without a specific meaning for child termination. Understanding SIGCHLD helps developers implement proper child‑process handling and resource cleanup.

Q6. Three processes issue read requests for the same file on disk. After the I/O completes, which statement accurately reflects how the kernel wakes the waiting processes?

A.Only the first process on the wait queue is awakened
B.All processes on the wait queue are awakened simultaneously ✅
C.The kernel selects a random process to wake
D.Processes must poll the disk repeatedly until data arrives
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Option B is correct because the kernel’s wait queue mechanism awakens every process that was sleeping on that event once the disk I/O finishes, ensuring all readers can proceed. Option A is wrong; the kernel does not limit wake‑ups to a single process. Option C is inaccurate; wake‑ups are not random. Option D describes inefficient polling, which the wait queue avoids. This behavior demonstrates how wait queues enable coordinated access to shared resources.

Q7. A programmer needs to transfer a small amount of data from one user process to another without creating a temporary file. Which IPC method is most suitable given that signals cannot carry payloads?

A.Signal with custom data ✅
B.Pipe
C.Semaphore
D.Shared memory
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: The best choice is B because a pipe provides a unidirectional byte stream that can carry the required data between processes without needing a file. Option A is impossible since signals lack payload capacity. Option C (semaphore) only synchronizes access and does not transmit data. Option D (shared memory) could work but requires additional coordination and is more complex for small transfers. Knowing that pipes are designed for simple data flow helps developers select the most straightforward solution.

Q8. How do signals and wait queues complement each other in Linux interprocess communication?

A.Signals replace wait queues for all events
B.Wait queues are used only in user space, while signals operate in kernel space
C.Signals provide simple notifications, while wait queues allow processes to sleep until complex events are satisfied ✅
D.Both mechanisms are identical in functionality
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: Option C correctly captures the relationship: signals give a lightweight notification that something happened, whereas wait queues let a process block until a specific condition, such as I/O completion, is met. Option A is false because signals cannot replace the blocking behavior of wait queues. Option B misstates the domain of each mechanism; both exist in kernel space. Option D incorrectly claims they are the same. Understanding this complementarity lets developers combine both tools for efficient event handling.
