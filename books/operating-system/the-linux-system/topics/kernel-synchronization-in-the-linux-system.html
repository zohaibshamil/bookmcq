What is Kernel synchronization in The Linux System?

Definition:
Kernel synchronization in The Linux System employs spinlocks, mutexes, semaphores, RCU, and atomic operations to protect shared data structures from concurrent access races in SMP and preemptible contexts.

Example:
A spinlock protects a linked list traversal in interrupt context where sleeping is forbidden, using to disable local interrupts and prevent deadlocks.

Reason:
Unprotected concurrent modifications corrupt kernel state leading to crashes or security vulnerabilities; appropriate synchronization primitives balance safety with performance across diverse execution contexts.

📝 All Kernel synchronization in The Linux System MCQs

Q1. A program creates two tasks using clone() with flags CLONE_FS and CLONE_VM only. Which resource is NOT shared between the parent and child?

A.Current working directory
B.Memory space
C.Open file descriptors
D.Signal handlers ✅
💡 Difficulty: easy | ✅ Correct: D

📖 Explanation: The CLONE_FS flag shares the current working directory, and CLONE_VM shares the memory space, so both of those are common. Open file descriptors are shared only when CLONE_FILES is set, which is absent here, so they remain separate. Signal handlers are shared only with CLONE_SIGHAND, which also isn’t set, making them the only resource not shared. This helps developers decide which flag to add when they need specific isolation.

Q2. What does the CLONE_FILES flag cause the child task to share with its parent?

A.File descriptor table ✅
B.Virtual memory
C.Signal handlers
D.Process ID
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: When CLONE_FILES is specified, the kernel makes the child use the same files_struct as the parent, meaning the file descriptor table is shared. Virtual memory requires CLONE_VM, signal handlers need CLONE_SIGHAND, and the process identifier is always unique. Knowing this lets programmers choose CLONE_FILES when they want threads to operate on the same set of open files.

Q3. Which system call in Linux creates a new task that can share resources with its parent?

A.exec()
B.fork()
C.clone() ✅
D.wait()
💡 Difficulty: easy | ✅ Correct: C

📖 Explanation: clone() accepts a mask of flags that decide which resources—such as memory, file system, or file descriptors—are shared with the parent. fork() always creates a separate copy of resources, while exec() replaces the current process image, and wait() merely waits for a child to finish. Therefore, clone() is the call that enables selective sharing, essential for building user‑level threads.

Q4. A server program uses clone() with CLONE_VM, CLONE_FS, CLONE_FILES, but not CLONE_SIGHAND. After creating a child task, the parent changes its signal handler for SIGTERM. What happens in the child?

A.Child receives new handler
B.Child retains old handler ✅
C.Child crashes
D.Child gets no signal
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: Because CLONE_SIGHAND was not set, the child has its own signal‑handler table. Changing the handler in the parent therefore does not affect the child, which continues to use the handler that existed at creation time. This isolation is useful when a thread must handle signals differently from the rest of the program.

Q5. A developer wants two threads to operate on the same memory but have independent file descriptor tables. Which combination of flags should be used?

A.CLONE_VM | CLONE_FILES ✅
B.CLONE_VM only
C.CLONE_VM | CLONE_FS
D.CLONE_VM | CLONE_SIGHAND
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: The requirement is to share memory (CLONE_VM) while keeping file descriptors separate, so CLONE_FILES must be omitted. The simplest flag set that meets this is just CLONE_VM, which gives a shared address space and independent file‑descriptor tables. Adding extra flags like CLONE_FS or CLONE_SIGHAND would share additional resources that are not needed.

Q6. If a task created with clone() shares CLONE_VM and later calls execve(), what happens to the shared memory region?

A.It remains shared
B.It becomes private
C.It is duplicated ✅
D.It is freed
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: execve() replaces the calling task’s entire address space with a new program image, discarding the previous memory mapping. Consequently, any memory that was previously shared via CLONE_VM is no longer visible to the other task, effectively making the region private to the calling task after the exec. This behavior prevents unintended sharing after a program change.

Q7. Why does Linux treat processes and threads as tasks rather than separate entities?

A.To simplify scheduling
B.Because tasks share kernel data structures
C.Because context is stored in independent subcontexts ✅
D.To improve security
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: Linux stores each component of a process—such as its memory, file system, and signal tables—in separate kernel structures. The main task_struct then points to these subcontexts. This design lets the kernel treat both processes and threads uniformly as tasks, because sharing or isolating any component is just a matter of pointing to the same or different substructures.

Q8. How does the presence of independent subcontexts enable selective sharing of resources?

A.By copying all resources
B.By allowing flags to point to same structures
C.By merging processes
D.By disabling multitasking ✅
💡 Difficulty: medium | ✅ Correct: D

📖 Explanation: When a task is created, the clone() flags tell the kernel which subcontext pointers (e.g., to the memory descriptor or file‑descriptor table) should be duplicated and which should be shared. This pointer‑level control means the kernel can mix shared and private resources without merging entire processes, giving fine‑grained control over what is common between tasks.

Q9. Which flag indicates that the child’s file‑system information will be shared with the parent?

A.CLONE_SIGHAND
B.CLONE_FS ✅
C.CLONE_VM
D.CLONE_FILES
💡 Difficulty: easy | ✅ Correct: B

📖 Explanation: CLONE_FS explicitly tells the kernel to let the new task use the same struct path that stores the current working directory and other file‑system state. Without this flag, the child would receive a copy of the file‑system context, making its cwd independent. Knowing the flag semantics helps developers decide when two tasks should see the same directory hierarchy.

Q10. A multi‑threaded database server uses clone() with CLONE_VM, CLONE_FS, CLONE_FILES, and CLONE_SIGHAND. After a bug, one thread modifies the file descriptor table, causing other threads to lose access to a log file. Which flag’s sharing caused this side effect?

A.CLONE_VM
B.CLONE_FS
C.CLONE_FILES ✅
D.CLONE_SIGHAND
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: The problem arises because CLONE_FILES makes all tasks share the same files_struct, which contains the file descriptor table. When one thread closes or alters a descriptor, the change is visible to every other thread that shares that table. The other flags affect memory, cwd, and signal handlers, none of which impact file descriptor visibility.

Q11. Consider two tasks created with clone() using only CLONE_SIGHAND. The parent changes its current working directory using chdir(). What is the effect on the child?

A.Child sees new cwd
B.Child sees old cwd ✅
C.Child crashes
D.Child cannot change cwd
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: Since only CLONE_SIGHAND was set, the child has its own file‑system context. Changing the directory in the parent therefore does not propagate to the child, which continues to operate in the directory that existed at the time of creation. This isolation is useful when tasks need different working directories while sharing signal handling.

Q12. A program creates a child task with clone() passing CLONE_VM | CLONE_FS | CLONE_SIGHAND, but not CLONE_FILES. The child opens a new file descriptor. How does this affect the parent?

A.Parent sees same descriptor
B.Parent sees none ✅
C.Parent sees descriptor but cannot use
D.Parent sees descriptor but it is closed when child exits
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Because CLONE_FILES was omitted, the child receives its own files_struct. Opening a descriptor modifies only that private table, leaving the parent’s descriptor table untouched. Consequently, the parent does not see the new descriptor at all. This behavior is crucial when a thread must work with temporary files without exposing them to the rest of the process.

Q13. A process spawns three tasks with different flag sets: Task A shares CLONE_VM | CLONE_FS, Task B shares CLONE_VM | CLONE_SIGHAND, Task C shares CLONE_FILES. Which pair of tasks can safely modify the same global variable without causing race conditions due to separate memory spaces?

A.A and B
B.A and C
C.B and C
D.None of the above ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: Only tasks that do NOT share CLONE_VM have separate address spaces, meaning each has its own copy of any global variable. Task C does not share memory with either A or B, but A and B both share CLONE_VM, so they would see the same variable and could race. Since no pair has both separate memory and a common variable, none can safely modify the same global without additional synchronization.

Q14. Explain how the Linux kernel's use of independent subcontexts for file‑system, memory, and signal handling influences the design of user‑space threading libraries.

A.It forces libraries to implement their own scheduling
B.It allows libraries to map threads to tasks with selective sharing ✅
C.It eliminates need for mutexes
D.It requires libraries to avoid clone()
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Thread libraries can create lightweight threads by invoking clone() with a chosen subset of flags, letting them share memory, file descriptors, or signal handlers as needed. The independent subcontexts give the kernel the flexibility to expose only the resources a library wants to share, simplifying the implementation of user‑level thread management while still providing isolation where desired.

Q15. What is the primary advantage of using clone() with a subset of flags over creating separate processes with fork() in terms of synchronization overhead?

A.Higher memory usage
B.Reduced context‑switch cost ✅
C.Increased security
D.No advantage
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: When tasks share memory via CLONE_VM, they avoid the costly copying of pages that fork() would perform (even with copy‑on‑write). This reduces the amount of data the kernel must manage during a context switch, leading to faster inter‑task communication and lower latency for synchronization primitives. The trade‑off is that shared resources must be protected by user‑level synchronization.

Q16. A developer writes a program that creates a child via clone() with CLONE_VM | CLONE_FS | CLONE_FILES. After the child exits, the parent attempts to read from a file descriptor that the child closed. What is the expected behavior?

A.Read succeeds because descriptor is shared
B.Read fails because descriptor was closed for both ✅
C.Parent gets segmentation fault
D.Parent receives SIGPIPE
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Because CLONE_FILES makes the file‑descriptor table shared, closing a descriptor in the child removes it for all tasks that share that table. When the parent later attempts to read from the now‑closed descriptor, the read call fails with an error (typically EBADF). This illustrates the need for careful coordination when sharing file descriptors.

Q17. Which kernel data structure holds the file‑descriptor table that can be shared between tasks?

A.task_struct
B.mm_struct
C.files_struct ✅
D.signal_struct
💡 Difficulty: medium | ✅ Correct: C

📖 Explanation: The files_struct is the kernel object that contains the array of open file descriptors for a task. When CLONE_FILES is used, multiple task_structs point to the same files_struct, enabling descriptor sharing. The other structures store scheduling information (task_struct), memory mappings (mm_struct), or signal handlers (signal_struct). Understanding this mapping helps developers predict the impact of flag choices.

Q18. When two tasks share CLONE_SIGHAND but not CLONE_VM, how are signal handlers stored?

A.In separate copies
B.In a common signal_struct ✅
C.In each task's mm_struct
D.In the process ID table
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: CLONE_SIGHAND makes the tasks point to the same signal_struct, which contains the array of signal handlers. Because CLONE_VM is not set, each task still has its own memory space, but they share the same handler definitions. This arrangement allows different threads to react to signals uniformly while keeping their memory isolated.
