Q1. In what year did the MULTICS operating system development begin?

🔹 A. 1960
🔹 B. 1965
🔹 C. 1970
🔹 D. 1975

💡 Difficulty: easy | ✅ Correct: B

📖 Explanation:

The development of MULTICS started in 1965 at MIT as a pioneering utility OS for large mainframes. This date is well documented in computing history. Option B is correct because it matches that start year. Option A (1960) is too early, preceding the project’s planning phase. Option C (1970) refers to the period when UNIX was being designed, not MULTICS. Option D (1975) is after MULTICS had already been implemented. Knowing the correct year helps students place the timeline of feature migration accurately.

Q2. Why is feature migration important for operating system design across different computer classes?

🔹 A. It allows proven concepts to be reused on smaller devices, reducing development effort.
🔹 B. It guarantees backward compatibility with legacy hardware only.
🔹 C. It limits innovation to mainframe environments.
🔹 D. It forces all systems to use the same hardware architecture.

💡 Difficulty: easy | ✅ Correct: A

📖 Explanation:

Feature migration matters because it lets proven operating‑system ideas move from powerful mainframes to smaller, cheaper computers, saving development time and leveraging existing reliability. Option A is correct as it describes reuse of concepts across device classes. Option B is wrong; backward compatibility addresses old hardware, not the spread of new ideas. Option C incorrectly claims migration limits innovation, while history shows it often spurs new designs. Option D is false because migration does not force identical hardware. Understanding this principle explains why many desktop features now appear on smartphones.

Q3. How did the design principles of MULTICS influence the architecture of UNIX?

🔹 A. By copying its graphical user interface directly.
🔹 B. By adopting its file system hierarchy unchanged.
🔹 C. By inheriting concepts such as hierarchical file system, process isolation, and security rings.
🔹 D. By using the same hardware platform.

💡 Difficulty: medium | ✅ Correct: C

📖 Explanation:

MULTICS introduced hierarchical file systems, process isolation via security rings, and a modular kernel, which UNIX adopted and simplified for smaller hardware. Option C correctly captures these shared concepts. Option A is wrong because UNIX did not copy MULTICS’s graphical interface; early UNIX was text‑based. Option B is inaccurate; while UNIX kept a hierarchical file system, it was not a direct copy of MULTICS’s layout. Option D is false because UNIX was designed for the PDP‑11, a different platform. Recognizing these influences shows how core ideas travel across system generations.

Q4. A microcontroller-based device needs fault tolerance similar to mainframe systems. Which OS feature, originally from large systems, should be implemented?

🔹 A. Round-robin scheduling
🔹 B. Virtual memory paging
🔹 C. Simple cooperative multitasking
🔹 D. Kernel-level checkpoint/restart

💡 Difficulty: medium | ✅ Correct: D

📖 Explanation:

Fault tolerance on mainframes often uses checkpoint/restart, where the system periodically saves its state and can recover after a failure. Implementing a kernel‑level checkpoint/restart mechanism (Option D) brings that capability to a microcontroller, matching the original goal. Option A (round‑robin scheduling) improves CPU sharing but does not address failures. Option B (virtual memory) helps with memory management, not reliability. Option C (cooperative multitasking) is less robust than checkpointing. Applying the checkpoint idea demonstrates how a high‑level feature can be scaled down for embedded devices.

Q5. An old mainframe batch job is being moved to a modern smartphone. Which migration step is most appropriate?

🔹 A. Rewrite the job in assembly language for ARM.
🔹 B. Encapsulate the job logic in a background service using an OS API that provides similar batch processing semantics.
🔹 C. Run the original mainframe binary under an emulator without changes.
🔹 D. Convert the job to a web application without considering OS features.

💡 Difficulty: medium | ✅ Correct: B

📖 Explanation:

When moving a batch job from a mainframe to a smartphone, preserving the job’s scheduling semantics while using modern APIs is key. Encapsulating the logic in a background service that offers similar batch processing (Option B) achieves this. Option A (rewriting in ARM assembly) is unnecessary and error‑prone. Option C (running the binary under an emulator) may work but ignores platform integration and performance. Option D (converting to a web app) discards the OS‑level batch nature. The chosen approach shows how migration keeps functional intent while adapting to new environments.

Q6. Why have some mainframe features not migrated to handheld devices despite success on desktops?

🔹 A. High resource requirements and limited power make them impractical for handhelds.
🔹 B. Handheld users prefer command-line interfaces.
🔹 C. Desktop OS vendors block feature sharing.
🔹 D. Handheld hardware uses the same architecture as mainframes.

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation:

Many mainframe features require substantial memory, processing power, or specialized hardware, making them unsuitable for handhelds that have tight power budgets and limited resources. Option A correctly identifies these constraints. Option B incorrectly assumes handhelds favor command‑line interfaces, which is not the primary limitation. Option C suggests vendor blocking, which is not a technical barrier. Option D claims handheld hardware mirrors mainframe architecture, which is false. Understanding resource constraints explains why certain robust features remain on larger systems and guides designers toward lightweight alternatives.

Q7. Given the historical pattern where multi‑user networking, fault tolerance, and virtualization moved from mainframes to desktops, which emerging feature is most likely to appear on IoT devices next?

🔹 A. Quantum computing support
🔹 B. High‑resolution graphical shells
🔹 C. Container‑based isolation similar to modern cloud platforms
🔹 D. Full‑disk encryption using hardware TPMs

💡 Difficulty: hard | ✅ Correct: C

📖 Explanation:

The migration pattern shows that complex capabilities such as multi‑user networking, fault tolerance, and virtualization moved from mainframes to desktops before reaching smartphones. The next logical step is container‑based isolation, which provides lightweight, secure environments similar to cloud platforms and is beginning to appear on embedded devices. Option C captures this prediction. Option A (quantum support) is far beyond current hardware. Option B (high‑resolution shells) already exists on desktops. Option D (full‑disk encryption) is already common on smartphones. Recognizing the trend helps anticipate future OS feature adoption on IoT.

Q8. An educational institution wants to provide a shared, networked multi‑user environment on low‑cost tablets. Which migrated OS feature should they prioritize to ensure each student gets an isolated session?

🔹 A. Single‑user login only
🔹 B. Time‑shared multitasking without user isolation
🔹 C. User namespaces and lightweight process isolation
🔹 D. Batch processing without interactivity

💡 Difficulty: medium | ✅ Correct: C

📖 Explanation:

Providing each student with an isolated session on shared tablets requires a mechanism that separates processes and resources per user. User namespaces and lightweight process isolation (Option C) deliver this separation while keeping overhead low. Option A (single‑user login only) would not allow multiple concurrent sessions. Option B (time‑shared multitasking without isolation) risks data leakage between students. Option D (batch processing without interactivity) does not meet the need for interactive use. Selecting the correct feature illustrates how migrated OS concepts enable secure multi‑user environments on inexpensive hardware.
