What is Inverted page tables in Virtual Memory?

Definition:
Inverted page tables store one entry per physical frame instead of per virtual page, with entries containing (PID, virtual page number) to resolve translations via hashing or chaining.

Example:
To translate , hash function indexes IPT; collision resolved by chain until matching entry found or miss declared.

Reason:
Dramatically reduces memory overhead for page tables in systems with large virtual address spaces, though increases translation complexity and TLB miss penalty.

📝 All Inverted page tables in Virtual Memory MCQs

Q1. A system uses an inverted page table that stores one entry per physical frame. When a process requests a virtual address, the OS must locate the corresponding frame. Which method is most efficient for finding the frame entry?

A.Scan the entire table sequentially ✅
B.Apply a hash function to the (process‑ID, page‑number) pair
C.Maintain a separate per‑process page table
D.Use a binary‑search tree keyed by virtual page numbers
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: The hash‑based lookup is efficient because the inverted table has one entry per frame, not per process. Hashing the (PID, page) pair maps directly to a table slot, giving average‑case O(1) time. Scanning the whole table (A) is O(n) and slow, while per‑process tables (C) defeat the purpose of an inverted design. A binary‑search tree (D) would require ordering and still be O(log n), slower than hashing.

Q2. What best describes an inverted page table?

A.A table with one entry for each physical frame ✅
B.A table with one entry for each virtual page of every process
C.A table that maps processes directly to swap space
D.A table that stores only dirty bits for pages
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: An inverted page table contains a single entry for every physical frame, recording which virtual page (identified by process ID and page number) currently occupies that frame. This contrasts with conventional page tables that have an entry per virtual page of each process. Options B, C, and D describe unrelated structures: per‑process page tables, swap‑space mappings, and a dirty‑bit array, respectively.

Q3. Why does an inverted page table typically use less memory than separate conventional page tables for many processes?

A.It stores one entry per physical frame rather than per virtual page
B.It compresses page numbers into shorter codes ✅
C.It eliminates the need for valid‑bit flags
D.It reuses entries for shared libraries
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: Because the inverted table has a single entry for each physical frame, the total number of entries equals the number of frames, independent of how many processes exist. Conventional tables allocate an entry for every virtual page of each process, which can explode as the number of processes grows. Compression (B) and flag elimination (C) provide modest savings, and shared‑library reuse (D) is a separate concern.

Q6. Process P1 and Process P2 both request virtual page 5. In an inverted page table, how is the entry for P2’s request distinguished from P1’s?

A.Both share the same table entry ✅
B.Each process has a separate entry identified by its process ID
C.The OS raises an error because the page is already mapped
D.A new physical frame is allocated automatically
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: The inverted table stores entries keyed by both the process identifier and the page number, so P1’s request and P2’s request map to distinct entries even though the virtual page numbers are identical. Sharing the same entry (A) would cause incorrect address translation, and an error (C) or automatic allocation (D) are not part of the lookup mechanism.

Q7. A system suffers a high page‑fault rate. Which combination is most likely to lower the fault rate while keeping memory overhead reasonable?

A.Switch to an inverted page table without any cache ✅
B.Use an inverted page table together with a translation look‑aside buffer (TLB)
C.Replace the inverted page table with a conventional table and increase page size
D.Adopt an inverted page table with double‑hashing but no TLB
💡 Difficulty: hard | ✅ Correct: A

📖 Explanation: An inverted page table reduces memory overhead, but lookups can be slower. Adding a TLB caches recent translations, bringing average lookup time close to that of conventional tables while preserving the space savings of the inverted design. Option A lacks the speed benefit, C re‑introduces large tables, and D adds hashing complexity without the caching advantage.

Q8. When handling collisions in an inverted page table, why might chaining be preferred over open addressing in a system with many processes but few pages per process?

A.Chaining uses less memory than open addressing
B.Chaining allows variable‑length lists, reducing wasted slots ✅
C.Open addressing provides faster lookups in this scenario
D.Both methods perform identically, so choice is irrelevant
💡 Difficulty: hard | ✅ Correct: B

📖 Explanation: Chaining stores colliding entries in linked lists attached to each bucket, so the table does not need to reserve extra slots for potential collisions. In a workload with many processes (many distinct keys) but few pages per process, collisions are relatively rare, and the overhead of maintaining pointers is minimal. Open addressing would require probing many empty slots, wasting memory and increasing latency. Therefore, chaining offers better space efficiency and comparable lookup speed in this context.
