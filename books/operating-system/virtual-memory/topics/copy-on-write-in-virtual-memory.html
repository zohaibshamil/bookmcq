Q1. What does the term copy‑on‑write (COW) describe in virtual memory management?

🔹 A. Immediately duplicating all pages for a new process
🔹 B. Sharing pages until a write occurs, then copying
🔹 C. Mapping files read‑only only
🔹 D. Allocating physical memory for each virtual page

💡 Difficulty: easy | ✅ Correct: C

📖 Explanation:

Copy‑on‑write means that when two processes reference the same physical page, the OS lets them share it read‑only. Only when one process attempts to modify the page does the kernel allocate a new physical page and copy the original contents, giving the writer a private copy. Options A and D describe eager duplication, which COW explicitly avoids. Option C is unrelated because COW works for writable pages, not just read‑only mappings. This behavior saves memory until a write is needed.

Q2. Why are sparse address spaces advantageous when loading shared libraries?

🔹 A. They eliminate the need for page tables
🔹 B. They allow unused regions to consume no physical memory until needed
🔹 C. They guarantee that heap and stack never collide
🔹 D. They force all libraries to be loaded at the same address

💡 Difficulty: easy | ✅ Correct: A

📖 Explanation:

Sparse address spaces contain large unmapped holes between allocated regions such as the heap and stack. Those holes occupy virtual addresses but no physical memory, so the system only allocates pages when a process actually grows into the hole. This saves RAM and reduces paging overhead. Option A is false because page tables are still required. Option C is unrelated; collisions are prevented by separate growth directions, not by sparsity. Option D is incorrect because libraries can be loaded at different addresses using relocation.

Q3. Process A calls fork(), creating Process B. Both have a read‑only mapping of libX.so. Immediately after fork, Process B writes to a global variable in libX. Which mechanism handles the write?

🔹 A. Demand paging loads a new copy of the entire library
🔹 B. Copy‑on‑write creates a private copy of the modified page
🔹 C. The OS swaps out the whole library
🔹 D. The write is ignored

💡 Difficulty: medium | ✅ Correct: A

📖 Explanation:

When Process B attempts to modify a read‑only page, the CPU raises a protection fault. The kernel then applies copy‑on‑write: it allocates a new physical page, copies the original contents, and maps the new page as writable for Process B. This leaves Process A still sharing the original page. Option A describes demand paging, which brings pages into memory but does not duplicate them on write. Option C would be unnecessary overhead, and Option D would violate program semantics.

Q4. How does copy‑on‑write complement demand paging in a system that uses lazy loading of pages?

🔹 A. COW replaces demand paging entirely
🔹 B. COW ensures pages are loaded only when written, while demand paging loads on first access
🔹 C. COW forces all pages to be resident at process start
🔹 D. COW only works for file‑backed pages, not anonymous memory

💡 Difficulty: medium | ✅ Correct: B

📖 Explanation:

Demand paging brings a page from disk into RAM the first time any process accesses it, regardless of read or write. Copy‑on‑write adds a second layer: after a page is present, it remains shared read‑only until a process writes to it, at which point the kernel copies the page. Thus demand paging handles initial loading, and COW reduces unnecessary copying for read‑only uses. Options A and C misrepresent the relationship, and D is inaccurate because COW works for both file‑backed and anonymous pages.

Q5. Three processes concurrently load the same large shared library. Without copy‑on‑write, each would have separate physical copies. Which outcome results from using copy‑on‑write for the read‑only mappings?

🔹 A. Each process still gets a private copy of every page
🔹 B. All processes share the same physical pages until a write occurs
🔹 C. Only the first process gets the library, others fail
🔹 D. The library is loaded into swap space

💡 Difficulty: medium | ✅ Correct: A

📖 Explanation:

With copy‑on‑write, the kernel maps the library read‑only for each process, allowing them to share the same physical pages. Only when a process attempts to modify a page does the kernel create a private copy for that process. Therefore memory is conserved while preserving correctness. Option A describes the situation without COW. Option C is false because all processes can map the library. Option D mischaracterizes swapping, which is unrelated to the sharing mechanism.

Q6. A process has a read‑only shared mapping of a configuration file. It attempts to modify a setting, causing a page fault. What does the OS do?

🔹 A. Terminate the process with a segmentation fault
🔹 B. Create a private writable copy of that page via copy‑on‑write
🔹 C. Ignore the write and continue
🔹 D. Reload the entire file as writable

💡 Difficulty: medium | ✅ Correct: A

📖 Explanation:

When the process writes to a read‑only page, the hardware raises a protection fault. The kernel's copy‑on‑write handler allocates a new physical page, copies the original data, and remaps the page as writable for the faulting process. This preserves the original shared view for other processes. Option A would only occur if the mapping were not COW-enabled. Option C would break program semantics, and Option D would be far more expensive than a single‑page copy.

Q7. What is a primary trade‑off when using copy‑on‑write for inter‑process shared memory versus using explicit shared memory segments?

🔹 A. COW always uses more memory
🔹 B. COW may incur copy overhead on first write, while explicit sharing has constant sharing cost
🔹 C. Explicit shared memory cannot be protected
🔹 D. COW cannot be used with fork

💡 Difficulty: medium | ✅ Correct: A

📖 Explanation:

Copy‑on‑write saves memory while pages remain read‑only, but the first write to a shared page triggers a copy, introducing latency and extra memory use. Explicit shared memory segments are set up for concurrent read/write access, avoiding the copy cost but requiring synchronization mechanisms and potentially more memory if many processes write simultaneously. Option A is opposite of the usual benefit. Option C is false because shared memory can have protection flags. Option D is incorrect; COW works perfectly with fork.

Q8. A process’s virtual address space has a hole from \(0x60000000\) to \(0x70000000\). The stack grows downwards and currently ends at \(0x60100000\). If the stack expands by \(0x20000\) bytes, which address will cause the first page fault?

🔹 A. 1610612736
🔹 B. 1609564160
🔹 C. 1611661312
🔹 D. 1611657216

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation:

The stack top is at \(0x60100000\) and grows toward lower addresses. Expanding by \(0x20000\) bytes moves the stack down to \(0x5FF00000\). The first address that enters the unmapped hole is the boundary at \(0x60000000\); when the stack crosses this address, the page is not present, causing a fault. Options B and D are addresses inside the already‑mapped region, and C is the original top, which is already valid.

Q9. A database system implements point‑in‑time snapshots using copy‑on‑write. At time T0, a process forks to create a child that will modify data. Which sequence correctly describes memory handling to keep the snapshot intact?

🔹 A. Both parent and child share all pages; when child writes, the OS copies only the modified pages
🔹 B. The OS copies the entire address space for the child immediately
🔹 C. Only the child receives a copy of every page, leaving the parent with empty pages
🔹 D. The snapshot is stored on disk, unrelated to copy‑on‑write

💡 Difficulty: hard | ✅ Correct: B

📖 Explanation:

At T0 the parent and child share all pages read‑only. When the child writes to a page, copy‑on‑write triggers a copy of that specific page, preserving the original for the parent’s snapshot. This selective copying minimizes overhead while maintaining a consistent view. Option B would waste memory by copying everything. Option C would break the snapshot because the parent would lose its data. Option D ignores the in‑memory snapshot mechanism.

Q10. In workloads with frequent writes to shared library data, how does copy‑on‑write affect overall system performance compared to pre‑allocating private copies?

🔹 A. COW always improves performance regardless of write frequency
🔹 B. High write rates cause many page copies, reducing performance versus private copies
🔹 C. COW eliminates the need for any page faults
🔹 D. COW forces the CPU to run at lower clock speeds

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation:

When writes are rare, copy‑on‑write saves memory and reduces copying. However, with a high rate of writes, each write may trigger a page copy, leading to many page faults and extra memory traffic, which can be slower than having each process start with its own private copy. Option A is too absolute; Option C is false because page faults still occur on writes. Option D is nonsensical.

Q11. Process X creates a child via fork. Without copy‑on‑write, each would need 200 MB of physical memory for its address space. With copy‑on‑write, only 30 MB of pages are written before the child exits. Approximate memory saved?

🔹 A. 170 MB
🔹 B. 200 MB
🔹 C. 30 MB
🔹 D. 0 MB

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation:

Initially both processes share the same 200 MB of pages read‑only, consuming only 200 MB total. During execution, 30 MB of pages are copied because of writes, adding 30 MB of private memory. The total physical memory used becomes 200 MB + 30 MB = 230 MB, but without COW it would have been 400 MB. The saved memory is roughly 400 MB − 230 MB = 170 MB. Options B and C misinterpret the calculation, and D suggests no saving, which is incorrect.

Q12. What security implication arises from copy‑on‑write pages that are initially read‑only shared among processes?

🔹 A. An attacker can modify another process’s memory without triggering a copy
🔹 B. Copy‑on‑write prevents any process from reading shared pages
🔹 C. If a process exploits a copy‑on‑write race, it may infer the presence of other processes
🔹 D. Copy‑on‑write automatically encrypts shared pages

💡 Difficulty: hard | ✅ Correct: A

📖 Explanation:

Because pages are shared read‑only until a write occurs, a malicious process cannot directly alter another process’s memory, but timing attacks can reveal whether a page is still shared or has been copied, giving hints about other processes’ activity. Option A is false because writes trigger a private copy. Option B misstates the read capability. Option D is unrelated; COW does not provide encryption.
