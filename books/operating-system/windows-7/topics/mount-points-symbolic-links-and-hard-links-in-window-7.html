What is Mount points, symbolic links, and hard links in Window 7?

Definition:
NTFS supports mount points (junctions), symbolic links, and hard links enabling flexible namespace organization where link resolution follows \( \text{Path}_{\text{resolved}} = \text{Resolve}(\text{Link}) \) with cycle detection.

Example:
Directory junction C:\Data\Backup pointing to D:\Backups allows seamless redirection without drive letters.

Reason:
Advanced linking enables storage virtualization, application compatibility shims, and flexible data organization while maintaining single-copy semantics for hard links and transparent redirection for junctions.

Q1. Which of the following best defines a symbolic link in a Unix-like file system?

A.A special file that contains a path to another file or directory ✅
B.A duplicate copy of the original file's data
C.A reference that points directly to the same inode as the target
D.A hidden file that cannot be accessed by users
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: The correct answer is A because a symbolic link is a special file that stores a pathname pointing to the target, allowing the link to reference files across different directories or file systems. Option B describes a regular copy, which consumes separate storage. Option C describes a hard link, which shares the same inode. Option D is unrelated; hidden files are still regular files. In practice, using a symbolic link lets administrators redirect configuration files without moving the original data.

Q2. How does a hard link differ from a symbolic link regarding the way the operating system tracks the target?

A.Hard links create a new directory entry that points directly to the same inode as the target ✅
B.Hard links store the absolute path of the target file
C.Hard links use a separate metadata structure to map to the target
D.Hard links are only possible on network file systems
💡 Difficulty: easy | ✅ Correct: A

📖 Explanation: The correct answer is A because a hard link creates another directory entry that points directly to the same inode, so both names refer to identical data on disk. Option B describes a symbolic link, which stores a pathname rather than an inode reference. Option C is incorrect; hard links do not use separate metadata structures. Option D is false because hard links work on local file systems, not only network ones. Understanding this distinction helps administrators choose the appropriate link type for file sharing.

Q3. Why does the operating system prevent the deletion of a file that still has active hard links?

A.Because the file's data is still referenced by at least one directory entry ✅
B.Because the file system needs to preserve the symbolic link target
C.Because the inode is locked until all processes close the file
D.Because the file is stored in a protected system directory
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: The correct answer is A because a file cannot be removed from the file system while any hard link still points to its inode; the data remains needed until the link count drops to zero. Option B is wrong since symbolic links are independent path references and do not affect the target's existence. Option C misstates inode locking; the inode is released only after the link count reaches zero, not based on open handles. Option D is irrelevant because directory protection does not govern link deletion. This rule ensures data integrity when multiple names reference the same file.

Q4. A system administrator wants to replace a large log directory with a new location without changing any application configurations. Which link type should they use to point /var/log to /mnt/storage/logs, and what is a key advantage of that choice?

A.Create a hard link; it works across different file systems
B.Create a symbolic link; it can reference directories on another file system ✅
C.Create a hard link; it updates the target automatically when moved
D.Create a symbolic link; it requires less disk space than a hard link
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: The correct answer is B. A symbolic link can point to a directory located on a different file system, allowing /var/log to redirect to /mnt/storage/logs without moving the original files. Option A is incorrect because hard links cannot span file system boundaries. Option C is false; hard links do not automatically update when the target moves. Option D is misleading; while symbolic links use minimal disk space, the primary advantage here is cross‑filesystem capability. Using a symbolic link lets the administrator change the log location transparently for all applications.

Q5. What is the effect of mounting a separate file system at /mnt/data on existing symbolic links that point to /home/user/docs inside the original root file system?

A.The symbolic links become broken because the target path is no longer reachable
B.The symbolic links continue to work because they resolve paths after the mount ✅
C.The symbolic links are converted into hard links automatically
D.The symbolic links are ignored by the kernel during mount operations
💡 Difficulty: medium | ✅ Correct: B

📖 Explanation: The correct answer is B because symbolic links are resolved at the time of pathname traversal, after the mount operation, so a link that points to /home/user/docs still reaches the original target even if another file system is mounted elsewhere. Option A would only be true if the mount point replaced part of the path the link references. Option C is incorrect; the kernel does not convert links. Option D is false; mounts do not ignore existing symbolic links. This behavior is essential for maintaining link functionality across mounts.

Q6. A developer copies a directory tree from /src to /dst using the command `cp -r /src /dst`. After the copy, they notice that changes in /src affect files in /dst. Which link type likely caused this behavior, and how should the command be altered to avoid it?

A.Hard links were created; rerun the command without the `-l` option ✅
B.Symbolic links were created; add the `-L` option to follow links
C.Hard links were created; use `cp -r -a` to copy file contents
D.Symbolic links were created; use `cp -r -P` to preserve them
💡 Difficulty: medium | ✅ Correct: A

📖 Explanation: The correct answer is A. The observed shared changes indicate that the destination contains hard links to the source files, which occurs when the copy command is invoked with the `-l` (link) option. Removing that option and running a plain `cp -r` copies the actual file contents, breaking the link relationship. Option B misidentifies symbolic links, and option C suggests `-a` would fix the issue, but `-a` preserves links rather than copying data. Option D also confuses link types. Using the proper copy command ensures independent copies for backup or deployment.

Q7. On a server, /var/www is a mount point for a separate file system. An administrator creates a symbolic link /var/www/html -> /srv/web/html. Later, they move /srv/web to /opt/web and update the link accordingly. However, a running web service still serves content from the old location. What kernel mechanism explains this behavior, and how can the service be forced to use the updated link without restarting the entire server?

A.The kernel caches directory entries; clearing the dcache with `sync; echo 3 > /proc/sys/vm/drop_caches` forces re-evaluation
B.The kernel caches inode information; dropping the inode cache with `echo 2 > /proc/sys/vm/drop_caches` updates the link
C.The kernel uses the mount namespace; remounting the filesystem with `mount --make-rprivate` updates the link
D.The kernel resolves symbolic links at the time of file open; closing and reopening file handles in the service updates the target ✅
💡 Difficulty: hard | ✅ Correct: D

📖 Explanation: The correct answer is D. The kernel resolves a symbolic link each time a process opens the file, so if a service keeps file descriptors open, it will continue to read from the original inode even after the link is changed. Options A and B refer to cache dropping, which does not affect already opened handles. Option C mentions mount namespaces, unrelated to link resolution. To make the service use the new target without a full restart, the administrator can close and reopen the affected file descriptors, or reload the service configuration, prompting the kernel to resolve the updated link.
